## 1. 目标与本次范围

数字人不应只有用户发消息时才发生变化。它需要在虚拟时间中经历自己的生活：完成任务、遇到小麻烦、得到小惊喜、改变原来的安排，并在之后的互动中记得这些经历。

本设计以第一版 DayPlan 为生活骨架。后端提供心理作用机会与现实扰动边界；DayPlan 先向 Director 获取当下关切和行动倾向，再生成具体事件及可能的计划走向。需要新的取舍时双方继续协商，Executor 提交后再通知 Director 决定行动和表达。提交前的商量和提交后的通知是两个不同阶段。

本次不是重做用户输入处理：

- 用户提出新安排、双方确认约定等，继续由 Director 理解；需要调整日程时与 DayPlan 协商。
- 本次新增的是没有用户直接推动时，数字人自身也能产生的模拟生活事件。
- 不重新编译 PersonWorldProfile，不修改原始聊天和 LightRAG 原始世界图谱。
- 不修改认知模型配置，不启用 LoRA，不删除 PersonaActor。
- 第一版只覆盖低现实扰动、存在合理处理办法的日常变化，不构建完整的社会、天气或多人物仿真系统；可处理不意味着必然顺利解决。

核心原则：**计划是打算做什么，事件是虚拟分支里发生了什么，通知是让另一个 Agent 知道发生了什么。三者不能混为一体。**

## 2. 角色与权限

| 组件 | 职责 | 边界 |
| --- | --- | --- |
| Scheduler | 根据虚拟时间产生检查机会，维护冷却和待处理任务 | 不调用模型编故事，不判断自然语言 |
| OpportunityPolicy | 可复现抽样，选择可选心理作用方向及现实扰动预算 | 不生成剧情，不指定人物最终情绪，不把抽样结果当事实 |
| DayPlanAgent | 获取 Director 的当前状态意见，生成生活候选、协商走向并维护计划 | 不绕过协商独自决定人物反应，不发最终聊天 |
| Executor | 验收提案，原子提交事件、计划变更和待投递通知 | 不通过关键词或正则理解人物与剧情 |
| Director | 提供当前关切、情绪倾向与行动意图，参与事件走向协商；提交后决定行动和表达 | 不编制完整日程，不为读取计划询问 DayPlan，不审批所有基础规划 |
| PersonaActor | 在 Director 决定表达后形成自然的消息 | 不自行创造生活事件或修改计划 |

DayPlan 与 Director 保持同级。`plan_day` 基础规划仍可在职责内独立提交；`advance_life` 的新事件必须先取得适用于当前机会的 Director 意见。此处是状态依赖协作，不是主从审批：Director 判断人物此刻更可能怎样选择，DayPlan 判断这些选择如何落实到生活。一次答复若已明确允许的选择范围，不要求每个候选再固定往返确认。

## 3. 第一天的骨架与后续变化

### 3.1 第一版计划

DayPlan 首先生成可执行的正常一天，例如工作、午餐、通勤、晚餐和休息。

第一版计划的版本必须可追溯。后续修改产生新版本，不覆盖初始版本，也不把上一轮模拟选择升级成新的历史规律。实现前需补齐计划版本留存：不能仅依赖当前行的 version 数字或 Phoenix 保存旧版本内容。

第一版是参考骨架，不是不可修改的剧本。已发生部分和明确承诺受保护；未来的可调整部分可以随事件变化。

### 3.2 逐步展开，而非早上生成全天意外

不在早上预先生成“下午被同事叫住、晚上朋友邀约”等完整剧情并交给 Director。

调度器可以预先安排抽样检查时刻，但具体事件在接近实际发生的时刻才由 DayPlan 生成。尚未发生的候选不能进入已发生经历、用户可见消息或事实记忆。

对预计持续时间和未来结果也要区分：

- “刚收到返工要求”可以成为此刻的模拟事件。
- “预计需要半小时”属于估计及排程选择。
- “半小时后已经完成”不能在开始时就记成发生过的结果。

第一版不要求对所有小活动建立完整任务生命周期；明确区分起因、预计影响与实际已确认结果即可。

## 4. 随机机制：机会随机，内容符合人物

### 4.1 机会、理解与内容分工

第一层由后端控制机会：

- 此刻是否允许检查；
- 是否已到冷却时间；
- 当天的事件数量和时间扰动预算是否还有余量；
- 抽样是否激活；
- 可选的心理作用领域、作用方向、心理重要性预算，以及现实扰动边界和有效窗口。

第二层由双方协商后由 DayPlan 形成内容：

- 结合人物画像、当前活动和近期经历，这个机会是否适合使用；
- Director 补充此刻的关切、情绪背景、行动倾向和应保护的意图；
- 发生什么具体事件；
- 是否改变安排，改变哪些部分；
- 或者明确选择 `no_event`。

一次机会并不意味着必须发生事件。抽样未激活时不调用模型；已激活但不适合生成时，Agent 也可以返回 `no_event`，该机会随即结束，不能重新抽到“有故事”为止。

### 4.2 可复现与去重

机会拥有后端生成的稳定 ID、抽样种子或抽样值、策略版本、首次检查时间和过期时间，并在执行前持久化。

同一机会的 Worker 重试、进程重启和模型格式修复必须沿用原抽样结果，不重新抽奖。不用进程内不稳定的 `hash()` 当跨重启种子。

计划输入版本与抽样身份分开：计划改变时重新校验原机会是否还适用，不因一个新输入就获得额外抽样次数。失去适用场景的机会取消或过期，不硬套到新的活动上。

### 4.3 频率与时间位置

事件检查不全部固定在生活块起点，否则数字人只会在整点切换活动时遇到意外。可在适用生活块内部抽取检查时刻；计划变化后重新核对该时刻是否有效。

设置统一、可配置的运行策略，包括：

| 配置 | 含义 |
| --- | --- |
| enabled | 是否启用自主模拟事件 |
| block_rate_policy | 按活动情境确定每虚拟小时机会率，不按轮询次数或块数量计数 |
| psychological_affordance_weights | 可选心理领域与方向的条件权重，包含 open；不是具体事件题库 |
| disruption_weights | 机会激活后抽取允许的现实扰动档位；不等于情绪强度 |
| minimum_virtual_gap | 同分支事件之间的最小虚拟时间间隔 |
| max_events_per_local_day | 每个分支本地日期的事件上限 |
| max_shift_per_event | 单次事件对计划时间的最大扰动 |
| max_total_shift_per_day | 当天累计排程扰动预算 |
| opportunity_ttl | 调度延迟后机会仍有意义的有效窗口 |
| retry_policy | 临时技术失败的有限重试和退避 |

具体默认数字在实现前集中确认；不把未经验证的频率写成已认可的产品行为。默认体验方向是稀疏、轻量，不要求每天或每个生活块都发生事件。

活动情境使用 Planner 已提供的结构化活动属性；缺失时采用保守默认或不激活，不用正则从名称猜工作、睡眠。机会率随活动块变化，持续时间按虚拟时间累计；可采用分段强度 λ(t) 的等待时间抽样，区间至少一次机会的概率为 `1-exp(-∫λ(t)dt)`。相同活动拆成多个块不应增加期望机会数。冷却、上限和 Agent 的 no_event 会降低最终事件频率，这不是严格的无约束泊松过程。

先排除不符合当前活动、剩余时间、预算的组合，再对剩余权重归一化；没有合法组合则不激活。心理领域、方向和扰动存在相容性约束，不能把所有字段独立抽样后拼成矛盾要求。暂不设置细粒度主题分布，也不维护具体事件题库。概率属于可版本化产品参数，不是心理学测得的普遍人生频率。

计数按分支本地日期计算，时间点统一存储为 UTC。暂停虚拟钟时停止产生和激活机会；恢复时不补演停机期间每一个可能事件。过期机会直接标记过期，重新从当前处境安排下一次检查。

## 5. 心理作用机会与第一版边界

### 5.1 理论依据与工程取舍

- Argyle、Furnham、Graham 的《Social Situations》提供目标、角色、规则、互动与环境的情境分析视角，用于从现有计划和画像理解事情发生的处境，而不是建立庞大剧情分类。参见[出版社章节与目录](https://www.cambridge.org/core/books/abs/social-situations/rolesystems/C74A837E21B9B13E7332C41D6D6FEE33)。
- 事件系统理论区分新颖性、扰动性、关键性及时间和影响传播；本项目借鉴这些区别，但不把组织研究的量表直接当成人物仿真参数。参见[原始论文](https://www.morgeson.com/downloads/morgeson_mitchell_liu_2015.pdf)。
- Lazarus 与 Folkman 的《Stress, Appraisal, and Coping》及其评价研究帮助区分外部变化、人物关切和应对选择，不把事件自动等同于固定情绪。参见[书籍目录与介绍](https://books.google.com/books?hl=En&id=i-ySQQuUpr8C)、[作者的评价与应对研究](https://pubmed.ncbi.nlm.nih.gov/3701593/)。本设计依据公开章节、预览及研究，不声称已逐页阅读全部著作。

下面的字段是工程组合，不是统一心理量表。自主、胜任、关系连接等心理领域复用 Profile 已采用的概念；领域表示可以触及的体验，不表示已测出某种心理缺口，更不是强制补偿目标。

### 5.2 后端机会契约

```json
{
  "psychological_affordance": {
    "domains": ["autonomy"],
    "direction": "open",
    "salience_budget": "low"
  },
  "constraints": {
    "max_schedule_disruption": "minor",
    "max_added_minutes": 15,
    "allowed_scope": "current_block",
    "protect_confirmed_commitments": true,
    "allow_long_term_consequences": false,
    "require_plausible_handling_option": true,
    "require_user_intervention": false
  }
}
```

15 分钟只是示例，不是已确定默认值。窗口、当前活动引用、策略版本与随机身份另由运行时绑定。模型读取解析后的当前处境，不重复生成数据库信封。

| 字段 | 含义与使用边界 |
| --- | --- |
| domains | 第一版可为空，或选 autonomy / competence / relatedness；不为了填字段强行制造心理主题，不限制 Agent 的具体事件内容 |
| direction | supportive / challenging / mixed / open；表示支持性机会、轻微挑战、混合或开放，不规定人物最后开心还是烦躁 |
| salience_budget | 可触及个人关切的重要性上限；第一版 low，不是指定实际情绪强度，也不能靠类型检查证明心理影响一定很小 |
| max_schedule_disruption | 现实排程扰动上限：none / minor；与心理重要性分开，重大现实变化第一版禁用 |
| max_added_minutes / allowed_scope | 时间与影响范围的可验收上限；不得用多个小改动绕过累计预算 |
| require_plausible_handling_option | 要有解决、绕过、推迟或拒绝的可行选择，不表示必须执行某个选择或保证成功 |

后端不得提交“同事请求帮忙”“她应该感到被认可”等内容要求。Director 可以认为当前不适合该机会，双方可以 no_event；不得在同一机会里反复换心理方向直到生成成功。也不能根据“需要连接”就必然安排朋友邀约，不能把系统变成持续制造挫折或自动满足需求的装置。

### 5.3 具体内容由 Agent 生成

下表仅解释范围，不是后端枚举、固定题库、必填主题或抽样分布：

| 类别 | 示例 | 可能的计划影响 |
| --- | --- | --- |
| 日常顺利 | 一项任务提前完成 | 提前休息或保留空余缓冲 |
| 轻微工作变化 | 临时返工、同事求助 | 调整工作内容，适度顺延 |
| 生活小插曲 | 常去的用餐窗口没开 | 更换用餐方式，通常无需重排全天 |
| 小惊喜或体验 | 吃到喜欢的菜、发现一本想读的书 | 形成可记忆经历，不一定改时间表 |
| 轻量环境变化 | 虚拟场景中下雨、路程略有延误 | 调整移动或户外安排 |
| 轻量社交机会 | 收到朋友的普通邀约 | 先记录收到邀约，不自动承诺参加 |

天气、同事和朋友的动作均属于虚拟分支中的模拟，不伪装成真实天气服务或真实第三方消息。没有相关人物资料时不要为了小事件创造一整套真实身份和履历。

第一版不自动生成重大疾病、事故、失业、关系破裂、重大财务变化、危险情境等会重写人物生活的事件，也不通过频繁制造麻烦或危机迫使用户持续回应。这些语义边界由 Agent 判断，Executor 校验结构化范围；不能宣称正则能全面验证剧情安全或心理重要性。

随机事件不得擅自取消或改变与用户已确认的承诺。若一个候选必须违反承诺才能成立，DayPlan 应选择无事件、调整为不冲突的轻量事件，或仅提出尚待协商的后续安排；不得先把违约写成事实再要求 Director 圆场。

## 6. 同一个 DayPlanAgent 的两种任务

不增加独立“突发事件 Agent”。同一个 DayPlanAgent 使用统一 Harness，根据明确的任务模式工作：

### 6.1 `plan_day`：制定或修订基础日程

沿用现有职责：读取人物理解、日期类型、约束和共享计划，输出日程提案或协商问题。

### 6.2 `advance_life`：推进模拟生活

新增输入包括：

- 当前机会的可理解约束：可选心理作用方向、心理重要性和现实影响预算、有效窗口；
- 当前本地时间和所在生活块；
- 昨天、今天、明天的已提交计划；
- 初始骨架与当前计划之间已经发生的变化；
- 当前有效承诺与不可回写时段；
- 已发布人物画像中的生活处境、规律、偏好和关系背景；
- 近期已提交模拟事件、尚未结束的影响、相关协商记录；
- Director 对本次机会给出的状态意见、有效范围及尚未解决的分歧；
- 当前调查笔记与草稿。

模型不需要数据库路径、随机种子、内部主键或重复的工具 JSON Schema。事件与任务身份由代码绑定，工具由 LangChain 注册。

`advance_life` 的行为要求：

1. 先检查机会是否仍适用；明显不适用可直接 no_event，不必无意义地唤醒 Director。
2. 有意继续生成时，先通过共享 request 向 Director 获取本次机会的当前状态意见；不得只读静态 Profile 就推定其此刻情绪。
3. 根据机会与 Director 意见生成具体候选；涉及尚未授权的取舍时以 proposal 继续商量，不追求戏剧性。
4. 区分外部变化、人物的理解、准备采取的行动和未来预计结果；只有提交成功的内容才是已发生经历。
5. 需要排程变化时尽量局部修改，不借机重写全天；无需改日程的小事件仅提交事件。
6. 信息不够、机会不合适或会损害承诺时允许 no_event；未知当前状态不代表可以随意补写情绪。
7. 不编写要发送给用户的台词，不决定 Director 必须回复。

活动字段继续只写具体要做什么。例如“处理返工任务”，而不是“处理返工任务（被同事使唤，情绪低落，期待用户关心）”。

## 7. 输出契约与数据落点

下列为拟议领域契约，不是当前代码已经存在的类型名。实现时使用 Pydantic 约束结构，模型输出和持久化信封分开。

### 7.1 模型输出

```text
LifeAdvanceDecision
  outcome: no_event | request_context | discuss | submit_event
  no_event_reason: 可选的简短原因
  peer_request: request_context 时向 Director 请求状态
  discussion: discuss 时的问题、候选或异议
  event: discuss 或 submit_event 时的候选
  plan_proposal: 与该事件绑定的可选既有 DayPlanProposal

SimulatedEventProposal
  occurrence: 具体变化、涉及的角色；时间由提交信封绑定
  situation: 当前活动和必要社会处境；复用背景，不重写人物履历
  characteristics: 新颖性、现实扰动、对目标的重要性；语义判断允许未知
  impact: 预计增加时间、受影响安排、影响范围与可能后续影响
  appraisal: 可选的暂定理解、相关关切；关联 Director 意见，不指定固定情绪
  handling: 可行选项、双方选定的行动意图、尚未解决的问题
  actual_outcome: 尚未发生的结果必须为空
  assumptions: 模拟设定与不确定部分
  context_references: 已提供背景引用，可为空，不伪造原始消息证据
```

通过 discriminated union 约束各 outcome 的必填与禁止字段。请求阶段不能提交事件；讨论阶段的候选不能更新已提交投影。该结果映射到既有 AgentTurnResult 和 PeerMessage，不引入第二套路由循环。具体嵌套字段在实现时用 Pydantic 定义，不退化成任意字典。

后端为提交信封绑定 `opportunity_id`、`proposal_id/revision`、Director 意见消息引用、输入/计划/状态版本和有效期。Director 对具体候选的同意只适用于该候选版本；若首次答复给出允许的选择范围，DayPlan 可据此提交，并说明方案如何符合该范围。代码只验证意见存在、版本有效、类型和硬约束；语义上的符合性由双方判断，不能宣称后端理解自然语言授权。

人物评价不要求 0–100 情绪分数或完整心理状态方程；初步理解可以被 Director 修正。选定行动不等于行动已完成，不把预计恢复时间当作实际结束时间。

### 7.2 后端持久化

优先复用现有领域事件账本及队列，不为观测再建 AgentRun/Step/ToolInvocation。

| 数据 | 需要保存的内容 |
| --- | --- |
| 事件机会 | 稳定机会 ID、分支、虚拟检查时刻、有效期、抽样值、策略版本、状态、重试信息 |
| 协商工作状态 | 当前阶段、候选及其修订、Director 意见引用与有效范围、输入版本、分歧、恢复位置 |
| 模拟生活事件 | 事件 ID、机会 ID、`origin=simulation`、实际生效虚拟时间、具体内容、预计影响、提交版本与背景引用 |
| 计划版本 | 初始骨架、后续已提交版本、前后版本关系、导致修改的事件 ID |
| 待投递通知 | 稳定消息 ID、接收方、事件与回执引用、待处理/已处理状态 |

机会生命周期为 `scheduled → active → committed / no_event / expired / cancelled / blocked`；未激活结束为 `inactive`。active 内单独维护阶段 `awaiting_context / drafting / discussing / ready_to_submit` 和执行状态 `pending / running / waiting / retryable_failed`，避免把等待对方误报成失败。仅 committed 对应正式模拟事件。

候选另有 `proposed / agreed / rejected / superseded / committed` 状态。agreed 仍非事实，必须取得 Executor 成功回执。状态转换由适配层和回执控制，不解析正文“已同意”或“已发生”。no_event 是正常完成，技术失败不能伪装成 no_event。

事件自身属于分支虚拟经历，并非现实目标人物的事实；来源标签不可在摘要、检索或通知中丢失。

## 8. 执行与原子提交

逻辑流程为：

```text
Scheduler 到达检查时刻
  → 领取并校验机会，保存抽样结果
  → 未激活：结束机会，不调用模型
  → 已激活：DayPlan.advance_life
      → 明显不适用：no_event，结束
      → request：向 Director 请求当前状态与选择范围
      → answer：Director 提供意见，或建议不使用机会
      → DayPlan 形成候选；范围明确可提交，否则 proposal/answer/objection 继续协商
      → 无合适候选：no_event，结束协作任务
      → 已有有效协商依据的 event + 可选 plan_proposal：Executor 验收
          → 拒绝：返回具体原因，有限修正或结束机会
          → 成功：同一事务保存事件、计划版本及待投递通知
              → 路由 Director 处理通知
              → Director 自主选择等待、行动、协商或表达
```

模型调查期间不持有长数据库写事务；仍使用既有分支写者控制、任务租约和输入版本守卫。

提交前重新读取当前虚拟时间、计划版本、用户输入版本和承诺，检查机会是否过期。若模型运行期间用户改变安排，不提交旧上下文下的候选。

Director 当前状态意见也绑定输入修订、状态修订和虚拟有效期。新的用户消息到达后，先完成正常 Director 处理，再基于最新版本刷新意见；不能机械复用几分钟前的情绪描述。失效时仍是同一次机会和原抽样，候选 superseded 后从检查点恢复协商；超出窗口就过期，不无限延期或重抽。

事件不允许通过回写旧时间假装准点发生：首次生效时间由提交阶段确定。已提交事件重试则读取原回执，不能重新设置发生时间。

事件导致当前活动立即变化时，应从允许的当前/未来边界表达变化。现有“已开始块整体不可修改”的规则需要一个明确受限的事件切分契约：保留已经过去的前缀，只调整尚未发生部分，不给模型开放任意改写整个已开始块的权限。第一版若仍采用 15 分钟粒度，计划变化可以从下一合法刻度起生效；期间的短时影响作为事件内容交给 Director，不回写到上一刻度。

Executor 的确定性检查包括权限、类型、时间顺序、影响预算、来源归属、版本、幂等性和硬约束；人物一致性与事件合理性由 Agent 结合上下文判断，不用正则从正文识别“这是返工还是情绪低落”。

扰动预算按提案与已提交计划的实际差异计算，同时检查事件声明的额外占用，不仅相信模型自报分钟数。计划延后、活动取消和跨块替换分别受约束，不能把取消整段任务报成“增加零分钟”。事件、计划修订、预算扣减及 outbox 在同一事务中完成；无事件不扣已发生事件数，但该机会已使用，仍受独立的机会调用频率限制。

## 9. 提交前协商与提交后通知

### 9.1 Director 提供可用的当下理解

DayPlan 通过 `request` 请求本次机会的 `life_event_context`。Director 从近期互动、已确认行动、尚未结束的经历和共享画像中形成简短意见：

```text
DirectorLifeContext
  current_concerns: 此刻主要在意什么，可未知
  affective_context: 近期互动后的感受倾向与相关原因，可未知
  action_tendencies: 倾向接近、回避、继续或暂缓什么，不做固定映射
  protected_intentions: 需要保护的承诺和当前意图
  response_scope: 在何种范围内 DayPlan 可继续形成方案
  open_questions: 会改变选择的未解问题
  recommendation: proceed | discuss | no_event
```

这不是新的全量 LifeState，也不是公开内部思维链。稳定人格来自 Profile；当前理解由 Director 维护并明确表达到可恢复共享消息中，不依赖它某次调用的隐藏上下文。没有近期状态时明确未知，可以结合画像给出保守选择范围，但不能编造“刚才情绪低落”。不新增心理诊断或每分钟情绪打分任务。

心理与情绪的连续性通过“先前状态意见 + 此后实际发生的互动/生活事件 + 已经过的虚拟时间 + 当前目标”交给 Director 更新理解，不使用固定的“疲惫减 10、开心加 20”公式。意见信封记录基于哪些已提交输入、生成时刻、修订号和适用窗口；状态修订指这份意见的投影版本，不要求新增全量 LifeStateVersion。旧意见保留可追溯，新意见可以修正它；不能自动清空未结束的关切，也不能假定负面感受经过固定分钟数就必然消失。

提交前 appraisal 是假设性的反应理解；提交后 Director 结合实际生效事件重新判断是否延续该理解，并将必要的新状态写成简短可恢复意见。候选取消时不把其预计心理影响累积到人物状态。实际后续结果由之后的生活推进或交互确认，不能在预计结束时刻到达时直接宣布成功。

### 9.2 协商示例与最短路径

后端提供“自主选择相关、轻微扰动、不得损害约定”的机会，不提供具体故事：

1. DayPlan → Director/request：当前处于工作块；请求此刻关切和可以接受的行动范围。
2. Director → DayPlan/answer：目前倾向安静完成手头任务，不愿额外承担人际义务；可安排不增加义务的小选择，不影响晚间约定。
3. DayPlan 生成具体候选与走向。若完全在上述范围内，附上意见引用提交；若需要承担新义务，则先以 proposal 说明取舍，等待 Director 意见。
4. Director 对超出范围的候选给出选择或 objection；DayPlan 调整方案或 no_event，不以同级协商为名强行反复说服对方。
5. Executor 成功提交后，DayPlan 才发送关联回执的 notification；Director 再决定是否表达。

不是固定六轮模型调用，也不是给全部 DayPlan 工作添加审批。每次新机会至少取得一次适用的 Director 状态意见；同一机会恢复时可以复用仍有效的意见。日常聊天判断无需询问 DayPlan 的原有规则不变。

### 9.3 LangGraph 调度、等待与防循环

复用平级 director/day_planner/executor 节点，PeerMessage 使用既有 request、answer、proposal、objection、submit、commit_result、notification；心理上下文请求只是 payload.operation，不新增网络 A2A 或工具内嵌 Agent。

全局消息保留协商记录；tasks/proposals 保存阶段和候选投影，已提交 day_plans 只随成功回执更新。消息投影明确标记“候选，未发生”，PersonaActor 也不能将可见候选作为现实经历说给用户。

同一分支保持串行写入，但不能持有整个协商期间的分支锁或阻塞等待对方。每个节点结束后保存检查点并交回 Router；等待持久化为 waiting，队列可优先处理用户消息。模型调用中有新输入时沿用统一 Harness 的输入失效/取消机制；若供应商无法立即取消，返回结果不得提交，不能承诺即时抢占。后台机会不得成为普通聊天的前置依赖。

每分支最多一个活跃自主事件协商，避免多个候选各自消耗同一时间预算。重复请求使用 task_id/reply_to 和稳定消息 ID 去重。无新信息、候选版本或已解决分歧的重复往返受统一协作预算与无进展守卫约束；没有合适选择以 no_event 结束，模型/服务耗尽以明确失败状态结束。不另写 max_rounds=2，也不允许新 Job 重置累计预算。

协商后 no_event 需要结束任务并留下结果，必要时答复正在等待的对方；它不产生“生活事件已发生”的通知，不触发表达。Director 无法提供意见时可退避等待至机会过期，不能绕过协商直接生成并提交。

### 9.4 提交后的可靠通知

复用当前 PeerMessage 的 `notification` 类型，发送方为 `day_planner`、接收方为 `director`。通知必须关联已提交事件和 Executor 回执。

例如提交成功后，通知的语义内容是：

> 已提交这次生活变化；预计占用当前活动中的十分钟，后续安排和已确认约定不变。具体事件、尚未结束的影响和双方选定的行动见关联内容。

消息元数据由运行时补齐事件 ID、机会 ID、计划版本和提交回执。没有计划变化时明确说明“日程未变”，不伪造新计划版本。

**记录到共享 State 不等于已经送达。** 需要同时满足：

- 消息在可恢复的共享协商记录中可见；
- Director 获得一次实际处理机会；
- 处理完成有持久化确认，重试不重复处理同一通知。

采用轻量事务 outbox 语义：事件提交事务同时保存待投递通知，随后由现有队列和 Router 恢复投递，不引入独立消息中间件。

若进程在“事件提交完成、Director 尚未运行”之间退出，恢复时只补投通知，不重新生成事件。若聊天先到，可在同一次 Director Cycle 中合并处理待通知事件，避免重复唤醒。

Director 不被要求每次都发消息。它可以保持沉默、自然分享、解释安排变化或继续协商。只有形成表达任务后才调用 PersonaActor。

## 10. 三天共享计划、边界唤醒与 LifeState

Director 继续直接读取共享三天计划。生活事件通知是新增变化输入，不替代已有计划上下文，也不把 Director 变成只能等待通知的被动组件。

计划边界唤醒和模拟机会是两类不同触发：

- 计划边界：让 Runtime 处理活动切换。
- 模拟机会：让 DayPlan 判断是否发生新的生活变化。

两者到期时可合并调度，不能因此重复生成事件。模拟事件改动计划后，重新计算受影响的未来边界与机会，取消失效任务，但不取消无关的用户延迟回复任务。

当前跨日调度还存在“没有下一块则固定次日 07:00”的兜底。正式接入本功能前需改为读取次日已提交计划的边界；计划未就绪时进入明确的准备策略，不擅自认为每天七点开始生活。

本设计不再扩大 LifeStateVersion 的职责。活动、位置、默认忙闲等可由 DayPlan 与虚拟钟计算，不应为了每一次边界重复保存相同事实。

真正不能从计划推导的临时影响，应来自已提交事件及明确有效范围，而不是模型每轮重写一份全量心理状态。现有 LifeState 可在迁移期继续作为兼容投影；其退役需要单独清理读写路径，本文不宣称它已经删除，也不要求本功能先重写全部 Runtime。

## 11. 经历与记忆：让一天积累起来

模拟事件必须进入分支可检索的经历来源，而不能仅留在当前计划名称或 Phoenix Trace 中。

DayPlan 查询近期经历，避免一天多次遇到相同插曲；Director 查询这些经历，能理解“刚才为什么改了安排”；之后的对话可以自然回忆“昨天临时改了材料”。

记忆策略：

- 原始事件是权威来源，模型摘要是派生内容，保留对应事件 ID。
- 明确区分 `simulation` 与原始聊天、用户输入等来源。
- 小事件可以低优先级、按需检索，不把所有小事永久提升为核心人物记忆。
- 一次模拟返工不能反向成为“目标人物长期被压迫”的画像结论。
- 不将分支模拟事件写回原始 LightRAG 图谱或已发布 PersonWorldProfile。
- 未来若增加分支专属图或向量索引，也必须与原世界资产隔离。

一天结束后的丰富程度来自真实保留的虚拟事件与它们造成的变化，不来自事后一次性补写当天未曾发生的故事。

## 12. Prompt、工具与代码组织

沿用当前组织原则：行为规则在独立 Prompt 文件，工具 schema 和工具内检索逻辑放在工具模块，不散落到配置文件，也不重复拼接工具 JSON。

建议布局如下，新增路径属于待实现项：

```text
runtime_v1/
  agents/
    day_planner.md                 # 共享规划原则、既有 plan_day 行为
    day_planner_life_events.md     # advance_life 模式行为片段
  life_events/
    contracts.py                  # 机会、事件提案与回执类型
    policy.py                     # 概率、冷却、影响预算和去重策略
    scheduling.py                 # 虚拟检查机会与过期处理
    service.py                    # 领域操作；提交仍由 Executor 统一协调
    context.py                    # 装配机会、版本化 Director 意见与近期经历
  tools/
    plan_constraints.py           # 复用
    routine_evidence.py           # 复用，按需查真实背景
    plan_memory.py                # 复用并明确区分分支模拟来源
    plan_work.py                  # 复用调查笔记和草稿
    recent_life_events.py         # 查询已提交事件与尚有效的影响
  collaboration/
    ...                           # 复用同级节点、消息、Router 与检查点
```

`day_planner_life_events.md` 是同一个 Agent 的任务模式片段，不注册成新的子 Agent。启动时按任务模式组装行为文本及对应输出类型。

Director 的独立行为 Prompt 同步增加“回复生活机会状态请求、判断候选行动、提交后再表达”规则；不把这些规则塞进配置文件。collaboration 的既有契约、Router 和检查点负责该任务阶段与恢复，不由 life_events.service 手写双方 while 循环。概率和枚举集中放策略/契约模块，工具 schema 仍由 LangChain 注册。

不为事件设置单独的“模拟事件模型”，不在工具内部再藏一个不可见的创作 Agent。模型推理和工具调用继续经过统一 AgentLoopController，真实调用与失败以 Phoenix 为准。

## 13. 观察与故障恢复

Phoenix 关联机会、DayPlan 调查、提交回执、消息投递与 Director 处理，并记录实际使用的画像、图和计划版本。随机策略版本与抽样决定作为可审计元数据记录，但恢复不能依赖读取 Phoenix 文本。

运行恢复依赖业务事件、机会状态、待投递通知和 LangGraph 检查点：

- 模型调用失败：同一机会退避重试，复用已有调查，不重抽。
- 协商中断：恢复待处理消息、候选修订和意见有效性；不重新从心理领域抽样开始。
- 用户输入更新：保留旧协商历史，作废其提交资格；优先处理聊天，再刷新当前意见。
- 预算耗尽：明确 blocked，不通过新 Job 绕过熔断。
- 场景变化或机会过期：取消候选，不追补已经失去意义的事件。
- 提交后通知失败：只重投通知。
- Director 表达失败：保留已提交事件和计划，不反向回滚生活。
- 重放同一通知：利用事件/消息幂等键避免重复生成用户可见回复。

## 14. 第一版实施顺序与冒烟验收

### 实施顺序

1. 补齐计划版本留存及跨日边界调度，保持现有聊天流程不变。
2. 增加机会状态、随机策略和分支虚拟时间扫描；先提供关闭开关。
3. 增加心理机会契约、Director 状态答复及 DayPlan 的 advance_life 模式，复用 LangGraph 完成提交前协商。
4. 接通候选版本、意见有效期、用户输入优先处理和中断恢复，再接事件与可选计划修改的原子提交。
5. 接通必要的当前块受限切分、待投递通知和 Director 的提交后处理。
6. 增加分支经历读取，再开启有限的真实模型体验。

### 冒烟验收

- 没有用户消息时，可根据虚拟时间产生一次生活变化。
- 未激活机会不调用模型；no_event 不修改计划、不生成已发生通知，已启动协商正常收尾。
- 每个正式模拟事件都有有效的 Director 意见；缺失、过期或不匹配候选版本不能提交。
- 一次状态答复足够时可以直接形成方案，涉及新取舍时必须继续商量；不固定强迫六轮调用。
- 候选在所有 Agent 可见时也不能进入正式计划、经历检索或用户消息。
- 协商期间用户发消息优先处理，旧意见失效；不会为了等生活事件而卡住聊天。
- 意见未知、对方调用失败、无进展重复协商均有明确退出/恢复路径，不重新抽样。
- 一个小事件不改日程也能保留为经历。
- 一个有影响事件只修改允许的当前/未来部分，保留历史及承诺。
- 自报零分钟但删除/移动受保护活动会被拒绝；预算扣减和事件提交具有同一幂等边界。
- 被拒绝候选不改变人物情绪投影，预计处理完毕不自动成为已完成事实。
- 提交失败时不发布“事件已发生”的通知。
- 事件提交后重启，只补投一次通知，不重复抽样、事件或消息。
- Director 可以收到事件后保持沉默，也可以正常经过 PersonaActor 分享。
- 暂停、恢复、跨午夜、队列延迟不会产生密集补演或错误的本地日期计数。
- 连续同类事件受到频率与重复约束；模拟经历不进入原始世界图谱。

验收不仅看能否生成合法 JSON，还要人工检查：内容是否贴合人物、变化是否自然、是否破坏承诺、是否重复、是否把一般倾向写成固定剧情。

## 15. 总结

**后端提供心理作用机会与现实边界，DayPlan 负责生活怎样展开，Director 参与判断人物此刻为什么会这样选择。先协商，后提交，再决定如何表达。**

第一版计划提供秩序，随机机会提供变化，事件账本保留经历，共享通知连接生活与对话。丰富的是这个虚拟分支实际经历过的一天，而不是把人物分析塞进日程名称，或让数字人不停主动讲故事。
