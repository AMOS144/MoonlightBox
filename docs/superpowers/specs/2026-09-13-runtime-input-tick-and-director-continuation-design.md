# Runtime 三秒节拍与 Director 连续输入设计

状态：已按确认方案实现并进行离线回归；实现落点、验收与部署边界见第 12 节。

## 1. 目标与不做什么

用户聊天、DayPlan 通信、到期唤醒和生活事件，都是人物此刻可以接收到的信息。
Director 应当综合理解这些输入，而不是每收到一条消息就被重启一次。

约定：

- 空闲时每 3 秒检查是否需要启动 Director。
- 每次模型调用前，一次接收截至本次读取边界的全部未读输入，不逐个时间片处理。
- 当前模型请求执行期间不插入消息、不因普通新输入取消请求。
- 还需要继续思考，就接入新增输入；已经提交最终决定，就执行决定。
- 新输入的轻重缓急交给 Director，不由后端预先替人物判断。
- 每条分支只有一个 Director 执行者，不同分支可以并行。

不新增 Tick、Mailbox、通知中心或新的 A2A 服务实体；复用事件队列、Job、共享协作记录、
AgentLoopController 和 LangGraph 检查点。必要的顺序字段属于已有输入记录，不另建系统。

3 秒不是回复间隔、最大思考时间、输入防抖时长、抢占时间，也不是对话回合边界。
用户不断发消息不会不断推迟节拍；不要求用户连续安静 3 秒才开始处理。

本版表达能力由 Director 使用说话 skill 完成，不设置独立表达 Agent 或提交后的表达阶段。
需要说话时，通过 read_skill 加载 speaking，读取占位符注入的 expression_profile；
按需通过 execute_tool 调用 get_style_examples。技能说明与检索结果进入同一个 Director
执行上下文，使用同一套输入续接、容量管理和检查点机制，不启动第二个模型循环。

## 2. 四个概念必须分开

| 概念 | 含义 | 不代表什么 |
| --- | --- | --- |
| 已入队 | 输入已可靠保存 | Agent 已看到 |
| 本次执行已接收 | 输入已进入可恢复的模型上下文 | 已回复、已解决 |
| 本次输入已消费 | 对这批输入的决定已成功提交 | 必须向用户发过一句话 |
| 待回复或待办 | 人物决定稍后处理的事项 | 每个节拍都要再次调用模型 |

Director 决定 wait，也可以完成一次输入处理，但用户消息仍可处于 awaiting_response。
后续靠新输入或到期唤醒继续，而不是不断扫描同一条未回复消息来重复启动 Director。

所谓已读位置，是当前执行已接收的输入集合/游标，不是旧 runtime_input_revision。
不能用“最大的消息时间”代表已读位置：迟到消息、回填时间和未来发生时间会造成遗漏。
第一版可在现有检查点中保存 input_event_ids 与已接收的输入正文，不要求新建游标表。

## 3. 输入存储与顺序

### 3.1 用户消息

用户每发一条消息，立即保存 BranchMessage，并在同一事务中保存对应 RuntimeEvent。
消息保留原文、角色、虚拟发生时间与客户端幂等 ID。消息接口不直接投递一个 Director Job。
历史摘要/索引维护仍是独立工作，不冒充一次聊天触发。

### 3.2 DayPlan 与生活事件

继续使用共享协作消息与已有 RuntimeEvent：

- 协商请求保留问题、提案、发送者、接收者及已有任务关联标识。
- 已提交计划的通知关联实际计划版本或 Executor 回执。
- 已发生生活事件使用现有事件 outbox，不能把尚未发生的候选写成事实。
- 同一逻辑通知只有一个幂等标识，不能因恢复或重复投递变成两个独立输入。

共享协作记录是交流内容，RuntimeEvent 是唤起/送达入口。两者引用同一个逻辑通信，
不是重复向模型展示两份文本，也不是两套需要分别批准的事务。

### 3.3 发生时间与接入顺序

发生时间告诉 Director 事情何时发生，接入顺序告诉系统何时收到。二者不能混用。
输入按接入顺序呈现，同时保留原始发生时间；不会按情绪强度或预设重要性重新排序。

RuntimeEvent 已补独立接入时间 received_at，使用服务器 UTC 时间；
同一接入时间用 ID 稳定排序，不宣称能确定物理上同时到达的严格先后。
已读判断使用具体 ID 集合，不依赖 received_at 单独去重。
未来才到期的唤醒仍按虚拟时钟判断是否可交付，不能提前消费。

## 4. 常驻调度器：只投递，不推理

复用 worker_main 中已有的独立扫描线程，使用可停止的等待，每 3 秒检查一次活跃分支。
不为每条分支创建一个常驻线程，不在扫描线程里执行任何 Agent。

每次检查：

1. 将已经到期的现有唤醒纳入可处理输入范围；暂停的虚拟钟不触发新的到期唤醒。
2. 检查分支是否已经准备就绪、是否有可交付的新输入。
3. 检查是否已有相关 Job 待领取、运行或正在退出；这些状态都不能再次投递。
4. 空闲且有输入时，幂等投递一个 Runtime Job。
5. 没有输入时，不调用 Director，不生成空回合。

运行时间很长也不能停止节拍扫描。扫描耗时超过一拍时跳过过期拍，不连续补发多个空任务。
进程重启直接扫描现有队列，不补造停机期间的时间片。

多 Worker/多个扫描器必须通过现有数据库事务、Job 幂等键与分支执行互斥共同避免重复。
不能仅依靠 Python 中先查一次有没有运行任务；并发扫描可能同时读到空闲。
也不能因旧 Job 已经 succeeded 就把这个分支永远视为忙碌。

DayPlan 规划维护、历史摘要和 Director 输入处理需要区别用途：后台摘要不能挡住聊天；
已在执行的 Director 也不能被一个新到达的普通通知抢占。

## 5. Director 从启动到继续思考

### 5.1 初次启动

领取执行权后，读取截至当前边界的全部可交付输入，并装配正常人物背景、当前状态、
共享计划、连续聊天及协作信息。取消旧的 250ms 分组和一次最多 16 个事件的截断行为。

这里“全部”不意味着无视模型窗口：输入不能静默丢弃，超大批次由统一容量估算和可恢复
上下文维护处理。若无法装入，必须明确暴露容量问题，不能把没交给模型的消息标记已消费。

### 5.2 模型请求期间

收到的新输入只入队。当前请求继续完成，不因消息数量或节拍推进而取消，不另开 Director。

### 5.3 下一次模型请求之前

如果当前产物是调查工具调用、可修复的工具错误，或尚未完成提交的普通文本：

1. 读取全部新增输入，一次加入，不管它们跨了几个时间片。
2. 保留已有模型消息、完整工具回执和工作状态，不重新初始化 Agent。
3. 更新模型可见的输入边界，以及提交工具使用的同一份输入范围。
4. 用统一容量机制检查/压缩，再发出下一次模型请求。

新增输入中用户原文不能只有引用 ID；DayPlan 通知不能只更新计划表却不把消息告诉 Director。
不得在刷新输入时顺手换掉整个背景、丢掉协作历史或重置调查草稿。

接入位置统一由 AgentLoopController 提供模型调用前的扩展点；领域适配器负责查询输入和
生成上下文。不是给 Director 手写第二套 while 循环。传输失败重试也不能偷偷改变同一次
请求的输入；新的输入接收发生在明确的下一次思考边界。

### 5.4 时间示例

第 3 秒开始思考；第 4 秒收到用户 A；第 6 秒收到 DayPlan B；第 7 秒收到用户 C。
第 8 秒模型返回查询工具调用，工具完成后，下一次思考一起看到 A、B、C。
如果第 8 秒返回的是已接受的最终决定，则执行它，A、B、C 留给下一轮。

第 2.9 秒和第 3.1 秒发出的两句话不因此成为两个必须分别回复的话题。
时间片不负责判断用户是否说完，由 Director 根据实际内容决定回应或等待。

## 6. 完成边界：已决定就执行

Director 在当前执行中完成判断、加载说话 skill、按需检索表达示例和形成最终回复。
最终提交工具接受包含实际回复内容的决定，才表示此次思考结束。之后直接由 Executor
执行，不再转交另一个表达过程；不得仅因队列又有新输入，把决定退回 Director 重想。

“打算说话”或“已经加载 speaking”不是完成边界。skill 读取、风格检索和措辞形成仍属于
Director 的思考过程：若还要下一次模型调用，就先接收全部新增输入。
最终决定已接受后，新输入留给下一轮；Executor 不再调用模型改写回复。

提交失败只针对真实条件，例如：

- 已经明确取消，或者 Worker 丢失租约。
- 分支背景被显式切换、运行控制条件发生改变。
- 要修改的计划或人物状态版本发生真实写冲突。
- 相同业务副作用已提交，需要返回幂等回执而不是再发送一次。

“发现未读新消息”本身不是提交失败条件。无需要求队列清空才准发送。

Executor 在一个短事务中完成：业务写入、幂等回执，以及本轮实际接收的事件消费确认。
不得在 Agent 刚读到事件时就永久标记 completed；不得将当前队列全部清空。
已有用户待回复状态按 Director 的 input_resolutions 更新，不由事件消费批量代替。

## 7. DayPlan 与 Director 同时工作

DayPlan 可以独立调查和准备提案。需要商量时保存现有工作状态并投递协作输入，
让出执行，不持有分支写锁等待 Director 回复。

Director 忙碌时：通知积累；若它继续思考（包括使用说话 skill），接收通知；若最终决定
已被提交工具接受，则之后处理。
Director 自己决定是否先处理生活事务、继续聊天或说明需要离开，不由调度器判断重要性。

Director 的意见通过共享协作记录交回 DayPlan；DayPlan 继续原工作，而不是重新抽样生活事件。
计划更新仍由 Executor 校验版本后提交。通信、提案和已生效安排必须保持区别。

实施约束：不能只改 3 秒等待而继续在整轮分支写锁内同步交接。本实现已将 Director、
规划任务与生活机会的执行权分离：等待对方意见的路径持久化后结束当前执行占用，
独立调查使用各自 Session，正式副作用仍通过事务与版本检查保护。
继续复用现有任务/协作记录，不另建 Agent 消息总线。

## 8. 等待与持续输入

Director 决定 wait 后，本次已接收事件可以被消费，待回复事项仍保留。
没有新输入也没有到期唤醒时，下一个节拍不再运行模型。

如果用户一直发消息：Agent 不被不断取消，也不强制等到消息停止；它可以根据本次读到的
内容提交。最终决定边界以后到达的输入下一轮处理。允许正常聊天交错，不追求每句话覆盖
发送瞬间的全部信息。

没有输入就不运行模型，不等于数字人永不主动：DayPlan 的生活事件和既有到期唤醒会提供
新的触发。此设计不新增每 3 秒随机产生一次“内心活动”的模型调用。

## 9. 检查点、恢复与取消

检查点至少保留：已接收输入 ID、对应可恢复原文、当前消息历史、工具结果和领域工作状态。
消费确认仍留到业务事务，不以 Phoenix trace 作为恢复来源。

| 中断位置 | 恢复要求 |
| --- | --- |
| 输入入库后、Job 投递前 | 下一拍从队列发现输入 |
| 已接收、模型请求前 | 从检查点继续；重复接收按 ID 去重，不丢正文 |
| 模型/工具执行中 | 沿用统一恢复与预算策略，补入未读输入，不从头调查 |
| 决定已接受、尚未提交 | 恢复原决定及其输入集合，不因后来消息重想 |
| 业务提交成功、Job 尚未成功 | 查询幂等回执，不能再次发送；后来输入保持未消费 |

当前已接受决定需要绑定它自己实际读取的输入快照。恢复时重新查询整个队列并把新内容
当作旧决定的依据，是错误做法。输入刷新回调、输入状态格式要进入检查点契约版本管理。

普通新消息不消耗失败重试额度，也不改变分支执行代际。
明确取消仍走 Job → Controller → 可取消 I/O；不能中断的操作等待退出，且禁止迟到提交。

## 10. 代码职责与实施顺序

1. service.submit_user_message：只写消息与事件，移除逐消息 Director 投递。
2. worker_main + runtime_v1/jobs：统一三秒空闲扫描、去重投递、到期唤醒接入。
3. AgentLoopController：在每次模型思考前调用输入续接点，包含普通文本未提交的回环；
   传输重试、容量失败重试与提交终止路径不得漏接或误接。
4. Director 接入层：读取新增输入、维护同一输入范围的上下文与提交工具；不重复装配整份
   人物背景，不把事件消费职责放进 Prompt。
5. 协作节点：DayPlan 消息和用户消息进入同一读取边界，等待通信不长期占用分支执行权。
6. 说话 skill/Executor：Director 在提交前完成表达，Executor 使用已决定的回复与输入快照，
   在短事务中确认实际消费集合及业务结果，不新增提交后的模型调用。
7. 检查点：恢复已接收集合与上下文；已完成决定不刷新成另一个任务。

## 11. 最小验收场景

- 多条用户消息跨两拍，到下一次思考时一起可见，未按拍分成两次强制回复。
- 用户消息、DayPlan 请求、生活通知同时到达，保留来源/原文/时间。
- Director 运行超过 3 秒，不产生第二个执行；多个扫描器也不重复投递。
- 模型返回调查工具后接收新增输入，工具结果继续保留。
- skill 读取或风格检索期间新增消息，在下一次 Director 思考前合并；不另开表达执行。
- 模型最终决定被接受后新增消息，不重跑；Executor 按已提交内容发送。
- wait 之后无新事件，不每 3 秒重复模型调用；到期唤醒能继续。
- 超过 16 条事件不遗漏；迟到时间戳不被游标跳过；未来唤醒不提前消费。
- 恢复前后输入不丢、不重复消费；提交成功后进程退出不重复发消息。
- 状态版本冲突、明确取消和租约失效仍禁止不合法提交。
- 压缩保留未处理输入与游标；未交付给模型的正文不冒充已读。

### 12.1 实际执行边界

- Director 使用 speaking skill，提交带实际 `reply.messages` 的决定，之后直接进入 Executor。
  已移除协作图的独立表达节点，不再在生活任务里另启动一个 Director。
- Director 与 Planner 使用不同执行锁。等待意见时保存 Job/规划工作并投递 RuntimeEvent，
  当前执行退出；不是在分支写锁里等待对方。共享发言随交付合入 LangGraph 消息列表。
- 规划等待回答时标记 `blocked / awaiting_peer_reply`，不被定时维护误判为进程失败并重跑。
  用户补充信息后仍能回答先前的问题；问题被消费不等于协商已经结束。
- 生活问题的 `life_responses` 与 Director 行为同事务交付，DayPlan 继续原候选。
  已过期机会不因迟到答复重新激活。
- Executor 的提交回执和事件消费同事务；Job 完成状态随后更新。恢复旧 Job 先查业务回执，
  已提交则直接幂等返回，不误处理后来输入。
- 输入新增不会推进 `runtime_input_revision`。显式改变时钟控制、背景等运行条件仍保留代际保护。
- 队列时间点持久化及比较统一 UTC，模型看到分支本地日历时间；发生时间在输入中保留偏移。
  历史 `received_at` 只能用已有发生时间回填，不伪称已恢复原始接入顺序。

### 12.2 验收范围

`backend/tests/runtime_v1/test_input_tick.py` 覆盖：

- 25 条输入一次接收，接口不逐消息投递 Director，空闲不触发模型。
- skill 工具返回后，一次并入用户消息、迟到的 DayPlan 通知和到期唤醒，保留工具回执。
- 两个并发扫描器只投递一个 Director；新输入不能绕过失败任务的恢复策略。
- 决定接受后、提交前中断，重建服务后仍提交原决定及原输入集合；之后重放不重复发送。
- wait 保留待回复语义，到期后能够继续回应。
- 东八区的未来事件和唤醒不会提前交付。

`test_peer_collaboration.py` 覆盖独立计划任务的追问、回答、继续规划、提交和回执通知；
`test_life_events.py` 覆盖生活意见入队、候选继续、一次提交、正常通知消费与过期关闭。

### 12.3 部署边界

本次没有修改体验分支数据，没有重跑付费模型，也没有自动升级共享数据库或重启现有进程。
上线此代码前，停止旧 Worker，使用项目现有迁移入口将共享数据库升级到
`0059_runtime_event_received_at`，再重启本地开发进程。

实际并行需要可用 Worker 执行槽；项目启动脚本已有 realtime/cognition/background 进程。
三秒扫描是独立线程，单个 Worker 自身仍串行领取工作：只启动一个 Worker 时，排队的任务
仍须等待该 Worker 的当前工作退出，不能把调度器独立宣称为无限并发。
