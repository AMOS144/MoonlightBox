# 统一用户主线与前端交互重构设计

日期：2026-09-14  
状态：前端主线与只读流程投影已实施；历史起点背景编译及新建分支后端链路未完成。不能将本文整体标记为已交付。  
代码核查基线：`runtime-prune` worktree 当前前端及新节点调查入口。

实施记录：[当前完成范围、验证与剩余工作](../implementations/2026-09-14-unified-user-journey-implementation.md)。下文保留完整目标，不把尚未实现的历史分支契约改写成已完成能力。

## 1. 目标：让用户完成一件连续的事

统一主线：

**导入记录 → 确认人物与资料 → 审阅人物背景 → 调查并选择起点 → 准备该起点的分支 → 开始聊天。**

用户是在逐步建立、理解并进入一段人生，不是在依次操作导入器、图谱、模型注册表、事件分析器和任务管理器。页面必须围绕用户的目标组织，而不是照搬后端模块名称。

“统一”包括三个层次，缺少任何一个都不算完成：

1. **逻辑统一**：所有入口对“已经完成什么、还缺什么、下一步是什么”给出相同答案。
2. **交互连续**：用户的对象、选择、草稿、待回答问题和阅读位置不会因换页、后台更新或刷新而消失。
3. **UI 统一**：页面共享同一套组件、视觉变量、状态语义和操作规则，而不只是都使用深色背景。

不把所有功能塞进一个大页面，不新建一个包办全部工作的前端 Agent，也不为了显示流程再建一套可写的业务状态库。

## 3. 主线的作用域：不是所有用户都从第一步重新开始

### 3.1 项目准备与分支准备分开

- 第 1—3 步主要形成项目级资料：导入记录、参与者绑定、已发布人物背景。
- 第 4 步形成可重复选择的经历与起点；可以继续调查其他候选。
- 第 5—6 步属于具体分支。一个项目可以同时有准备中的分支与已经可以聊天的分支。

不能用一个全局 `current_step=5` 覆盖所有分支，也不能因为新导入正在处理，就把已有聊天分支判定为不可用。

### 3.2 首次用户与回来继续的用户

首次进入项目时推荐主线下一步；返回时优先恢复用户上次主动进行的工作（包括审核、回答问题或聊天），已有聊天作为稳定快捷入口。后台任务完成不能覆盖用户最后的主动位置。待审核背景、待回答节点问题作为明确待办保留，不强迫用户重走 onboarding。

允许浏览已完成步骤。允许在资料编译期间阅读原文、补充信息；检索未就绪时如实标注。主线是推荐工作顺序，不是把所有可并行活动锁死的六道门。

### 3.3 一切完成状态带有对象和版本

“人物背景已确认”应指向具体发布版本；“起点已确认”应指向具体候选、边界及批准；“可以聊天”应指向具体分支的准备结果。

上游更新后，展示“有新资料可用于重新整理”，不能静默替换已批准的边界或已运行分支。是否重新编译、采用新结果，由相应业务流程决定。

追加导入形成新一轮资料整理。新草稿与旧发布版并存，用户批准新草稿后，新版本供后续创建采用；已有分支继续使用自身绑定的版本，不自动回退到准备阶段。恢复位置只记录路由及所选对象，不是业务完成状态。

## 4. 六个阶段的页面与操作设计

### 4.1 导入记录

**用户要解决的问题：我的记录能否正确进入项目？**

前两步使用同一导入会话：选择文件并上传解析 → 预览并确认人物 → 正式提交导入。第一步完成只称“记录已解析”，不称“已保存导入”；只有确认事务成功才称“导入完成”。本页不承担等待全部 Agent 工作完成。

保留：目录/文件选择、媒体附件、格式预览、可解析条数、异常记录和导入幂等能力。

调整：

- 首屏主按钮为“选择聊天记录”；预览后进入“确认人物与资料”，最终按钮为“确认人物并导入”。
- 原始记录与后续生成资料明确区分；解析后展示待确认范围，正式提交后展示已保存数量。
- 解析完成提示“记录已解析，请确认双方身份”；正式提交后交给资料整理与人物背景审核。
- 原文件尚未上传的草稿刷新后若无法恢复，明确要求重新选择文件；不能宣称浏览器保留了文件授权。
- 重复提交返回同一导入结果，不重建项目或启动重复任务。

删除本页“导入与所有分析一起完成”的 Stepper，以及把建图、画像、节点 Job 成功统一解释成“生成若干关键节点”的逻辑。

### 4.2 确认人物与资料

**用户要解决的问题：谁是我、谁是目标人物，记录是否理解对了？**

将参与者绑定、导入范围检查、人物别名审核组织在同一阶段。UI 可有局部步骤，但不能让用户在“聊天数据”和“世界”之间自己寻找依赖。

- 第一个操作确认双方身份、名称及可用头像。首次绑定仍可在后端导入确认事务中执行，不要求为拆页面重写导入协议。
- 随后展示记录时间范围、资料缺口和会影响后续理解的问题。详细解析报告默认折叠。
- 需要建立索引时，显示“正在整理可查询资料”，说明可以离开，完成后会出现待办。
- 别名合并候选展示“这些名字是否是同一个人”，而不是只展示图节点编号和 merge 参数。
- 没有别名候选或全部完成审核时，明确继续；不能停在一个没有可点内容的审核页。
- 修改参与者绑定后，由后端判断相关派生资料是否需要重建，前端展示影响，不直接沿用旧的“已完成”。

退出条件是必要参与者绑定与相关审核已满足，并有明确的资料准备状态。资料确实未就绪时显示缺项；不是要求每一个可选媒体标注都做完。

主按钮依状态为“确认人物”“处理待确认项”或“查看人物背景”；完成后交接给第 3 步。

### 4.3 审阅人物背景

**用户要解决的问题：系统理解的这个人是否像真实的 TA？**

保留现有七个人物栏目、来源展开、栏目调查状态、版本比较、选择字段后对话纠正，以及 Profile/Graph 多步批准机制。

调整布局和信息层次：

- 主内容是人物理解，默认不展开 Phoenix 调用次数、内部错误码、工具日志和模型配置。
- 顶部明确区分“当前已发布背景”和“正在审核的新草稿”，不让新构建遮掉用户正在阅读的已发布内容。
- 选中一条或一组描述后，在右侧“与助手一起修改”面板讨论，始终显示此次修改对象。
- 当前理解、待确认修改和已发布结果分开呈现。不能把“Agent 已生成草稿”标成“已经修改成功”。
- 纠正流程仍保留必要批准：理解确认、画像变更、图谱变更、最终执行。通过统一侧栏表现，不减少实际授权边界。
- 未知、未覆盖、调查失败用不同状态展示；不能为了进入下一步强迫 Agent 填满所有字段。

发布后展示明确交接：“人物背景已确认，下一步寻找想重新开始的时刻”，主按钮“调查并选择起点”。不要强制跳走正在阅读结果的用户。

本页默认是基于完整导入记录形成的人物背景，不把它称为任意历史节点的背景。第 5 步生成的历史背景须另行标明所属起点。

### 4.4 调查并选择起点

**用户要解决的问题：从哪段经历、哪个具体时刻开始另一条时间线？**

保留新节点 Agent 的顺序阅读、RAG/LightRAG 调查、增量候选、用户补充、提问与恢复、原文圈选和边界预览。

- 左侧是逐步出现的经历候选；中间是当前经历和起点选择；右侧沿用公共 Agent 对话面板。
- 候选出现不抢焦点，不改变用户选中的卡片；更新同一候选时标明有新内容。
- 用户不需要理解工具调用协议。进展写“正在查看出行前后的对话”“更新了这段经历的时间范围”等公开工作摘要。
- “等待你回答”必须成为项目级待办，不能因为这个 Job 成功结束就从顶部消失。
- 允许回答、不确定、跳过、纠正问题前提。问题、输入草稿和提交幂等键在刷新后保持。
- 起点确认前显示真实消息边界；区分发生时间、后来提及的时间，以及选中的分支起点。
- 选中一个起点后，继续调查其他候选是独立选择，不能默认悄悄在后台无限继续。

主按钮依状态为“开始调查”“发送回答并继续”“预览这个起点”“确认起点”。确认之后展示结果卡及下一步“准备这条分支”。

完整创建契约接通后，边界预览内收集可选分支名称，最终主按钮合并为“确认起点并准备分支”，不再跳转另一页重复确认。批准成功而创建失败时保留批准回执，仅恢复创建。能力未接通时仍只允许明确的“确认起点”，展示持久阻塞原因，不把按钮提前命名为能创建分支。

**当前能力缺口**：新起点结果尚未完整接入历史背景编译和新的分支创建契约。缺口补齐前，下一步应明确显示“历史分支准备尚未接通”，提供已确认结果查看，不出现无效按钮、假进度或旧 EventNode 创建表单。

### 4.5 准备该起点的分支

**用户要解决的问题：这个起点对应的人物背景和生活，是否已准备好？**

创建页从已批准的起点接收选择结果，不再让用户重新选择一遍旧事件、复制时间或选择 LoRA 版本。普通用户只需确认起点说明，并可填写分支名称。

必要准备项由后端提供真实状态，例如：

1. 验证所批准的精确边界及资料版本。
2. 编译该起点可见的人物背景和历史资料。
3. 准备该分支所需的 DayPlan。
4. 完成 Director 的独立初始化，得到起点时的心理状态和未结束交流。
5. 检查聊天所需的必要资产，给出可进入状态。

上述条目是目标契约，不是声称当前全部已经实现。只有真实状态变化才能显示完成，不能用定时器推动进度。

交互要求：

- 持续显示分支名称、目标人物、起点时间，用户知道正在准备的是哪一条分支。
- 默认展示阶段与缺项；没有可靠总进度就不显示百分比，也不推测剩余时间。
- 允许离开，返回同一分支时恢复准备界面；失败显示可以恢复的具体阶段，不笼统要求从头再来。
- 上游批准失效、功能尚未实现与暂时网络失败分别展示，不对前两者无限重试。
- 准备完成后主按钮“进入聊天”。后台完成不会强制把用户从人物审核、其他分支或其他页面带走。

项目完整资料与历史分支资料须有不同的可见范围标识。沿用“最新时刻体验”时明确标注该模式，不用它冒充历史隔离。

准备页提供“这个起点的人物背景”预览，一直标明分支和边界。不要求用户把七个栏目再审一遍；只有必须由用户澄清的问题才暂停。分支背景纠正默认仅影响当前分支；修改项目资料或图谱必须另行进入项目纠正流程并展示实际影响范围，不能复用项目级批准来授权分支级修改，反之亦然。

### 4.6 开始聊天

**用户要解决的问题：像平常聊天一样，与这个人继续相处。**

保留现有微信式聊天布局、头像、媒体、表情包、消息时间分隔、历史消息加载、分支边界、虚拟时间和发送状态。

- 不重做成 Runtime 调试页，不把 Director、DayPlan、工具、计划 JSON 和心理状态列表塞进普通聊天主界面。
- 进入聊天后弱化首次准备的六步导航，以人物、分支名称和当前虚拟时间为主。
- 历史资料、当前分支信息和诊断入口通过辅助面板按需查看。
- 区分消息“已发送到系统”、人物暂未回复、请求失败和分支尚不可运行。发送成功不等于对方已经作出回复。
- 不根据网络请求耗时假装人物在输入；输入中等状态必须有可信信号。
- 日程等资产在运行中发生暂时问题时，使用后端给出的运行策略提示；不要让前端自行推断应该关闭聊天或强制重建分支。
- 返回项目后，再次进入应恢复该分支的阅读位置；在查看旧消息时，新消息不强制滚到底部，显示“有新消息”入口。

## 5. 项目导航与页面之间的交接

### 5.1 一级导航

建议收敛为四个面向用户的区域：

| 区域 | 职责 |
| --- | --- |
| 概览 | 恢复当前工作、继续上次聊天、查看待办 |
| 人物资料 | 导入资料、人物确认、已发布背景及纠正入口 |
| 选择起点 | 节点调查、已确认起点、继续补充经历 |
| 我的分支 | 已有分支、准备状态与聊天 |

训练、模型配置、评估、Phoenix 和原始技术报告进入“高级设置 / 诊断”，不占据首次体验的主流程位置。活动地图保留为人物资料的辅助视图，不单独抢主线。

### 5.2 主线导航与局部导航不重复

左侧四个区域只回答“去哪里”，阶段提示只回答“正在做什么、接下来做什么”，不再生成另一排可点击的六步菜单。人物栏目只出现在人物工作台，候选列表只出现在起点工作台。聊天隐藏阶段提示。

阶段提示的状态来自统一流程视图，不由页面自己计算 `active=2`。局部导入可显示两步进度，但不把所有后台任务串成六步 Stepper。紧凑屏幕保留当前阶段、状态与一个下一步操作。

### 5.3 首页不再猜测下一步

首页顺序为：当前可继续的聊天或工作、需要用户操作的待办、已有分支。原始记录数量和技术资产数量只作次要信息。

若同时存在多个待办，列清楚对象，由用户选择；不能用“最后更新的一个 Job”覆盖其他任务。对当前分支有阻塞的事项就近置顶，其他项目准备工作不抢占聊天入口。

每次阶段完成使用同一种交接卡：**已完成的结果 + 下一步的目的 + 一个明确主操作**。不自动越过用户审核，也不在后台状态刷新时主动导航。

## 6. 统一状态来源，不另建一套业务状态机

建议增加一个只读的项目/分支 Journey 投影接口，名称可为 `GET /api/projects/{id}/journey`，按需要传当前分支或起点引用。它在实施前还不是现有接口。

投影读取现有导入、参与者、画像发布、调查问答、批准边界、分支准备和 Job 状态。后端是事实来源；前端只做呈现与路由映射。

至少提供：

- 当前作用域：项目、所选起点、可选的分支。
- 各阶段的业务状态、关联资产版本、必要缺项。
- 用户待办：审核什么、回答哪个问题、发生在哪个工作台。
- 可用操作及不可用原因，例如继续审核、恢复调查、准备分支、进入聊天。
- 关联对象的版本，用于拒绝旧批准和旧操作。

不允许前端通过事件数量、模型数量或 Job 成功来推断 `ready`。展示用状态统一为：尚未开始、系统处理中、需要你操作、已确认、已完成、暂时受阻、已暂停。分支资产齐备才叫“可以进入聊天”；“草稿生成”是待审核而不是已确认。可继续是操作可用性，不是替代业务状态。必要时附上局部阶段，不把所有状态压成一个百分比。

投影可以是多个来源的只读聚合，无需新增 Journey 持久化实体。批准和执行仍由原业务接口在事务中检查；快照即使稍有延迟，也不能使过期操作真正提交。

主按钮由有类型的操作映射生成。前端不执行服务返回的任意 URL 或脚本，也不因为返回了一个字符串就假定操作已经被授权。

## 7. 如何使用现有组件库实现 UI 统一

### 7.1 技术选择与现状

继续使用项目已有的 **Mantine、Tabler Icons、React Query 和 React Router**，不再引入另一套基础 UI 库。当前已有 `App.tsx` 的 MantineProvider 和 `app/theme.ts`，但主题主要设置了主色、字体、圆角；还不足以约束整套产品。

统一不是“每页都 import Mantine 就行”。必须同时收敛主题变量、组件默认规则、公共交互组件和页面布局。

以下组件名称是拟新增的项目组件，不宣称是 Mantine 原生组件。优先组合现有基础组件，不另造按钮、输入框和弹窗系统。

### 7.2 三层组件职责

| 层级 | 使用内容 | 约束 |
| --- | --- | --- |
| 基础层 | Mantine Button、TextInput、Textarea、Select、Checkbox、Alert、Badge、Paper、Stack、Group、Modal、Drawer 等 | 直接使用库组件并继承主题；不要为每一个基础组件建立无意义的一对一包装 |
| 项目公共层 | JourneyHeader、JourneyNavigation、StageStatus、StageHandoff、AsyncState、AgentConversationPanel、SourceConversation、ReviewActions | 封装多页重复的产品语义、交互与视觉规则，不负责发起具体业务审批 |
| 领域层 | 人物栏目编辑、节点边界选择、分支准备清单、聊天气泡 | 使用公共层和主题变量；保留各领域特有交互，不合成一个参数无限增长的大组件 |

例如，普通按钮直接用 Mantine Button；涉及“批准哪些变更、批准是否失效”的操作栏使用公共 ReviewActions，但具体批准接口与事务约束仍在领域代码。

### 7.3 一处维护主题与视觉变量

继续以 `app/theme.ts` 为主题入口，补充统一的组件默认值和语义变量。CSS 需要使用与主题同源的变量，不在各页面重复定义一套颜色。

建议初始规范如下；这是目标规范，不是对当前全部页面的描述：

| 项目 | 统一规则 |
| --- | --- |
| 品牌与背景 | 保留现有深色与 moon 主色方向；主操作用品牌色，不把品牌金色当警告色 |
| 状态颜色 | 成功、处理中、待用户操作、警告、错误有固定映射；颜色必须配合文字/图标，不单独承担含义 |
| 层次 | 背景、工作面板、选中项、边框、正文、次要文字、禁用内容各有语义变量 |
| 字体 | 沿用同一中文友好的字体栈；正文、页面标题、区域标题、辅助说明通过统一 Typography 规则指定 |
| 字号 | 正文默认 16px、表单/紧凑列表 14px、辅助说明 12px；主标题和区域标题设固定等级，不能每页任意放大 |
| 间距 | 用同一组 4/8/12/16/24/32px 间距变量；控件间距、面板内边距、区域间距分别固定对应等级 |
| 圆角 | 基础控件、卡片、浮层继承主题档位；不要每页另写一组 radius |
| 密度 | 默认舒适密度；仅原文列表、诊断等明确区域使用紧凑密度，不把所有页面压成后台表格 |
| 图标 | 统一 Tabler 来源，固定导航/操作/状态图标尺寸档位；常见操作有一致图标和文案 |
| 动效 | 只用于明确的展开、进入、状态反馈；数据轮询不触发整页过渡、闪烁或滚动动画 |

先把映射写进主题和组件示例，再迁移页面。不要先在十个页面复制目标数值，最后才补主题。

### 7.4 统一页面骨架

主要保留两种布局，而不是强求每页一模一样：

- **准备工作台**：统一项目/人物标题、阶段说明、主操作区域；内容可为单列审核或列表—详情—侧栏布局。
- **聊天界面**：保持熟悉的聊天结构，主区域让给消息和输入；沿用同一基础控件、字体和状态语言，不强行套用审核页面的卡片密度。

使用 Mantine 的布局基础组件处理间距和响应式，工作台分栏、消息气泡等特有布局使用局部 CSS Modules 或明确作用域的样式。工作台三栏是内容关系，不是要求小屏也硬塞三栏。

宽屏：候选/栏目列表、详情和对话面板可并排。中屏：对话面板可收起。窄屏：使用 Drawer 或独立详情区域切换；保留选中对象与输入，不靠横向滚动勉强展示。

断点来自统一主题，不在各页面分别创造不同的“手机版”宽度。表单控件、点击区域、文字换行和媒体尺寸须在窄屏实际检查。

### 7.5 统一 Agent 对话面板

PersonWorld 纠正与节点调查共享以下外壳能力：

- 顶部显示当前讨论对象、任务状态和关闭/收起入口。
- 区分用户消息、助手的公开说明、简短工作活动、待确认修改。
- 当前问题有稳定位置；回答、不确定、跳过或纠正前提按领域能力显式提供。
- 输入框、提交中、防重复提交、草稿恢复、失败重试有统一行为。
- 关闭面板不等于取消后台任务；取消必须是明确操作，并显示是否仍在退出。
- 使用独立会话标识，不把不同 Agent、不同候选或不同纠正任务的内容混在一起。
- 面板固定显示任务对象、谁需要操作和修改影响范围；项目待办链接恢复具体会话/问题。不同任务的输入独立保存，收起面板不丢弃草稿，也不取消任务。
- 不展示或编造隐藏思维链。完整技术调用按需进入 Phoenix。

面板接收消息、状态和操作回调，不直接知道图谱修改权限，也不自行推进批准流程。复杂 Graph/Profile Diff 等由领域组件插入，不用通用聊天消息气泡承载所有审批。

### 7.6 统一异步、错误和表单交互

- 初次无数据使用 Skeleton 或明确加载状态；已有数据刷新保留原内容，局部提示更新中。
- 空白状态解释“还没有什么”和“现在能做什么”；不得把请求失败当作零条数据。
- 字段校验错误放在字段附近。影响整个操作的失败使用面板内 Alert，保留输入，提供明确恢复操作。
- Toast 仅用于短暂且不阻塞的反馈，如“已保存”；问题、待审核、准备失败不能只弹一下就消失。
- 执行中按钮有明确状态；防重复提交不能仅依赖按钮禁用，还要配合后端幂等。
- 破坏性或批准性操作明确展示对象与影响。不能只写通用“确定”。
- 不用颜色掩盖差异：“未知”“没有匹配”“读取失败”“未执行”分别呈现。

### 7.7 CSS 与旧控件清理规则

`index.css` 收敛为必要的全局基础样式和应用骨架；页面专属选择器迁到所属模块。重点核查全局 `h1`、`button`、链接样式是否覆盖 Mantine 组件。

将散落的 `.primary-button`、手写按钮、原生 select 的独立视觉样式迁入统一基础组件。原生语义元素仍可用于内容结构，并非禁止 HTML；不允许它们绕过统一的交互和视觉规范。

聊天气泡、时间分隔线、媒体展示等已经形成用户熟悉体验的样式保留并局部化，不以“统一 UI”为名再改成一张新 Runtime 页面。

只有确认选择器、组件或资源无引用后才删除；历史页面复用的样式先隔离，不能一次性清空全局 CSS。

### 7.8 组件示例与验收入口

增加一个仅开发环境可见的 UI 示例页，复用正式主题，展示按钮、表单、空白/加载/错误状态、阶段交接卡、Agent 提问、审批 Diff 插槽和窄屏布局。优先使用现有测试与开发设施，不把新增大型组件文档平台作为前置条件。

测试 ThemeProvider 必须与正式页面使用相同主题及被测配色模式，避免生产深色页面与测试默认配色不一致。组件示例通过后，业务页面只能组合这些规则，特殊例外要有清楚用途。

## 8. 前端代码组织与数据层收敛

建议目录职责：

| 目录/模块 | 职责 |
| --- | --- |
| `app/theme.ts` | 全局主题和基础组件默认规则 |
| `app/router.tsx` | 规范路由及集中维护的旧链接重定向 |
| `components/layout/` | 工作台、项目标题、阶段导航与侧栏布局 |
| `components/feedback/` | 公共异步状态、业务状态与交接卡 |
| `components/agent/` | 通用 Agent 对话外壳，不持有领域批准逻辑 |
| `features/journey/` | 只读流程投影查询、类型、操作映射、项目待办 |
| `features/data/` | 导入与记录浏览，不串联所有后台 Agent |
| `features/world/` | 人物理解及纠正；将大页面按职责拆分 |
| `features/nodes/` | 经历调查、候选、边界审批 |
| `features/branches/` | 分支创建、准备、列表和聊天 |
| `features/advanced/` | 可选训练、模型、评估及诊断入口 |

这是职责收敛，不要求为了目录整齐重复搬动全部文件。已有组件能复用的先复用；只有出现明确共享语义才抽取公共组件。

React Query 统一 query key 工厂和失效策略。一次发布、回答或批准，应刷新相关领域数据和 Journey 投影；不要让每页各列一组不完整的 invalidateQueries。

业务状态在后端；服务器数据在 React Query；打开的面板、输入草稿和阅读位置在合适的本地状态中。不得把“已批准”“分支 ready”等权威状态写入 sessionStorage 代替后端判断。

## 9. 路由与旧入口处理清单

以下是目标路由约定，实施时集中迁移并保留必要深链接：

| 当前入口 | 处理方式 |
| --- | --- |
| 项目列表、创建项目 | 保留；创建后进入首次导入 |
| 项目首页 | 重构为继续工作与待办，不再用旧资产数量判断阶段 |
| `/data` | 转到规范的 `/setup/import`；已导入记录可从资料区继续浏览 |
| 新增 `/setup/participants` | 承载人物绑定和资料确认；复用现有后端能力 |
| `/world` | 保留为人物背景工作台，整合阶段交接 |
| `/events` 与 `/nodes` | `/nodes` 为新调查规范入口，`/events` 只作集中重定向，不维护两套页面状态 |
| `/timeline` | 主入口转向新起点工作台；原旧事件时间轴移入明确的历史只读入口 |
| `/events/legacy` | 从主导航移除，必要时作为高级区历史只读入口保留 |
| `/branches/new` | 改收已批准起点引用，不再接受旧 `eventId/originTime` 作为新流程的批准依据 |
| `/branches/:id` | 保留稳定分支入口；按真实 readiness 显示准备或聊天内容 |
| `/branches/:id/preparing` | 可重定向到同一分支入口，或保留薄路由共用准备视图；不得另写状态判断 |
| `/models`、`/training/:jobId`、`/evaluation` | 下沉高级区；旧链接重定向时保留对象 ID；不是首次聊天门槛 |
| `/world/places` | 保留辅助地图，不改变主线完成状态 |

旧分支链接必须继续可打开，不能因为新起点协议改变就让已有聊天不可访问。携带旧 `eventId` 的新建链接应解释这是旧版起点，要求在新流程重新确认；不能自动把旧事件转换成用户已批准的新边界。

## 10. 删除、保留与重构的明确边界

### 10.1 应删除的前端逻辑

- 首页 `getNextAction` 中基于旧事件/训练模型的流程猜测。
- ImportWizard 中跨多个 Agent 的全流程控制、误用 Job 成功的完成判断与旧节点计数文案。
- 主导航中的强制训练、模型版本选择、技术质量评估入口。
- 创建分支页重新选择旧 EventNode、在 URL 自由拼接起点时间及“必须先训练”的普通用户交互。
- 全局任务提示只展示 running/queued Job 的选择逻辑，替换为业务待办与运行状态的统一投影。
- 相同状态各页不同名称、不同颜色、不同错误处理和重复恢复按钮。
- 已无引用的旧事件交互组件、手写通用控件样式和重复数据请求封装。

“删除”是移除旧产品主线和无用代码，不是删除原始记录、模型文件、历史事件、已批准资料或已有分支。

### 10.2 必须保留的能力

- 原始导入、角色绑定、头像与媒体、记录浏览和原文定位。
- 新版人物背景栏目、来源、纠正对话、版本与图谱多步批准。
- 新节点调查、增量候选、暂停问答、资料范围和批准边界。
- 分支列表、准备与失败恢复、现有聊天记录及微信式聊天体验。
- 虚拟时间、消息时间分隔、表情包和发送状态。
- Phoenix 与必要诊断能力，但默认不占据普通体验主界面。
- 对仍被使用的训练、模型、评估和历史页面提供高级入口，而不是直接删除资产与服务。

### 10.3 必须重构而不能只换文案

- 项目级流程状态与导航判断。
- 新起点批准结果到分支创建的契约。
- 画像审核、节点调查使用的公共 Agent 侧栏。
- 异步数据刷新与稳定视图的关系。
- Mantine 主题、公共组件和旧全局 CSS 的边界。

## 11. 必须同步补齐的后端契约

前端改造不能掩盖这些缺口：

1. **只读 Journey 聚合**：让页面共享同一组真实阶段与待办，不让前端重建业务规则。
2. **批准起点交付**：分支创建接受服务端可验证的选择结果，校验项目归属、资料版本和精确边界。单独传一个时间字符串不够。
3. **历史背景编译**：为所选边界生成对应资料；后文可帮助“发现节点”，不等于可进入该历史分支的认知上下文。
4. **准备契约**：区分必要资产、可选资产、正在准备、等待用户、可重试失败、不可继续及 ready。
5. **模型配置责任**：普通用户不选择 LoRA 版本。当前分支接口仍有模型版本等旧依赖，需由后端明确绑定当前认知配置或运行配置；不能只删除前端校验就宣称依赖消失。
6. **事件/快照一致性**：返回业务对象版本、稳定问题 ID 与可恢复状态。批准仍以事务中的最新检查为准。

在这些契约完成前，可以先改善准备前四步和已有分支的体验；第 5 步缺失项要真实展示。不得以旧创建接口或最新画像兜底来伪造历史流程已完整接通。

## 12. 连续感的具体工程规则

- 列表项按稳定业务 ID 渲染，不能以请求时间或整份响应版本作为整页 key。
- 后台更新保留当前内容、选中项、展开项、输入和滚动容器，不反复挂载页面。
- 稳定待审核状态不需要高频轮询；活动任务按需要刷新，终态停止无意义请求，重新进入时再确认真实状态。
- 若采用推送，断线后从版本化快照恢复；重复或乱序通知不能覆盖新内容。无需为了统一 UI 强制全站改成 SSE。
- 问题回答成功以服务端回执为准；网络响应丢失重试同一幂等请求，不生成两个回合。
- 跨页保留的是同一任务的上下文，不把所有 Agent 的对话共享成一个大聊天室。
- 回到前一步时仍能看见后续工作状态；不清除已确认成果，不把返回导航等同于撤销。
- 阶段阻塞要说明用户可以做什么；尚未实现的能力不能显示“正在处理中”。

## 13. 实施顺序

### 第一批：纠正错误引导，建立统一基础

完成主题与公共状态组件的基线；明确规范路由；删除错误的训练门槛文案和历史隔离承诺；建立 Journey 投影契约及前端读取入口。高级功能先从主导航下沉，不直接删除数据。

### 第二批：打通前三步

拆开导入与后续 Agent 执行，组织人物/资料确认，重构人物背景审核的主次信息与侧栏。每个完成动作都有交接卡；刷新和跨页后能恢复待办。

### 第三批：收拢节点工作台

迁入统一布局、公共 Agent 侧栏、状态和原文组件；节点确认进入项目主线；退役旧时间轴作为新分支入口的逻辑。

### 第四批：补齐分支契约并接入准备与聊天

完成第 11 节中的必要后端能力，再接新建表单和准备清单。已运行分支保持兼容，聊天 UI 不重做。

### 第五批：集中清理

在入口替换和引用检查完成后，删除旧判断函数、重复组件、废弃 CSS 和无用路由实现；保留集中、薄的旧链接重定向。更新测试，不长期同时维护两套业务流程。

## 14. 验收标准

### 14.1 用户路径验收

- 新项目从导入到人物确认、背景审核、节点选择都有清楚的下一步，不需要猜菜单位置。
- 用户在别名审核或 Agent 提问时离开，回来仍能看到同一待办与原草稿。
- 人物背景发布后有结果与节点调查入口，不只是一条短暂 Toast。
- 节点更新不抢选择；回答重复提交不重复启动；用户明确知道哪些范围尚未调查。
- 新批准起点不会落入旧事件/训练模型表单。
- 分支准备缺历史编译能力时明确受阻，不出现假 ready；后端补齐后真实进入聊天。
- 已有分支可直接继续聊天，后台新资料整理不会强迫其回到导入页。
- 失败、待用户操作、没有结果和资料未知不会混为一种空白状态。

### 14.2 UI 验收

- 六个阶段的同类标题、按钮、表单、状态、间距与反馈来自同一规范。
- 主操作一眼可辨，危险操作和批准操作明确说明影响。
- 只用键盘也能完成表单、候选选择和对话；焦点可见，弹层关闭后回到触发位置。
- 宽屏、窄屏均能阅读详情和回答问题，隐藏面板不丢输入。
- 已有内容后台刷新不整页闪烁、不回到顶部；查看旧聊天时不被新消息拉走。
- 聊天仍然像原来的聊天应用，而不是一个多 Agent 监控后台。

### 14.3 工程验收

用少量高价值冒烟用例验证主线、等待/恢复、版本冲突、已有分支兼容和布局稳定；不为每个纯样式枚举大量测试。真实浏览器至少人工走一次桌面与窄屏主线。

测试使用的模拟 ready 不能作为真实资产准备完成的证明。最终交付分别报告：前端代码/构建结果、后端契约实现情况、体验环境实际状态、真实主线是否已跑通。四者不混写成一个“全部完成”。

## 15. 完成后的体验应当是什么

用户始终知道：正在和谁建立这段人生，当前讨论的是哪份资料或哪个起点，系统已经做到了哪里，哪些决定需要自己确认，以及下一步怎样继续。

组件库解决一致的视觉与基础交互，公共工作台解决一致的操作习惯，真实业务投影解决一致的流程判断。三者共同建立连续感，而不是再增加几个看起来统一但仍相互割裂的新页面。
