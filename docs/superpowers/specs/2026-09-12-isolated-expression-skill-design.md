## 1. 决策与表达：共享理解，隔离过程

Director 负责判断：此刻发生了什么，人物如何理解，想怎么回应，以及准备采取什么行动。

表达执行负责实现这个决定：在眼前的对话中，用这个人的方式把意思说出来。

采用以下顺序：

1. Director 完成判断，提交表达意图与本轮状态、记忆等提案。
2. Executor 做无副作用的前置校验。
3. PersonaActor 使用独立 System Prompt 和装配好的上下文，自主进行多轮思考与只读工具调用。
4. PersonaActor 返回最终回复，或明确的任务澄清需求、执行失败。
5. Executor 在当前输入、状态和计划仍有效时统一提交。
6. 实际发出的回复进入正常聊天历史，成为后续 Director 可见的互动。

**隔离的是风格检索、措辞尝试和表达过程，不是切断人物理解，也不是隐藏人物实际说过的话。**

## 2. 为什么隔离 PersonaActor 的上下文

如果把表达过程放进 Director 的主循环，表达规则、检索结果和措辞尝试会占据它的上下文，并影响后续判断。例如，历史风格示例可能被误当成本轮事实，措辞目标也可能反过来改变原有决定。

采用独立表达上下文后：

- Director 不携带表达工具结果和候选措辞继续决策。
- 表达模型仍能看到必要的原话、人物理解和本轮感受。
- 实际发出的承诺、问题、称呼和语气正常回到聊天历史，不逃避行为反馈。
- 表达材料仍由 Phoenix 记录供开发者分析，但不会从 Trace 自动注入正常决策上下文。

这是减少干扰的架构边界，不保证模型绝不会错误引用材料。来源标记、工具作用域、清晰任务和检查仍然必要。

## 3. 独立 Agent，而不是一次 API 改写

PersonaActor 具有独立的 System Prompt、原生工具集合、模型消息列表、恢复检查点与统一 Harness 预算。它使用与 Director 相同的认知模型和思考配置，自主执行“理解任务 → 查询材料 → 查看结果 → 调整查询或措辞 → 产出”的多轮循环。

可能不调用工具直接完成，也可能连续检索风格、展开原文、检索并比较多个表情包的历史使用片段后才完成。模型自行判断是否需要更多材料；不以一次 API、一次检索或固定两轮作为流程终点。

它的职责边界是：

- 负责具体语言、表情包、图文组合和互动表达，不只是机械改写。
- 可以为表达任务向 Director 提出具体澄清，但不维护另一套人物心理和计划。
- 不成为 Director、DayPlan 之外的第三位生活决策者，没有独立生活调度权限。
- 使用现有 AgentLoopController，不手写另一套模型/工具循环。
- 独立 System Prompt 统一维护表达目标、调查方法、自检与边界，不再拆出另一层行为说明。
- 同一任务的调查与候选素材可以恢复，任务完成后不把内部过程灌入 Director。

## 4. Director 交付的唯一表达契约

以 `expression_task` 为唯一新写入口。旧 `communication_intent`、`content_points` 可以在历史读取适配层转换，不继续要求模型同时生成两套内容。

建议语义结构：

```yaml
ExpressionTask:
  purpose: 这次希望通过表达达成什么
  speech_mode: reply | proactive | delayed_reply
  respond_to_refs: 本次回应的消息引用
  must_convey: 必须准确传达的内容，可为空
  optional_content: 可以自然采用但无需全部说出的内容，可为空
  stance: 对当前事情的立场或回应方向，可为空
  feelings: 本轮相关感受及其对象，可为空
  interaction_style: 本次互动希望采用的方式，可为空
  boundaries: 不能新增或改变的事实、承诺、行动和关系边界
  context_refs: 表达时需要展开的相关材料引用
```

这些字段是表达指导，不是逐项填满的问卷。只要求 purpose、speech_mode 和任务类型所需字段；普通问候无需写一套心理分析。回复需要可定位的回应对象，主动开场可以没有 respond_to_refs。

示例：

```json
{
  "purpose": "接住用户的开心，让他愿意继续分享",
  "speech_mode": "reply",
  "respond_to_refs": ["当前消息引用"],
  "must_convey": [],
  "optional_content": ["可以轻轻问一句发生了什么好事"],
  "stance": "一起开心，不急着分析原因",
  "feelings": "被他的开心感染，也有些好奇",
  "interaction_style": "亲近、轻松",
  "boundaries": ["不知道开心的原因，不要替他编"],
  "context_refs": []
}
```

示例引用仅用于说明，不是生产请求的固定值。

### 4.1 表达自由与行动边界

PersonaActor 可以决定句式、语气词、称呼、停顿、分段，以及任务允许范围内的自然接话。

它不能自行承诺改时间、答应见面、改变立场、宣布任务完成，或引入新的事实和实质行动。普通接话问题是否适用，结合 purpose、optional_content 和 boundaries 判断，不再使用“绝不能增加任何问题”的笼统限制。

Director 不应为了控制结果提前写好完整台词；只有必须精确转达的名字、时间、引用等需要明确保留。

## 5. PersonaContext：怎样传递完整理解

由后端 PersonaContextAssembler 装配，Director 不需要重复复制整段对话和画像。

| 层 | 内容 | 装配原则 |
| --- | --- | --- |
| 当前任务 | ExpressionTask | 独立置顶，不混在长背景里 |
| 接话原文 | respond_to_refs 对应消息、尚待处理输入、最近连续对话 | 明确发送者、时间、顺序，不用摘要代替本轮原话 |
| 相关旧事 | context_refs 展开的材料、相关摘要及其引用 | 不复制 Director 全部工具结果；必要时可继续回读 |
| 人物与关系 | 已绑定画像的整体介绍、相关栏目、关系与风格理解 | 保留中文解释及事实/推断区别，不另查全局最新画像 |
| 本轮处境 | 已提交主观状态的相关部分、本轮拟表达的感受与立场 | 明确“已提交背景”与“本轮尚未提交的理解” |
| 表达相关现实约束 | 当前活动、相关已确认安排、必要提交回执、虚拟时间 | 不复制三天完整日程及所有协商材料 |

### 5.1 如何选择而不重新做一遍人物分析

默认提供稳定的表达核心材料：人物整体介绍、身份与相处方式解释、与用户关系、风格摘要。

其他材料依据 Director 的 context_refs 和当前任务已有的明确关联补入。第一版不新增一个“判断该传什么”的模型调用，也不通过聊天关键词正则推断应加载哪个人格栏目。缺少栏目时允许用只读工具按栏目展开。

必需原话和任务不能为了预算被静默删除。可展开的长背景采用摘要及引用；仍超出容量时明确失败或要求缩小任务，不声称已读完全部材料。

### 5.2 不直接传递什么

- Director 的完整模型消息列表和中间推理。
- 全部工具返回、候选计划和未采纳方案。
- 全量未结束关切、全部共享协商记录。
- 没有绑定当前任务的全局最新画像或其他分支聊天。

PersonaContext 是专门的只读投影，不是另一个可写的人物状态。

## 6. Prompt、风格检索与表情包工具

### 6.1 目录与组装

建议目录：

```text
runtime_v1/
  actor.py                  # PersonaActor 的 AgentLoopController 适配
  persona_context.py        # 本文约定的隔离上下文装配
  expression_contracts.py    # 表达任务、图文输出和澄清结构
  agents/
    persona_actor.md         # 独立行为 Prompt 与工具名声明
  tools/
    style_examples.py       # 统一检索文字/表情包使用片段；schema 与查询模板
    director_context.py     # 复用或拆出连续原文、画像读取工具
  collaboration/
    nodes.py                # Director → PersonaActor → Executor
```

`agents/persona_actor.md` 是表达行为的唯一作者维护入口，正文完整说明如何理解任务、查找互动片段、依据历史互动选择表情包、组织图文回复、自检及请求澄清。启动时读取该文件作为 PersonaActor 的 System Prompt，并独立装配 PersonaContext，不再加载额外的表达方法文件。

工具名可以在 Agent 声明中列出；工具 Schema 与实现留在对应工具文件，由 LangChain 原生绑定，不拼进 Prompt，不自建另一套工具注册表。LightRAG 的内部检索模板属于工具实现，不是第二份 Agent 行为 Prompt。

### 6.2 get_style_examples：查互动片段，不是返回一团检索文本

工具目的：理解目标人物在相似互动中怎样表达，包括文字、表情包、单独回应与图文组合。匹配重点是互动目的、情绪、关系距离和表达方式，而不仅是话题相似。

输入保留自然语言 situation、intent、speech_mode，以及受控的返回数量。项目、人物、分支和图版本由后端绑定，不要求模型选择数据库。

处理流程：

1. 用当前互动描述向 LightRAG 检索候选线索。
2. 将引用还原为当前分支可见的真实消息。
3. 展开命中附近连续片段，保留发送者、时间、顺序及文字/媒体类型。
4. 同一区域的重复命中合并；片段长时明确截取边界和回读位置。
5. 返回真实片段供 PersonaActor 理解，不把 RAG 生成的总结当成目标人物原话。

不通过相邻 self/target 消息硬配问答，不用关键词正则判定“关心”“嫌弃”等互动含义。时间间隔是解释线索，不自动证明两句有关或无关。

建议返回：

```yaml
retrieval_status: ready | empty | partial | unavailable
examples:
  - messages:
      - source_ref: 原消息引用
        speaker: 原发送者及角色
        occurred_at: 原时间
        kind: text | sticker | image | other
        text: 可用原文字
        asset_ref: 可用媒体引用，若有
    media_refs: 片段中的可读媒体
    context_complete: 本次提供的局部窗口是否完整，不代表语义必然充分
    before_ref: 继续向前读取的位置
    around_ref: 可展开的命中消息
```

PersonaActor 需要更长前后文时调用 read_conversation，想换互动方向时重新查询。工具不承诺不存在的分页参数。表情包不能只以“[表情包]”占位后就宣称已分析其含义。

### 6.3 表情包统一从 get_style_examples 获得

本方案不引入视觉模型，不调用图片描述、OCR 或视觉向量服务，不把图片或动图帧发送给模型。也不另设 search_stickers、read_sticker 工具。

表情包在当前关系中的用法从真实互动推断，而不是根据画面给它贴固定语义标签。同一张图可能在不同上下文表达撒娇、调侃、敷衍或结束话题；画面含义不等于互动中的实际作用。

因此，get_style_examples 以“使用事件及其前后对话”为检索单位，资产仅作为可复用的表达载体。PersonaActor 根据双方的文字、表情出现位置、时间间隔、后续回应和自己的整体理解决定是否适合当前情境。推断不必依赖明确自述，但也不能声称知道图片上写了什么、画了什么。

### 6.4 如何召回没有文字的表情消息

不能只把 LightRAG 查询结果中恰好出现的表情包当作全部候选。工具后端同时处理两类候选，但对 Agent 保持单一入口：

1. 通过 LightRAG 找到语义及互动相近的聊天区域，展开真实原文。
2. 为目标人物历史表情消息建立使用片段的文本检索投影：将附近双方文字与角色、顺序、时间关联起来，用文字上下文召回使用事件，而不是对图片做检索。

第二类索引复用项目已有文本检索能力，先检查现有 LightRAG 原文索引是否已保留这些关联，缺少时才补建派生投影。它不需要额外的图片理解模型，也不在聊天请求中全量重新分析素材库。

工具合并两路候选，按消息引用去重、展开并返回。片段窗口只是取材料的范围，不代表后端认定这些消息互为问答；PersonaActor 可用 read_conversation 补齐上下文。

没有邻近文字或有效关联的使用事件不能凭资产哈希猜语义，应明确可检索覆盖不足。不能因为索引没覆盖就断言“她不会使用表情包”。

### 6.5 工具返回的表情包关联

在第 6.2 节的原文片段之外，返回本次命中涉及的表情包资产及使用关联：

```yaml
sticker_candidates:
  - asset_ref: 稳定素材引用
    available: 文件是否可读
    usage_refs: 本次可回读的原消息引用
    used_by: target
    uses:
      - source_ref: 一次真实使用
        before_ref: 前文展开位置
        around_ref: 使用消息展开位置
    more_usage_cursor: 同一素材其他历史使用的翻页位置，若有
```

所有用途解释由 PersonaActor 结合原片段形成，不由后端输出固定的“这张图表示关心”。同一素材的多个用法分开保留，不能压成一个永久含义。

get_style_examples 可增加可选 asset_ref 与 usage_cursor 参数，用于在同一入口查看某张候选的其他历史用法。首次调用描述情境即可；按素材查询时必须携带来自已返回材料的合法引用。后端校验分支范围与目标人物使用记录，不允许模型用任意引用遍历资产库。只有实际实现游标后 Prompt 才能承诺此能力。

第一版只复用目标人物真实使用过且在分支可见范围内的素材；用户使用过但目标人物没用过的图不自动进入目标人物候选。普通照片、自拍、截图也不当作表情包发送。

### 6.6 复用现有资源，不再建设视觉标注链路

当前体验项目已只读核对：306 张独立表情包素材均有可读文件，目标人物有 626 次使用，涉及 205 张素材；现有表情包语义标注为 0 条。这是本次核对时的快照，不是代码常量。

复用 MediaAsset、消息与素材关联、媒体读取接口和现有前端图片渲染。需要补齐的是历史使用片段的召回、Agent 返回素材引用，以及新版 Runtime 的图文提交，不是重新收集图片或生成图片描述。

素材层仅负责稳定引用、哈希去重、类型/MIME、原消息与发送者关联、文件可用性。不生成视觉描述或 OCR。文件格式与完整性检查是普通资源校验，不属于模型看图。

原始媒体不修改，派生文本索引另存；本次核对的服务直接读取体验数据目录，不能宣称已经配置了原目录只读回退。检索和提交均检查可用性，文件缺失与没有合适互动样例分开报告。

### 6.7 谁决定使用表情包

PersonaActor 依据表达任务、当前关系与历史互动决定纯文字、文字加表情包，或仅发表情包；Director 无需逐张批准。

不规定每几条必须发图，也不要求每次都额外检索表情包。一次风格查询即可同时获得文字和表情包用法；已有上下文足够时可直接表达，不为复杂度增加固定调用。

必须准确回答的事实、时间和承诺不能用含义不清的图替代。如果上下文不足以判断是否适合复用，可查看该素材其他使用片段、换候选或选择纯文字；不引入视觉模型兜底，也不向用户宣称已经看懂图片。

其他只读工具保留 read_conversation、get_profile_section。计划修改、记忆写入和图谱维护不向 PersonaActor 开放。新的实质事实判断仍通过具体澄清交回 Director。

## 7. 独立调用与状态隔离

PersonaActor 使用与 Director 相同的供应商、模型与思考模式配置，不接 LoRA、不降级成小模型。

LangGraph 中使用独立的 `persona_actor` Agent 节点，但它不是新的同级协商角色。节点调用现有 AgentLoopController，使用独立消息列表、上下文整理缓存和 checkpoint 命名空间。

表达内部模型消息不能写入 Director/DayPlan 的共享 `messages`。共享流程只保留任务状态和必要错误结果；正常成功后直接进入 Executor，不再让 Director 逐句审核一次。

历史恢复命名空间也要区分旧 PersonaActor、新表达执行与 Director，不能把旧 Actor 节点的未完成检查点当成新表达执行继续跑。

### 7.1 预算与恢复

不把固定两轮或固定一次检索当作完成标准。有效输出自然结束，超时、重复无进展和成本上限由统一 Harness 保护。

预算需覆盖完整的“决策＋表达＋提交前处理”，表达阶段不能绕过 Cycle 总预算。具体容量根据真实 Phoenix 数据调整，本设计不随意新增一组小数字。

同一任务、同一输入版本的临时失败，可恢复表达执行，不必重跑 Director。新用户输入、绑定背景变化或依赖的计划/状态版本失效时，旧表达任务作废，重新交给 Director。

## 8. 输出、澄清与失败

表达结果使用互斥类型。以有序 messages 为唯一新写交付内容，替代重复的 text + bubbles；每项是 text 或 sticker 的区分联合，不能混填字段：

```yaml
ExpressionResult:
  status: ready | needs_clarification
  messages:           # ready 时必须为非空有序列表
    - kind: text
      text: 可直接发送的文字
    - kind: sticker
      asset_ref: 本次可用且已检索或查验的素材引用
  clarification:      # needs_clarification 时必须有
    question: 哪个缺失或矛盾会改变表达结果
    related_refs: 对应的任务或材料引用
```

模型调用失败、超时和解析失败由 Harness 返回执行错误，不要求模型把基础设施错误伪装成 clarification。

`needs_clarification` 只用于影响事实、立场、承诺或回应对象的问题。不能因为不知道选哪个语气词就问 Director。返回的是简洁具体的问题及引用，不带全部风格检索记录和措辞草稿。

Director 收到澄清后可修订任务、补查资料、决定问用户或停止表达。反复相同澄清视为无进展，受同一任务总预算约束，不能无限来回。

## 9. Executor：只提交真实产生的表达

提交前重新检查：

- 本次任务对应的输入 revision 是否仍有效。
- Director 基于的状态、相关计划或已确认约束是否已变化。
- 虚拟时间推进是否使当前任务前提失效；不能只按表达启动时刻验收。
- 输出结构是否合法、顺序是否明确；每条文字非空，每个素材引用属于本任务授权范围且实际可读。
- 素材引用是否来自本任务可用上下文或成功工具结果；模型不能自造文件路径或 URL。
- 幂等键是否已经提交过。

消息类型、必填字段、素材权限与存在性可以做确定性检查；“有没有新增承诺”“是否像真人”不能声称靠 Pydantic 或正则就能完整验收。第一版依靠任务边界、PersonaActor Prompt 中的自检及真实用例观察，不额外常驻一个审稿 Agent。

表达失败时，不发送 Director 的内部要点、不冒充主动沉默，也不把用户输入标记为已回复。依赖表达成功的状态和记忆变化不能落库。

沿用统一提交事务：回复、输入处理结果及对应状态/记忆更新一并提交。Director/DayPlan 先前已通过独立事务成功提交的计划不因表达失败而回滚。

### 9.1 图文提交和前端展示

一组 messages 以稳定的提交标识和序号保序，沿用现有消息/媒体模型；若当前存储只支持一条文本加 bubbles，需要明确适配或迁移，不能把图片信息塞进 text 冒充完成。

前端在原微信式聊天界面渲染文字与表情包，不新增“新版 Runtime”页面。由后端将 asset_ref 解析为现有受控媒体地址，支持静图、动图、历史回读与重连后的稳定顺序。内部 reference 不作为用户可见消息。

某张素材提交前失效时，返回可恢复的媒体错误，让 PersonaActor 在同任务中重选或明确改为文字。不静默删除图片：那张图可能决定整组文字究竟是玩笑还是指责。可在不依赖素材持续可变路径的前提下使用受控持久资产引用；显示时遇到文件丢失要呈现加载失败，不能宣称已经完整展示。

后续 Director 读取实际聊天时也保留 sticker 类型、asset_ref、原始使用引用及必要的对话回读能力，不把“只发了表情包”变成一条空消息。只有实际发送的素材引用及其关联聊天语境进入历史，未采用的候选和检索过程不回灌。

第一版 messages 表示图文顺序，不实现逐条打字、发送延迟或中途打断。原子保存和网络展示是两回事，重连不得重复插入消息。

## 10. 哪些内容会回到 Director

正常成功时，后续 Director 可见：

- 实际发出的聊天原文及时间。
- 已提交的人物状态、记忆与行动结果。
- 必要的提交回执。

不会回灌：PersonaActor 的 System Prompt、表达模型中间消息、风格查询结果、候选台词和表达过程分析。

澄清时，只返回第 8 节的具体问题。失败时，只返回可用于重试或重新决策的错误类别和任务状态。

表达工具材料不自动进入记忆。若实际回复作出了有意义的承诺，必须与 Director 原批准任务一致；不能事后把表达模型擅自新增的承诺当作合法行动。

## 11. Phoenix 观测

同一 Runtime Cycle 下区分 Director、PersonaActor 与 Executor 阶段。表达阶段记录真实模型和工具调用、耗时、失败、模型配置、PersonaActor Prompt 版本、输入材料范围与最终产物。

表达和决策关联使用内部任务标识，不要求模型输出数据库 ID。内部标识仅用于恢复、追踪和提交校验。

继续保留项目已有的上下文诊断能力；开发者可以查看表达材料，但正常运行不从 Phoenix 恢复业务状态。可恢复数据由现有 Harness checkpoint 和任务状态负责，不恢复自建 AgentRun/Step/ToolInvocation 表。

## 12. 从当前工作区收敛的实施顺序

1. 检查被中断的修改，逐项处理，不整体回滚用户其他改动。
2. 从 Director 主循环移除表达加载工具与风格工具；Director 只提交 ExpressionTask，不直接生成 reply。
3. 建立 PersonaActor、独立上下文和表达结果契约；将全部表达行为统一写入 agents/persona_actor.md，不保留独立表达 Skill 文件或加载入口。
4. 把运行图接成 Director → 前置校验 → PersonaActor → Executor；保留 DayPlan 同级协作。
5. 处理澄清、失败重试、旧输入作废、幂等提交和检查点版本边界。
6. 按新版职责恢复并改造 PersonaActor 入口、独立 Prompt 和上下文装配器，清理被替代的重复接口，不删除 Agent 本身。历史数据库字段保留可读；兼容字段与适配代码明确标注，不作为新模型输出接口。
7. 改造风格片段检索，复用已核对的媒体资产，在 get_style_examples 内接入使用片段检索及有序图文输出，不接视觉模型。
8. 补齐提交、前端渲染与历史回读；同步工具说明，通过冒烟后，再经确认重启体验环境。

## 13. 最小验收

- 普通问候：Director 形成任务，PersonaActor 在独立上下文中完成表达，不强制检索，最终消息正常提交。
- 多轮能力：真实 Harness 下覆盖查询风格 → 回读上下文 → 查询同一素材的其他历史用法 → 重新选择 → 输出，不是固定单次 API。
- 风格查询：返回真实互动片段，保留角色、时间和媒体；工具结果不进入 Director 的主消息列表。
- 表情包：覆盖纯文字、纯表情、图文混排；检索失败、文件不可用和历史上下文不足均有明确处理。
- 无视觉依赖：不调用视觉模型、OCR、图片描述服务或视觉向量服务；不把图片内容注入模型。
- 情境理解：同一张图的不同历史用法保留各自上下文，不被固定标签覆盖；无文本表情消息也能通过关联片段召回。
- 素材边界：拒绝自造路径、其他分支资产和把普通照片当表情包发送。
- 前端与回读：图片、动图、消息顺序、刷新重连和 Director 后续看到的已发图文一致。
- 任务与上下文：本轮原话、相关旧事、新感受准确传达，不需要表达重新推断一次人物心理。
- 计划协作：只有确需修改计划时才进入 DayPlan；表达只使用已成功提交的安排。
- 澄清：不清楚是否已承诺出发时间时返回具体问题，不自作主张答应。
- 输入更新：表达期间收到新消息，旧回复不能提交。
- 临时失败与重试：失败不标记已回复；同任务恢复不重复发送、不重复写状态和记忆。
- 历史兼容：旧数据仍可读，旧 PersonaActor 检查点不会进入新表达路径。

验收使用小规模离线冒烟与少量真实对话，不扩展成耗时的大型评测工程。自然度必须看真实运行结果，不能只凭架构和结构校验宣称已解决。
