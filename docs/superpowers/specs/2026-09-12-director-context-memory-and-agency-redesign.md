# Director 重设计：人物处境理解、情绪与应对、连续对话及分层记忆

日期：2026-09-12  
状态：待审核设计；本文中的新增契约、工具和数据结构尚未实现。

本次修订：以 Lazarus 的认知—动机—关系理论为心理学基础，以 EMA 为实现参考，统一此前分散的关切、情绪、意向与行动进展。以下结构是 EMA 启发的项目设计，不是原模型复现，也不意味着能够还原真人内心。

## 1. 目标与边界

Director 不只是依据日程判断“回复还是等待”的路由器。它负责结合人物理解、正在发生的生活、与用户的交往历史，决定目标人物此刻怎样回应、继续做什么、暂时不做什么，以及哪些事情值得记住或稍后跟进。

本次重设计首先解决材料连续性和状态持久化，再调整行为 Prompt。不能用更长的 Prompt 掩盖聊天没有加载、记忆没有写入或检索不相关的问题。

统一主线是：人物经历了什么 → 怎样理解自己与环境的关系 → 产生怎样的感受和应对倾向 → 选择行动 → 根据实际结果重新理解处境。它描述跨轮反馈，不要求每轮执行五次模型调用。

沿用已经确认的架构：

- Director 与 DayPlan 是同级 Agent，通过现有 LangGraph 共享消息与任务协议交流。
- Director 默认可读昨天、今天、明天的共享计划，自行判断可用性；只有确需修改安排时才请求 DayPlan。
- DayPlan 负责计划和模拟生活事件；Director 提供当下心理理解、关切与意向，但不是 DayPlan 的审批上级。
- PersonaActor 负责结合上下文、工具与人物风格形成实际表达，使用云端认知模型；不恢复 LoRA 路径。
- Executor 是已提交业务变化的唯一写入入口。Agent 只提交提案。
- 继续使用 LangChain 工具、LangGraph 协作和统一 AgentLoopController，不新增独立循环。
- Phoenix 记录真实模型调用、工具调用、失败和上下文诊断；不恢复自建模型调用流水表。
- 暂不重做 OriginSnapshot 历史切片；体验分支沿用当前最后导入时刻的约定，明确实际绑定的已发布画像版本。

## 2. 现状：已经存在什么，缺少什么

以下来自当前工作树代码检查，不代表对某次真实供应商输入做过 Trace 验证。

| 链路 | 当前实现 | 本次需要解决的问题 |
| --- | --- | --- |
| 本轮用户消息 | `service.py` 将原文写入 BranchMessage 和触发事件；Director 可通过 trigger 读取 | 不应误诊为所有用户消息都没有传入；需要显式管理待处理消息及消费状态 |
| 最近聊天 | `context.py::_working_window` 按两小时、16 条筛选，再按 turn_id 补少量消息 | 时间间隔导致原文消失；turn_id 不是语义话题 ID |
| 导入历史 | `source_history.py` 支持前端历史投影 | 前端能看到不代表 Director 已收到，需要建立分支起点的对话衔接 |
| 人物背景 | ContextAssembler 提供 v3 画像投影 | 需要明确版本、语义层次和按需展开，不把所有人物描述当成当下状态 |
| 记忆初始输入 | `memory.retrieved_records` 初始为空 | 没有常规的相关记忆预取 |
| 分支记忆搜索 | `memory.py` 返回按确认状态、置信度和时间排序的候选，SQL 排序不使用 query 语义 | 不能称为分支语义检索，也不等于搜索新产生的聊天原文 |
| 原始世界搜索 | `tools/memory_search.py` 可查询 LightRAG 历史 | 原始世界与分支新增经历不是同一个数据范围 |
| 摘要 | `context.py::_persist_summary` 截取各消息片段，预算路径才触发 | 不是可靠的连续对话摘要，缺少常规回读和覆盖管理 |
| 记忆写入 | 存在 `Executor.confirm_memory` 和确认 API | 正常 Director 决策尚未形成自动的分支记忆提案闭环 |
| 当前心理状态 | `StatePatch` 有 mood、attention、current_goal 等字段 | 缺少可恢复的多项关切，也未充分区分事实、解释和意向 |
| 同级沟通 | 已有共享 collaboration | 模型投影存在 current 和顶层重复携带，需消除重复但保留共同可见性 |

## 3. Director 究竟维护什么

### 3.1 人物画像不是本轮重新生成的东西

PersonWorldProfile 描述相对稳定的人物理解。Director 使用其中的性格模型、偏好、价值、处境、关系和规律，但不在每条聊天后重新测一遍人格，也不把 MBTI 等标签机械翻译成固定动作。

例如，画像帮助理解她通常如何表达关心；当前互动决定这次是追问、陪着吐槽、讲自己的经历，还是稍后再谈。画像提供倾向，不替代具体判断。

### 3.2 心理学基础与实现选择

Lazarus 的《Emotion and Adaptation》（1991）将情绪与人物的目标、环境和应对联系起来，而不是把情绪看成独立标签。对项目的启示是先表达“这件事对她意味着什么”，再理解感受与行动。[出版社原著介绍](https://academic.oup.com/book/53474)

EMA（Marsella 与 Gratch，2009）围绕共同的“处境因果理解”组织信念、愿望、意向与计划；观察、推断和应对改变这一表征，情绪评价随之变化。本设计借鉴其统一表征与反馈结构，不照搬原实现中的符号规则、情绪映射和数值参数；语义评价由 Director 完成。[EMA 原论文，第 2.3 节](https://www.cs.uky.edu/~sgware/reading/papers/marsella2009ema.pdf)

其他模型只用于补充边界，不各自建立一个 Agent 或状态系统：

| 参考 | 借鉴内容 | 不采用的做法 |
| --- | --- | --- |
| Scherer，成分过程模型 CPM | 检查评价是否包含相关性、后果、应对能力与规范意义 | 把评价维度拆成固定串行模型调用 |
| Ortony、Clore、Collins，OCC | 区分针对事件、他人行为和对象的评价 | 只选一个情绪类别就直接生成动作 |
| Frijda，情绪与行动准备 | 行动倾向不等于实际行动 | 生气必然指责、开心必然分享 |
| Gross，情绪调节过程模型 | 改变处境、注意、理解或反应可以是不同应对方式 | 把克制表达等同于内心已经平静 |
| Carver、Scheier，行为自我调节 | 关注目标进展和结果反馈 | 只记录一次目标，不再更新进展 |

参考依据分别见 [Scherer](https://pmc.ncbi.nlm.nih.gov/articles/PMC2781886/)、[OCC 原著介绍](https://books.google.com/books/about/The_Cognitive_Structure_of_Emotions.html?id=dA3JEEAp6TsC)、[Frijda 原著章节](https://www.cambridge.org/core/books/abs/feelings-and-emotions/emotions-and-action/C110220022118243143A8F376B37A58B)、[Gross 原论文](https://emotrab.ufba.br/wp-content/uploads/2020/08/Emotion-regulationCurrent-status-and-future-prospectsGross2015.pdf)、[Carver 与 Scheier 原著章节](https://www.cambridge.org/core/books/abs/on-the-selfregulation-of-behavior/control-processes-and-affect/668163ED52A5E060E8E094D06CB1D299)。调研使用公开章节、摘要和论文，未通读全部著作；这里的工程取舍不是这些理论共同认可的标准架构。

### 3.3 当前处境状态，而不是几个互不相干的心理列表

拟用 `SubjectiveState` 统一人物当下的理解，包含整体底色与值得跨轮延续的事情。整体底色保留当前心境；身体精力引用生活状态中的唯一记录，不再复制一份独立能量值。

具体事件引发的感受附着在对应事情上；整体心境是较弥散的状态，不强制归因到单个事件，也不由各条情绪简单求和。疲劳不是生气，心境也不等于某一件事的情绪。[情绪与心境的区分见 Gross，第 2–3 页](https://emotrab.ufba.br/wp-content/uploads/2020/08/Emotion-regulationCurrent-status-and-future-prospectsGross2015.pdf)

Director 维护少量值得继续携带的事情，例如：

- 用户提到明天面试，尚不清楚他担心什么。
- 自己刚收到临时工作，需要处理，但还记着今晚的约定。
- 刚才的玩笑可能没有被接住，下一次表达需要留意。
- 答应稍后告知一个结果，目前还未兑现。

不是每条消息都生成事项，不强制填写“关心什么”，也不要求每个闲聊话题建立生命周期。短暂感受允许不形成长期记录。关系中的默契、误会和边界可以作为事项理解维护，不另建单一“好感度”。

### 3.4 三类内容必须能区分

| 类型 | 示例 | 使用方式 |
| --- | --- | --- |
| 已记录陈述或已发生事件 | 用户说“明天面试”；分支模拟事件已提交 | 保留说话者、主体、时间与来源；用户陈述不等于外部核验事实 |
| Director 的理解 | 用户可能更想被听见，而不是马上得到建议 | 允许依据整体上下文推断，可修订，不升级为用户亲口确认 |
| 人物意向 | 想先问问他最担心哪部分 | 尚未执行；不能当成已问、已答应或已完成 |

心理理解不要求逐条提供直接引语或通过独立核验 Agent。关联当前材料是为了恢复语境与纠错，不是给每个推断设置证据门槛。与此同时，“我猜他担心”与“他说他担心”不能混写。

## 4. 上下文组织

### 4.1 一个清晰的语义输入契约

拟新增 DirectorContext，按以下区域组织，而不是继续堆叠不透明字典：

| 区域 | 内容 | 装载策略 |
| --- | --- | --- |
| persona | 已绑定画像的核心理解、相关细分字段 | 稳定核心常驻，细分字段按需展开；版本在运行侧绑定 |
| situation | 虚拟本地时间、完整三日计划、当前块、已提交生活状态、承诺、实际变化 | 每轮刷新；计划缺失显式标记，未来计划不当作经历 |
| conversation | 未处理用户原文、最近连续对话、必要旧原文、摘要导航 | 本轮主体材料，优先保障 |
| subjective_state | 整体心境，以及事项关联的关切、评价、感受、应对和进展 | 同一持久状态的投影；有关事项优先，其余可检索 |
| recollections | 与当前输入相关的历史片段和分支记忆 | 有限预取，Director 可继续查询 |
| collaboration | Agent 商量记录、任务状态和提交回执 | 独立区域，全体可回查；不混成用户对话或生活事实 |

后台版本、CAS、数据库 ID 留在运行封套中。模型只接收引用所需的稳定 source_ref、concern_ref 等公开句柄。不能为了隐藏 ID 而把一切来源引用都删掉。

`situation` 表示已提交的现实条件，`subjective_state` 表示人物怎样理解它们，二者不是重复事实库。系统可见的未来候选和内部协商不自动成为人物已知事实；模型输入必须标明已知事件、预期和假设。

### 4.2 聊天是主线，但不混淆协议角色

第一版保留带 speaker、角色、时间和 source_ref 的结构化聊天原文，不必为了“像聊天”而强行映射成供应商的 assistant 历史：历史目标人物消息并不是 Director 自己先前输出的工具决策。

输入中明确列出 `pending_message_refs`，原文在统一 conversation.messages 中仅出现一次。触发事件通过引用关联它，避免 trigger 和窗口重复堆放同一句话。

结构化携带原文不等于摘要；content 必须完整保留。System Prompt 与聊天资料分离，聊天文本不能变成运行指令。

### 4.3 最近窗口不以时长决定记忆消失

取消“两小时后不再加载”的硬语义边界。按连续消息顺序和上下文预算选择近期后缀，尽量保留完整问答关系。

- 未处理用户消息单独受保护，不受普通最近窗口限制。
- 时间跨度作为信息显示，让 Director 理解隔了一晚，而不是后端替它断定话题结束。
- 特别长的单条输入不得静默截断；超出可执行预算时显式进入输入过长/待处理状态，保留原文并提供分段读取路径。
- 不把所有历史永久塞进每次调用。较老部分通过持久摘要、相关原文补回和查询工具承接。

分支最初没有新增聊天时，从当前绑定边界之前导入一段真实连续对话，作为 conversation 的历史前缀。后续新增消息自然接在其后。历史消息携带 import 来源和独立顺序，不伪造为新 BranchMessage，也不让历史消息重新触发回复。

## 5. 统一的处境状态与情绪演变

### 5.1 谁来判断

Director 判断什么值得继续关注；后端只检查结构、归属和更新版本，不用正则、关键词或沉默时长识别话题结束。

“不再讨论”“事情解决”“承诺完成”是不同的事情。关切状态也不承担消息删除或原文压缩开关。

拟采用以下结构，字段是项目语义示意，不是心理学量表，落地时由 Pydantic Schema 定义。`Concern` 保留为事项对象的名称，但其内部统一评价、情绪和应对，不再另外维护同一事情的情绪副本：

```yaml
SubjectiveState:
  background:
    mood: 有些紧绷，但不是对所有事情都烦躁
    body_state_ref: current_life_state
  concerns:
    - focus: 临时工作可能影响今晚的约定
      subjects: [target]
      appraisal:
        interpretation: 增加了一项工作，完成时间还不清楚
        stakes: [不想失约, 希望自己的时间得到尊重]
        expected_consequences: 可能推迟出发，尚未确定
        causal_understanding: 暂不清楚为什么必须现在完成
        coping_potential: 可以先确认范围，再协商安排
        open_questions: [剩余任务是否必须立即完成]
      response:
        feelings: 有点烦躁，也着急
        action_tendency: 想先弄清楚，而不是立刻取消约定
      coping:
        intention: 先确认任务范围
        action_ref: null
      progress:
        status: active # active | parked | resolved
        latest_change: 收到临时任务
        resume_when: 任务范围明确或用户询问安排时
      source_refs: [event_ref]
```

未变化字段不必每轮重写，未知字段可空。`appraisal` 是人物的可修订判断，不是独立事实；`coping.intention` 不是已执行动作。动作提交后关联 `action_ref`，执行状态及结果来自已有任务/回执，不能由模型在这个对象里自称完成。重要承诺同理，引用专门业务记录，不维护第二套完成状态。

`resume_when` 是 Agent 理解的描述，不是后端执行的自然语言定时器。确需定时跟进时提交独立 wakeup 意向，由 Executor 校验时间、写入调度，并关联关切；状态变化时撤销不再需要的唤醒。

含义：active 当前关注；parked 暂放但可再提；resolved 当前理解下已解决或无需再处理。允许 resolved → active。保留更新历史，不销毁原文。

### 5.2 一次普通 Director 决策顺带维护

在 LifeDecision 中新增 `subjective_state_updates`，支持整体心境更新及事项创建、修改和重新打开，替代上一版尚未实现的 `attention_updates`。更新可以发生在 speak、wait 或生活推进时，不要求每轮生成。

不新增 TopicAgent，不要求先扫描所有话题再允许回复。当前关切过多时由 Director 合并、暂放；上下文仅加载有关项和少量导航，其他项仍可检索，不通过数量上限删除业务记录。

### 5.3 演变规则：重新评价，而非随机重置

Director 读取旧状态、新事件、行动结果及实际经过的虚拟时间，判断哪些前提变化，再提交必要更新。不强制情绪每轮变化，也不每次都从画像重新推导一份状态。

| 示例变化 | 处境理解可能变化 | 可能的应对与感受 |
| --- | --- | --- |
| 收到临时工作 | 晚上约定可能受影响 | 着急，先确认范围 |
| 确认只需十分钟 | 影响比预想小，仍能按时出发 | 紧张缓解，决定处理 |
| 用户表示理解 | 关系压力减轻 | 感到被体谅，但工作未完成 |
| 工作实际完成 | 障碍解除 | 放松，疲劳可能仍在 |
| 到了出发时刻 | 原先意向可执行 | 推进实际安排 |

这只是验收场景，不是后端事件→情绪映射表。没有新的外部事件时，注意转移、回忆和重新理解也可能改变状态，但不能因此伪造外部经历。人物对假设的担心可以存在，假设本身不能变成事实。

第一版使用定性感受及变化描述，不设置未经校准的愤怒分数、固定情绪半衰期或“安慰一次就清零”。时间是重新评估条件，不自动解决关切；没有相关变化时保留状态，重要问题不因窗口裁剪消失。

### 5.4 应对与主动性

应对不限于压低情绪：可以解决问题、请求协助、调整安排、暂时转移注意、重新理解，也可以选择克制表达。它们由 Director 按人物和处境选择，不要求每次做出理性完美的调节，更不把数字人写成总在分析自己的心理咨询师。

行动倾向可能被现实条件、关系目标或其他关切约束，不直接转成动作。主动联系来自具体分享意愿、持续关切或约定，而非“有空就发消息”。需要未来执行时才提交可调度的意向；没有明确理由时不为每项情绪创建定时任务。

## 6. 摘要与检索：压缩材料，不决定遗忘

### 6.1 连续区间摘要

当历史积累导致近期原文预算不足时，对较老的连续区间生成摘要，不等某个话题“结束”。摘要应记录谈了什么、哪些结果已经出现、哪些问题没回答、有哪些约定，以及必要的原文定位。

拟持久化字段：来源流、起止顺序、覆盖消息引用、内容版本、摘要文本、未决事项引用、生成状态。摘要不能把猜测升级成事实，也不能代替正式承诺或关切状态。

使用统一 Controller 执行有界的摘要维护任务；不增加一个参与人物决策的同级 Agent。优先异步预制；摘要可拆成多个连续段，避免失败后整段重新生成。

只有覆盖关系校验通过并持久化成功，后续输入才可以用它代替所覆盖的旧原文。失败时保留上次有效摘要和未覆盖范围；若无法在预算内继续，本轮明确失败/等待重试，不能假装材料已总结。

摘要不是只存起来：ContextAssembler 必须实际加载与最近窗口衔接的摘要及相关旧段导航。需要准确措辞、指代或承诺时回读原文。原文持久化始终保留。

### 6.2 分支自己的语义检索

增加针对 BranchMessage 连续片段、已提交分支记忆和已发生生活事件的语义索引。基础数据在业务库，向量索引是可重建派生数据，不是第二份事实源。

- 原始导入世界继续由已有 LightRAG 提供查询。
- 分支索引按 branch 和可见截止时间隔离；先过滤作用域再召回，禁止跨分支串线。
- 保留说话者、事件主体、时间、来源类型和原文引用。
- 先按相关性召回，再结合时效、当前关切和纠正状态排序；不得把最近记录冒充语义命中。
- 通过事务 outbox 异步建立索引；刚提交但尚未入索引的内容仍在近期原文层可见。
- 查询返回索引覆盖进度、缺失范围和失败状态。空结果、索引未完成、检索服务失败分别表示，不统一成“没有资料”。

第一版可复用项目现有 embedding 配置建立隔离分支索引，不需要把模拟经历写入原始 LightRAG 图谱，也不引入另一套图谱治理流程。

### 6.3 自动预取与主动查询

Assembler 用本轮用户原文和当前关切的简短描述做小规模语义预取，不额外调用模型生成查询。不相关材料由 Director 忽略，存在模糊指代时使用工具改写问题再查。

没有本轮用户消息时，以实际触发事件和关联关切为检索线索，不进行无目的全库搜索。

## 7. 分支记忆写入闭环

新增 `memory_proposals`，让 Director 在普通推理中提出值得长期保留的变化。不要求每轮有新记忆，不把所有对话复制成记忆。

候选类型包括：用户陈述、分支已发生经历、关系互动理解、人物当前解释、承诺关联。记录 subject、summary、来源类型、来源引用、有效时间及 supersedes 关系。承诺的执行状态仍归专门业务状态，记忆只引用它。

Executor 校验引用确属可见范围、提交幂等性与结构一致性；不以正则判断情绪，不声称代码能证明心理推断正确。

自动写入使用明确的 user_report / observed / inferred / simulation 等来源或认识状态，不一律写成 confirmed。用户明确纠正可覆盖旧理解，旧版本保留但不再作为有效结论自动召回。

当前输入中冲突的新说法先记录“用户此刻这么说”，结合时间、主体与语境判断是否替代旧记录；不采用“最新一句话永远覆盖一切”的机械规则。

分支记忆、解释和模拟事件不得反向修改已发布 PersonWorldProfile 或原始 LightRAG。原始人物世界纠正仍走已设计的人工多步确认流程。

## 8. 每轮运行与提交

普通路径：领取触发事件 → 装载版本化上下文 → Director 统一循环与只读工具 → 必要的同级协作或表达 → Executor 提交。

Director 本轮任务不是输出完整心理分析，而是：结合新材料更新处境理解；形成或修订评价与应对倾向；选择实际行动；附带必要的处境状态和记忆变化。执行结果在下一次事件中触发重新评价，构成反馈闭环。这些是一次统一 Agent 任务内的职责，不是强制拆分的多个 Agent 或模型调用。

### 8.1 输出契约演进

保留现有 action、plan_request、peer_reply、next_wakeup_at；新增 subjective_state_updates、memory_proposals 和更明确的 expression_task。state_patch 继续承载生活条件变化，但其中旧 mood、attention、current_goal、open_conversation_threads 逐步改为新处境状态的兼容读取投影，不允许新旧字段双写。精力、活动和位置仍归生活状态，处境状态只引用它们。

expression_task 包括表达目的、需要承接的用户内容、相关事实/理解、希望采用的互动方式、不可声称已经完成的事项，以及必要的原文引用。不是 Director 写好台词再让 Actor换词，也不是只有“安慰用户”四个字。

同时传递本次表达相关的感受与应对选择，例如“仍疲惫，但感到被理解，愿意简单回应，不把工作烦躁迁怒给用户”。这不是台词，也不要求把内部心理解释说出来。

迁移时由适配层将 expression_task 转成现有 Actor 入参，随后删除重复旧字段；不要长期维护两个相互矛盾的表达契约。

### 8.2 待处理与已回复分开

每条输入关联处理状态与决策回执：未处理、已理解但待回应、已完成。选择 wait 不自动代表用户消息已回复，也不能导致它永远被当作新消息反复触发。

延迟回应关联 wakeup 与消息引用。Agent 可以决定不需要回复，但必须作为业务结果保留；模型失败不得伪装成有意沉默。新用户消息到来时，Director 看到尚待回应内容并决定一起处理。

### 8.3 事务、版本与恢复

处境状态和记忆提案在 Executor 事务内写入，使用输入 revision、状态版本与幂等键保护。更新引用已提交的旧处境版本，重试不重复叠加感受。Actor 尚未成功提交的内容不能成为“我已说过”或“我已答应”。

允许先提交不依赖表达的处境理解和感受变化；任何依赖实际发言的承诺或记忆必须与最终消息成功提交绑定。两类变化在提案中明确依赖，不依靠执行顺序猜测。表达失败是运行故障，不自动成为人物受挫事件；它不应凭空触发更强的烦躁。

长运行后提交重新读取虚拟时间、计划和输入 revision。有新消息或前提失效时重新评估，不能提交基于旧上下文的过期决定。失败恢复读取业务状态、图 checkpoint 和持久化摘要，不从 Phoenix 拼接正常业务状态。

## 9. 与 DayPlan、模拟事件和 PersonaActor 的衔接

DayPlan 读取共享日程和按需提供的处境状态投影。模拟事件协商时，DirectorLifeContext 来自同一份已持久化 SubjectiveState 加本轮判断，绑定状态版本，不在另一条路径虚构一套独立心理状态。

Director 解释当前在意什么、可能怎样应对；DayPlan 判断生活安排如何展开，必要时提出不同方案。后端机会参数描述允许的影响范围，不能直接指定人物应该生气或开心。普通可用性判断仍由 Director 阅读共享计划完成，不为判断而询问 DayPlan。

DayPlan 的候选、Director 的暂定 appraisal 和未提交排程只是商量材料。只有成功回执后的事件才进入实际经历；Director 随后可以更新感受、关切和表达意向，不要求每件事都告诉用户。

PersonaActor 接收同一连续对话基础、相关人物风格与 expression_task，可用既有风格工具查找表达方式。它负责措辞、表达强弱和消息组织，不独立生成或持久化另一套情绪，不把疲惫改成对用户生气，不重新决定计划，也不新增未经提交的生活事实。克制表达不等于内部感受已消失；如表达任务矛盾，返回修订请求而不是擅自改变人物状态。

所有 Agent 的商量记录继续存在共享 State，均能访问完整记录。长历史只在模型输入视图中做可回查压缩，不删除底层消息，不建立彼此不可见的私有协商历史。相同记录不同时放在 current 和 collaboration 两处。

## 10. 工具与 Prompt 组织

### 10.1 拟提供的只读工具

| 工具 | 作用 | 边界 |
| --- | --- | --- |
| search_memory | 统一查询相关人物背景、经历、约定与已有理解 | 后端自动查询绑定世界与分支记忆，模型不传 scope |
| search_conversation | 语义搜索完整可见交往历史 | 自动融合导入历史与分支命中、去重并排序；模型不选数据源 |
| read_conversation | 按 around_ref 展开前后文，按 before_ref 向前翻页 | 自动定位来源并跨起点衔接，不暴露 source/import_before_ref 等存储参数 |
| get_subjective_state | 读取整体状态，按主题或引用展开当前、暂放、已解决事项及其评价和进展 | 替代拟议的 get_current_concerns；可重开事项，不把 resolved 当成不存在 |
| get_profile_section | 按需展开已绑定画像栏目和模块 | 不能读取另一个未经绑定的画像版本 |
| get_recent_life_events | 读取已提交模拟经历 | 保留 simulation 来源，不返回候选为事实 |
| read_runtime_result | 回读本次工具长结果 | 继续复用统一运行时能力，不替代持久历史工具 |

工具通过 LangChain BaseTool/StructuredTool 定义并由统一 Controller 绑定给模型。工具 schema 不手工塞进 system prompt。各工具的检索实现及内部检索提示与工具代码放在一起。

底层的隔离不等于 Agent 的选库任务。导入历史与新增聊天在人物视角是一段连续交往；后端仍保护绑定快照、时间和分支边界。搜索按名次融合不可直接比较的不同检索器分数；命中以真实消息引用去重，原文重新从可见数据读取。来源标记仅用于理解材料，不要求模型先判断它存在哪里。某一路检索不可用时返回已有结果及 partial 状态，不能把失败解释为历史不存在。

### 10.2 文件边界

拟按职责拆分，避免把 context.py 再做成大文件：

```text
runtime_v1/
  prompts/director.py           # 主行为规则，人工维护
  agents/director_life_events.md # 同一 Director 的生活协商任务规则
  director.py                   # AgentSpec/Controller 适配
  director_context.py           # 分层上下文装配
  director_contracts.py         # DirectorContext、SubjectiveState、Concern、表达任务与提案
  conversation/                # 原文视图、摘要、覆盖状态、检索适配
  subjective_state/            # 统一处境状态读取、版本与更新；不实现心理正则规则
  tools/                       # 各工具独立文件
  memory.py                    # 记忆领域服务，必要时再拆包
  executor.py                  # 唯一提交入口，调用上述领域服务
```

这些是新实现位置建议，不能为整理目录复制一套旧实现并长期并行。复用现有分支消息、记忆、摘要表；确有字段缺口才迁移，先明确旧数据读取路径。

Prompt 应直接指导：先读哪些材料；如何沿着当前对话理解人物；何时需要回查；怎样选择实际行动；怎样区分理解与已发生事项。通过少量完整场景说明，不堆抽象哲学问题，不复述 JSON Schema，不要求每轮心理维度打分，不要求输出隐藏思维过程。

主行为规则以“处境评价—应对—反馈”为主线，给出有关新信息改变判断、情绪与行动不同步、表达不等于感受消失的简短示例。不能只写“使用 EMA”就期待模型自动遵守持久化契约，也不能要求普通问候填完所有评价字段。不新增情绪 Agent、关系 Agent 或独立心理循环。

## 11. 预算与运行故障

上下文预算和 Agent 循环预算继续由统一运行时管理。模型能力配置保留推理模式，实际启用情况由供应商请求与 Phoenix 核实，不能仅凭配置字段名称判断已开启。

有匹配 tokenizer 时记录精确计数；没有时使用明确标注的估计及供应商 usage 校准，预留输出、工具 schema 和推理开销。不以“云端会处理”为由任意发送超长上下文，也不将字符数标成精确 token。

优先保护当前未处理输入、关键当前状态和明确承诺；先减少重复材料与不相关召回，再使用已持久化摘要替换旧原文。无法满足预算时明确失败，不静默丢失必需信息。

工具出错允许有界恢复与替代查询；查询无进展、重复相同失败、总 deadline 等由既有 Controller 治理。恢复状态与分支记忆持久化，不依赖进程内工具缓存。此次不另设计一套 max_rounds 循环。

Phoenix 增加可解释的上下文元信息：画像绑定版本、原文范围与数量、待处理引用、摘要覆盖范围、预取来源与索引水位、处境状态版本、压缩原因、实际请求/工具失败。记录状态提案、提交差异及关联事件/行动回执，便于定位为何发生变化；不要求输出隐藏思维过程。业务页面区分未完成处理、主动等待和执行失败，不把失败显示成人物不想说话。

## 12. 实施顺序

1. **连续对话与输入状态**：明确消息处理契约，替换两小时硬窗口，接入导入历史前缀，去重 trigger/window/collaboration。先验证 Director 确实读到正确原文。
2. **摘要和历史回查**：持久化覆盖区间，常规回读，提供按引用读取工具；恢复时不从头丢失对话。
3. **分支语义记忆闭环**：独立索引、outbox、预取、搜索覆盖状态与 memory_proposals，禁止污染原图。
4. **统一处境状态与表达任务**：新增版本化 SubjectiveState，将事项、评价、感受、应对和进展贯通；清理旧心理字段的双写可能，在正常 Director 决策内维护，贯通 PersonaActor、生活协商与行动结果反馈。
5. **重写 Director Prompt 并实跑**：基于已经打通的数据契约写规则，不先堆 Prompt；用 Phoenix 检查真实输入和行为。

每阶段保持现有同级通信、计划生成和体验页面可用。旧字段只作过渡读取，不凭 turn_id 生成虚假的语义话题，也不将旧 mood 字符串推导成丰富心理历史。

## 13. 最小验收

只写关键冒烟测试，不为此建立大型评测平台：

- 隔夜继续“昨天说的那个”，近期原文或可回查摘要仍可用；时间间隔不自动关闭关切。
- 多条未处理消息及超出 16 条的连续聊天没有静默丢失；延迟回复不重复消费或漏回。
- 用户说“我明天面试”，主体保持 user；Director 的理解不写成目标人物工作事实。
- 更早的分支约定可语义召回，且不能检索到其他分支记录。
- parked/resolved 关切可重新打开；摘要失败、索引延迟明确可见。
- Actor 失败不会形成“已回复/已承诺”；重试不重复写记忆或发送消息。
- DayPlan 未提交候选不成为经历；已提交模拟经历可影响当前理解，但不写回原始世界图谱。
- 进程恢复后关切、摘要、待处理输入和提交状态一致。
- 同一事项的新信息可改变评价与应对，旧状态不会每轮重置；没有变化允许不提交更新。
- 工作完成与疲劳缓解不混同，用户体谅不自动解除尚未完成的工作；克制表达不清空内部感受。
- 意向不等于行动，实际结果以提交回执为准；Actor 失败和任务重试不重复叠加情绪。
- 普通 Director 与生活协商读取同一处境版本；PersonaActor 不拥有独立心理写入路径。

真实体验验收另外检查：回复是否接得上、是否恰当利用人物理解、是否避免每轮询问与说教、是否能自然暂放再接续事情。使用第 5.3 节的连续变化场景观察同一人物如何随理解和行动结果变化，不把某个情绪词设为唯一正确答案。结构测试只能验证数据契约，不能证明人物行为已经自然或心理模型已经获得验证。

## 14. 本次明确不做

不添加独立话题判定或情绪 Agent；不以正则判心理和话题；不为全部闲聊建任务；不把人格标签变成确定性行为规则；不硬编码情绪分数或统一衰减率；不把 EMA 启发的 LLM 实现宣称为心理学验证过的原模型；不让摘要删除原文；不建设第二套追踪系统；不重做原始画像和图谱；不在本次设计文档任务中修改运行代码或重启环境。
