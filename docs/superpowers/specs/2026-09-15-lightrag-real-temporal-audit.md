# 真实 chunk 映射与混合召回验证

日期：2026-09-15。结论：时间约束检索适配在真实资产回放上可行，但当前资产映射和全局描述隔离尚未达到生产要求。

## 数据与安全边界

读取共享目录中的数据库，使用 SQLite `mode=ro`，选择项目 e089f2fe-b7de-4988-a399-019e10b22b78 当前 active Publication 对应的图谱 1400178b-8e4a-468d-afd1-8e7c12d7aeec。

实际载入 380 个 chunk、GraphML 和三种向量文件到内存。图谱来源裁剪只发生在内存副本，没有初始化可写 LightRAG 实例；运行前后五个源文件 SHA256 完全一致。没有模型调用、真实资料修改或新建分支。

## 1. 映射验证结果

| 项目 | chunk 数量 |
| --- | ---: |
| 全部 | 380 |
| 重放建图清洗并通过完整 Bundle 文本一致性、chunk 唯一位置校验 | 200 |
| Bundle 重建文本仍不一致，拒绝猜测位置 | 154 |
| Bundle 已可重建，但 chunk 不是唯一可定位子串 | 26 |

严格映射覆盖率为 52.6%。这不是“原始消息丢失率”，而是当前实验能否准确证明每个 chunk 对应的完整消息范围。

实际发现：

- 现有 `_matching_indexes` 用数据库原文渲染行匹配，但建图调用 `build_clean_world_messages`，会清理技术载荷并处理引用署名；两者不是相同输入。376 个 chunk 所属 Bundle 不能用未经清洗的整段原文准确重建。**这不表示这 376 个 chunk 都完全没有可匹配消息。** 实测只有 4 个 chunk 没有任何未经清洗的完整行命中。
- 200 个可定位 chunk 中，192 个在头尾截断了消息。181 个的精确位置映射比现有完整行匹配找到更多消息。靠“命中了几行”无法完整证明 chunk 的时间范围。
- 154 和 26 两类残余缺口尚未逐个定位原因，不能断言只是空白差异或全部由某一版预处理造成。需要继续比较冻结 Bundle、当时清洗版本与 chunk 切分方式。

原型用已持久化的 BundleMessage 顺序建立消息字符区间；仅在重放真实清洗得到的整段文本与入库文本相同，且 chunk 子串位置唯一时，将字符区间交集映射到消息 ID。没有通过正则判断事实或时间语义。

## 2. 混合检索验证到底覆盖了什么

调用真实 LightRAG `_build_query_context(mode="mix")`，完整经过：

1. 实体向量召回与邻接关系扩展；
2. 关系向量召回与端点实体读取；
3. chunk 向量召回；
4. 实体、关系上下文截断；
5. 图谱关联 chunk 选择；
6. 三路片段合并去重与最终上下文组装。

三种向量候选集合在排序前按时间范围过滤，图的节点、边和 source_id 使用请求局部视图。采用既有向量的实际余弦排序，不预先指定返回哪些命中。

具体候选数量（排名之前）：全量为实体 704 / 关系 780 / chunk 380；before 为 290 / 285 / 100；after 为 264 / 246 / 99。实体与关系均实际经过 `Vectors.query` 中的先 allowed 过滤、再矩阵选择、最后余弦排名，并非只有 chunk 路径受限。实现是原型自有只读适配器，不是已经上线的 LightRAG Nano 存储改动。

以三个不同的真实 chunk 向量作为输入，分别运行全量/前段/后段范围，以及 WEIGHT/VECTOR 两种关联片段算法，共 18 次回放通过。VECTOR 路径实际调用 `get_vectors_by_ids`，不是悄悄全部落回 WEIGHT。

测试边界是可定位消息集合的中间时间 2026-04-30 09:58:08（沿用存储时间值，非新建/批准的用户起点）。前段允许 100 个 chunk，后段 99 个；一个跨界 chunk 和其他未映射 chunk 不进入限定范围。12 次限定范围回放最终返回 chunk 均无越界；另外 6 次为全量基线。

## 3. 完整上下文仍有缺口

即使 source_id 已裁剪，LightRAG 仍会把节点和关系的全局合并描述装入最终上下文。前段候选图中有 160 个节点的原始来源包含范围外 chunk，后段有 148 个。这个计数是**描述污染风险**，不是逐条语义验证出的未来事实泄漏数量。

因此只能说“返回 chunk 范围正确”，不能说“整个模型上下文无未来信息”。正式实现必须把全局描述明确隔离为跨期线索，或者不向受限 Runtime 返回它；不能用裁剪 source_id 后的引用给原始全局描述制造历史来源背书。

实体/关系的既有向量也未还原到历史版本，因此候选内排名仍可能受后期语义影响。结果应解释为“来源约束的图谱辅助定位”，不是历史图谱或历史 embedding 还原。具体接线和能力分层见 `2026-09-15-lightrag-temporal-retrieval-adaptation-design.md` 第 1.1、4.2、6.2 节。

## 4. 本实验没有覆盖

- 自然语言关键词抽取和 embedding 服务：使用真实已存向量回放，因此不证明用户问题的语义召回质量。
- HTTP sidecar、aquery 缓存及最终回答模型：调用的是完整混合检索上下文构建函数，不是整个供应商调用链。
- 真实 token 额度与性能：实验使用字节 tokenizer 和较大上下文额度以观察三条路径，不是生产参数基准。
- 跨界片段重新 embedding、残余映射修复及实体描述语义重建。

## 5. 下一步的实际阻塞点

1. 建图时保存精确的消息/清洗文本/chunk 字符区间映射；存量先回填能证明的部分，剩余明确标缺口。不能把当前 52.6% 当作足够的全量能力。
2. 在 sidecar 实装请求局部的时间检索视图，覆盖三路候选过滤及邻接扩展，缓存键包含图版本与边界。
3. 分开编译 Agent 的跨期线索和 Runtime 的受限材料，解决合并描述进入上下文的问题。
4. 完成上述接线后再做少量真实问题的在线查询，核对召回质量、缓存与错误处理，而不是现在宣布时间检索已经上线。
