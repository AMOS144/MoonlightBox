# 共享图谱与节点人物世界编译设计

日期：2026-09-14  
状态：节点编译、独立审核与纠正、节点发布、历史快照及分支准备入口已接通；实施和验收记录见 [时间检索改造文档第 12 节](2026-09-15-lightrag-temporal-retrieval-adaptation-design.md#126-节点审核发布到历史分支聊天)。真实节点仍须用户批准并等待分支准备成功；离线冒烟不替代模型质量验收。

## 1. 本次决定

只维护一份可查询的完整 LightRAG 图谱，用户选择起点后，复用现有 PersonWorld 七个栏目 Agent，编译“这个时刻的人物世界”。不再强制先编译并审核全量 Profile，也不为每个起点重建图谱或新增一个快照 Agent。

编译过程允许利用节点之后的原始记录：它们可以帮助解释早期材料、支持或修正判断、识别人物发生的变化。但产物必须描述所选时刻，不能把后来才发生的事件、形成的关系或获得的知识直接倒灌到那个时刻。

核心区分：**作者可以参考后来的材料来重建人物，角色不能因此知道未来。**

这不是严格的“只用当时数据做预测”。审核界面应明确叫作“结合完整记录重建该起点的人物背景”，不能宣称没有使用后续资料。

## 2. 与原方案的关系

本设计替代旧方案中“全量人物画像先发布，之后再按历史边界做纯前向切片”的强制流程。保留现有七栏目结构、心理模型、表达资料、统一 AgentLoopController、逐步纠正与图谱修改批准机制。

关联设计：

- `2026-09-10-person-world-profile-lived-world-redesign.md`：栏目结构继续有效，编译目标增加明确的起点。
- `2026-09-14-node-selection-investigation-agent-design.md`：继续调查和确认精确起点；不要求全量 Profile。
- `2026-09-14-unified-user-journey-and-frontend-design.md`：主流程顺序按本文调整，人物背景审核移到选择起点之后。
- `2026-09-04-agent-runtime-after-extraction-design.md`：OriginSnapshot 改为已审核节点画像和资料边界的运行时绑定，不再用最新背景冒充历史快照。

其他文档中冲突的旧流程不能继续作为实现依据。本文只修改这些决策，不撤销原有工具错误反馈、取消、恢复和事务保护。

## 3. 当前代码基础与实际缺口

### 3.1 已有且可以复用

- `node_investigation/agent.py`：统一 Controller 驱动调查，不直接依赖 PersonWorldProfile。
- `node_investigation/store.py`：保存资料版本、消息清单、候选、用户回答、精确边界及批准 hash。
- `node_investigation/tools.py`：顺序读原文、原文检索、图谱检索、候选维护。图谱不可用时可以继续读原文，但不是把不可用解释成没有经历。
- `world/person_world/coordinator_v3.py`、`section_agent_v3.py`：栏目协作和编译框架。
- `runtime_v1/initialization.py`：独立初始化执行上下文，仅把提交的初始状态连接到正常 Runtime。
- Runtime 的日程准备、独立节拍扫描、Director 与 DayPlan 协作及表达 skill。

### 3.2 必须补齐

1. 图谱“可查询”与全量画像“已发布”仍耦合，不能只删掉画像调用而不调整状态流。
2. PersonWorld 当前编译、恢复、发布基线主要围绕项目和图版本，必须增加节点作用域。
3. 原片段回查不总能精确定位消息：`chunk_matched` 和 `bundle_context_only` 不能混为一谈。
4. Runtime 现有 latest_profile 模式仍采用最新完整背景；它不能自动升级成历史模式。
5. 表达资料、世界记忆和工具检索也需要同一历史边界，不能只替换 Profile JSON。

此前起点契约修订已移除新创建请求中的旧 EventNode、训练模型和客户端时间参数；后端仍因历史编译缺失而拒绝创建。数据库迁移 `0061_branch_origin_boundary` 的上线状态需部署时核对，不能假设已经应用。

## 4. 新主流程

1. 导入记录，绑定用户和目标人物，确认需要处理的别名。
2. 构建完整图谱与原文索引。索引可查询后即可进入起点调查，不强制编译全量画像。
3. 起点 Agent 顺序调查，结合检索和用户解释形成候选。
4. 用户预览并批准精确边界，包括消息前/后或空档的明确时间。
5. 为该批准版本启动 PersonWorld 编译。七个 Agent 面向相同起点，允许分析前后资料。
6. 用户审核该起点的人物背景。需要修改时继续使用现有 Revision 对话流程。
7. 用户批准节点画像，创建分支并固定画像、图版本、资料边界与表达资料版本。
8. 准备日程、初始化 Director 的心理状态与未结束话题；成功后开放聊天。

全量画像可以保留为已有资产或将来的可选功能，但不再是新项目必须支付的编译成本，也不作为新节点编译的隐式默认答案。

## 5. 时间语义：不要只比较 timestamp

### 5.1 三种时间

| 概念 | 由谁确定 | 用途 |
| --- | --- | --- |
| 消息记录时间 | 原始消息和时区 | 确定消息在边界前还是后 |
| 内容所指时间 | Agent 结合完整上下文理解 | 区分回忆、当前陈述、计划、假设 |
| 结论适用时期 | Agent 判断，用户可纠正 | 判断能否写入目标节点画像 |

后端负责准确的消息顺序和边界归属；不使用关键词或正则决定“性格是否稳定”“关系何时成立”等语义。

边界不是只有 cutoff_at：同一时间可以有多条消息，消息之前与之后也不相同。以批准的资料版本、消息清单顺序、included_count、last_included_ref、first_excluded_ref 为准；时间用于日历解释，不能用 `timestamp <= cutoff` 代替精确消息边界。

### 5.2 后续材料的不同用途

| 材料 | 允许的用法 | 不允许的用法 |
| --- | --- | --- |
| 后来说“去年就在那里工作” | 辅助重建起点的工作情况 | 把说话日期当成入职日期 |
| 后来持续出现相似处事倾向 | 支持较稳定的人格理解，也检查变化 | 直接断言起点一定完全相同 |
| 后来说“最近才开始这样想” | 识别变化，缩小原判断适用期 | 把新想法倒填进旧节点 |
| 后来认识新朋友、换工作 | 作为后续变化留在调查审计 | 写成起点已有关系或工作 |
| 后来评价早先经历 | 帮助理解早期处境 | 把后来形成的评价冒充当时想法 |

“后续验证”在产品和 Prompt 中应解释为辅助支持、修订与反例检查，不是实验意义的独立验证，更不是确定正确。后续材料无法消除所有歧义，Agent 可以给出清楚的暂定理解，不恢复逐条强证据门槛。

## 6. 编译输入、画像与运行时快照

以下为建议契约，字段名可随现有模型收敛，不要求另建一套平行实体。

### 6.1 编译作用域

```yaml
NodeCompilationScope:
  project_id: 后端绑定
  target_participant_id: 后端绑定
  investigation_id: 已批准调查
  boundary_hash: 批准版本
  dataset_version: 原始资料版本
  graph_version_id: 本次共享图谱版本
  cutoff_at: 带时区的精确起点
  timezone: 批准时区
  included_count: 前缀消息数
  last_included_ref: 最后纳入消息，可为空
  first_excluded_ref: 第一条排除消息，可为空
  mode: retrospective_node
```

客户端只选择调查、批准版本和用户选项；数据库 ID、来源绑定、时间转换等由后端注入，不让 LLM 填写内部参数。

编译身份由资料版本、图版本、目标人物、批准边界、Prompt/工具/状态契约共同决定。相同有效身份可以复用结果；不同节点不能共享成功检查点或栏目工作状态。

### 6.2 七栏目不改成第八个“心理栏目”

继续使用 identity、life_context、social_world、agency、practices、life_course、relationship_with_user。investigation 仍是审计层，不是人物事实。

固定细分字段和情境模块继续使用，新增的是面向节点的理解任务，而不是让 Agent 自由输出另一份聊天摘要：

- identity：重建当时的自我理解与性格倾向，后续材料可帮助理解稳定特征，也要识别转变。
- life_context：判断当时工作、学习、照料等模块；后来进入的状态不得倒填。
- social_world：重建当时已形成的社会关系和关系处境。
- agency：区分当时的偏好、目标与承诺，以及后来的改变或实现结果。
- practices：描述当时适用的活动规律，不把后来的作息当成始终如此。
- life_course：叙述截至节点已经发生的经历；未来转折只用于辅助调查。
- relationship_with_user：重建当时的互动方式与关系状态，不用后来的亲密或冲突覆盖早期阶段。

每个 Agent 可利用全量材料形成理解，不要求每个字段都找到明确自述。对于会显著影响角色行为的时间歧义，要保留待确认项或询问用户。

### 6.3 两种视图，不是两套画像系统

**审核视图**包含节点画像、相关原文、后续辅助材料、主要判断说明和待确认问题。可沿用现有字段来源/调查审计结构，增加材料与结论之间的用途说明。

**Runtime 视图**只包含适用于起点的人物理解及当时可用记忆。后续材料正文、未来事件列表和验证过程不下发给 Director。

投影规则必须由显式结构表达，不能靠删除包含“后来”的句子。适用性由 Agent 理解；后端只检查结构、边界引用和投影权限，不自行判断人格。

例如可以输出“在这一阶段，她倾向于用玩笑表达不满”，但不要把“因为六月分手时她说……”附在 Director 的背景中。完整理由在审核界面保留。

OriginSnapshot 是审核通过版本的冻结绑定与运行时投影，不需要再调用一个 Agent 重复生成 Profile。

## 7. 共享 LightRAG 的工具设计

### 7.1 编译时允许全量检索

保留一份图谱。栏目 Agent 可选择全量线索或请求重点查看起点前/后的材料；时间分类在回到真实消息后完成，不能承诺 LightRAG 本身提供精确时间过滤。

返回建议包含：

```yaml
RetrievalFragment:
  content: 召回片段
  mapping: exact_messages | bundle_context_only | unresolved
  boundary_relation: before | after | mixed | unknown
  messages: 原始消息及各自顺序、时间、角色、边界归属
  locator: 可继续定位或分页读取的引用
```

无法精确定位的片段必须标 unknown；Bundle 开头的上下文不能代替命中位置。跨节点片段逐条标记，不能拿最早一条消息时间给整个片段贴标签。大结果用分页和可恢复引用，不反复传整段 Bundle。

图谱实体描述和综合回答可能混合多个时期，只作为线索。Agent 使用这些线索定位材料并判断适用时间，不将图谱当前状态直接写成起点状态。

跨界片段分组按后续确认的新规则：完整归入 before，复用原 chunk 和向量，不排除、不为跨界另做裁剪重嵌入；仅纯后段 chunk 归 after。返回仍标记 mixed 和逐消息前后位置，因此 before 是检索分组而非“全部消息都在节点前”的承诺。七栏目可以完整理解场景，节点后的部分不因分组就变成节点前事实。细则见 `2026-09-15-lightrag-temporal-retrieval-adaptation-design.md` 第 6.3 节；旧实验的跨界排除结果保留为历史记录，不代表新规则已验证。

### 7.2 运行时不能原样复用编译权限

PersonWorld 编译允许回顾未来，不代表聊天工具也允许。历史分支的 Director、DayPlan、表达检索只能获得当时允许使用的消息以及本分支后来产生的信息。

第一版安全方式：共享图谱内部召回可以用于定位候选，但返回模型前按冻结消息清单重新读取并过滤原文；不向 Runtime 返回包含未来信息的图谱综合答案。若图谱返回无法定位的内容，则不给 Runtime 当事实使用，可回退边界内原文检索。

不要求重建图谱，也不应为填满结果而把全量原片段漏进聊天上下文。召回受全量图谱影响是已知局限；这不等于角色获得未来原文。

## 8. 表达资料、记忆与初始化

- 节点 expression_profile 在本次节点画像编译中形成，不直接注入全量表达资料。
- 后来的材料可辅助理解早期表达方式，但只有后来出现的称呼、关系称谓和口癖不能无条件倒推。这是栏目/表达编译判断，不是词表硬过滤。
- `get_style_examples` 的可返回真实示例和表情包使用记录受节点前消息清单限制；媒资存在不等于目标人物在当时使用过。
- 世界记忆种子来自节点画像的 Runtime 投影；不把所有后续分析材料写入 MemoryRecord。
- 初始化 Director 阅读节点之前的连续对话，整理当时未结束话题、承诺和心理状态；不把后来的实际回复当成已经发生。
- 分支开始后新增对话、生活事件和记忆沿用现有 Runtime 规则，原记录中的节点后消息不会随虚拟钟推进自动导入为已发生事实。

## 9. Coordinator、工具和恢复的改动

本节是前段编译与后段复核的执行协议。不是先跑七个编译 Agent、再新建七个 Verifier；也不是在旧 Prompt 末尾加一句“请参考后面的聊天”。**同一个栏目 Agent 在同一个 Controller 执行中形成起点理解、主动检索后续材料、修订理解，最后提交自己的栏目。**

不增加新 Agent 类型。向现有 Coordinator 注入 NodeCompilationScope，七个栏目共享同一边界，在既有依赖关系下并行、按需读取其他栏目。

需要修改：

1. 栏目输入、检索回执和 Prompt 加入节点任务与回顾性分析说明。
2. 同节点栏目结果仍可共享；不同节点结果只能显式作为参考，不能被当成当前已确认结果。
3. 编译工作、检查点、工具缓存与审核会话均包含节点身份。取消/重试继续走统一 Controller 与 Job，不再增加外层重试循环。
4. 防止 Coordinator 默认加载项目最新 Publication 作为节点答案；基线必须匹配节点，或明确为空。
5. 失败保留已有栏目与调查状态，但不把缺失栏目伪报为完成；是否允许用户接受有缺项画像沿用审核策略。

### 9.1 在现有运行中的具体位置

当前 `section_agent_v3.py::run_section_v3` 已经把工具、`submit_section`、压缩器以及 `snapshot_work_state/restore_work_state` 交给统一 Controller。新能力接在这些扩展点，不在外面另写模型循环。

当前 Coordinator 通过 Send 启动栏目工作单元，并为同批次提供冻结的 `ModuleSnapshot`。这个机制保留：时间调查是**栏目内部的工作方式**；现有 draft/结合其他栏目重新考虑的阶段是**栏目之间的依赖处理**，两者不能混成两套“前段阶段/后段阶段”。

具体接线：

1. Coordinator 为各栏注入同一 NodeCompilationScope 和该栏已有工作，不注入项目全量最新画像作为默认答案。
2. `run_section_v3` 装配公共时间理解协议、独立栏目 Prompt、工具与工作摘要。
3. Agent 在原有原生工具回环内自主切换“建立理解、后续复核、回查前段”。Controller 不为这个切换额外启动模型或重置预算。
4. 工作通过工具保存到当前栏目 artifacts；Controller 检查点一并保存。栏目正常完成仍只调用 `submit_section`。
5. Coordinator 接收结果并更新下一批冻结快照。只有原有依赖阶段确实需要重看相关栏目时才再次运行，不因为“后段审核”给七栏整体翻倍调用。

### 9.2 起步：先建立该节点的解释基线

初始上下文包含：目标节点、本栏填写目的和字段、前后消息数量与时间范围、节点前最近连续对话、覆盖前段不同时期的少量原文入口、相关已接受栏目及本栏恢复笔记。

预读只放边界前材料，避免第一轮就把结局当成起点。它是起步顺序，不是永远禁止后段，也不要求读完所有前段消息才能检索。早期经历可通过时间分页和语义搜索扩展，不只靠节点附近几条消息理解整个人。

Agent 先写出一份可修改的本栏草稿：目前怎么看、适用时期、哪些地方拿不准、最值得用后续材料检查什么。这里允许依赖整体语境推断，缺少直接自述不阻止形成草稿。前段完全没有线索时也可明确记为未知，再询问后段是否包含对早期情况的回忆。

先有基线的作用是让后续检查知道在检验什么，而不是让后端证明每条理解都有合格证据。

### 9.3 后段：围绕判断查，而不是再总结一遍后半段

Agent 从草稿中挑会影响角色行为、存在歧义或可能变化的理解，提出能区分不同解释的问题。不要机械地给每个字段各检索一次，也不要只搜索支持自己的词。

例如前段推断“她反感别人替她安排工作”，后段可调查：她何时接受过他人安排、什么条件下不满、是否换岗后才改变、她是否回顾过早期处境。目的不是把后段所有工作消息重新总结，而是理解这一倾向的条件和时期。

查询后续材料时，优先从节点后较近时期寻找延续或变化，再按需要扩展更远时期；没有材料时可直接跳转相关回忆。无需规定统一的几天或几个月窗口，不同栏目的变化速度不同。

后段复核得到以下之一：

- 保留：后续材料与前段理解相容，没有发现需要修改的地方。
- 缩小：不是普遍性格，而是对某个人、某类任务或某段时期的反应。
- 修订：前段有另一种更合理的解释。
- 区分变化：节点时是 A，后来成为 B；只把 A 写进起点画像。
- 无法判断：材料无关、太少、定位失败或解释仍有分歧；保留暂定理解或未知，不强行制造验证结果。

后段发现新线索时，Agent 可以回到前段查对应场景，必要时再次查后段；不是强制单向的两遍扫描。若节点后没有任何消息，直接记录“无后续材料”，正常完成前段编译，不报错。

### 9.4 七个 Agent 分别怎样执行

| 栏目 | 前段先理解什么 | 后段具体怎么检查 | 最终怎样修改起点产物 |
| --- | --- | --- | --- |
| identity | 当时的自我叙述、角色认同，Big Five/MBTI 等框架下的暂定倾向 | 找相似选择在不同情境中的延续、明显反例、自述变化及人生转折；区分环境要求与个人倾向 | 修订维度描述及情境范围；不把成熟后的自我评价直接写成早期认同 |
| life_context | 当时适用的工作、学习、照料等模块，任务、资源、限制与感受 | 查后续对早期处境的回忆，以及入职、离职、搬迁、毕业等变化的发生时期 | 补全当时模块；把后来才开始的模块排除，时间模糊处明确说明 |
| social_world | 当时有哪些关系、互动位置、亲疏与支持/冲突 | 查后续称呼指代、共同经历回忆、初次认识与关系变化；同名不自动当同一人 | 澄清关系身份和当时状态；不能因为后面亲密就把早期写成亲密关系 |
| agency | 当时偏好、价值取舍、SDT 动机、目标和承诺 | 查后续选择、放弃、反例、理由与“后来才改变”的表达 | 区分原有动机与后续改变；目标后来实现不等于起点已实现 |
| practices | 当时反复活动、时间安排及所处工作学习模块 | 比较后续活动是否继续，是否随岗位、假期、居住状态改变；回查早期是否同一阶段 | 提炼当时规律及条件，不把后来的班次或偶发活动倒填 |
| life_course | 节点前已发生的经历和转变，各阶段的先后关系 | 使用后续回忆澄清早期事件、主体与发生时期；区分后来发生的转折 | 补充真正发生在节点前的经历；未来经历留在审计，不进入当时人生叙事 |
| relationship_with_user | 当时的相处方式、称呼、期待、矛盾、关切和未结束互动 | 查后续对早期相处的回顾、沟通修正与关系变化；区分当时表现与后来评价 | 修订当时互动理解，不提前写入后续确认的关系身份、和解或分离结局 |

各栏 Prompt 必须写出这些具体调查任务，而不是共享一个抽象的“核查证据”段落。公共协议只维护时间边界、工作保存和角色知识隔离，各栏负责决定什么值得查、怎样理解、如何填写已有细分字段。

### 9.5 工具接口如何支持这个过程

尽量扩展现有工具，不增加前段/后段各一套同名功能。

| 工具能力 | 模型填写 | 后端绑定或返回 |
| --- | --- | --- |
| 原文读取/检索 | 问题或分页位置；`period=before/after/all` | 同一批准边界、真实顺序、消息前后归属；原文可精确过滤 |
| `search_world` | 调查问题；希望重点查看的时期 | 共享图谱召回，定位后的时间分类；明确 period 不是 LightRAG 原生过滤保证 |
| `get_current_profile_section` | 栏目 | 同节点当前批次冻结结果、版本和可用性；没有则明确未就绪 |
| 保存栏目工作 | 草稿更新、复核问题、已形成判断和下一步 | 绑定本栏、本次编译身份并持久化，不发布画像 |
| `submit_section` | 对应栏目结构及简短复核总结 | 参数错误回传模型修复；接收后终止当前栏目回环 |

图谱查询没有找到目标时期的片段时，返回已检查的定位范围和限制，不写“该时期没有事实”。模型可以改问法、扩大范围或直接读原文。后端不代填“已经验证”，也不根据查询次数决定验证成功。

保存工作优先扩展现有 artifacts/工作笔记能力；若缺少模型可调用的保存入口，只新增一个栏目工作工具，而不是引入新的调查实体。工具名和 schema 最终在实现时与现有工具目录统一。

### 9.6 持久化的工作内容

在本栏已有 artifacts 中保存紧凑状态，例如：

```yaml
temporal_work:
  focus: reviewing_after  # 进展提示，不是后端强制状态机
  draft: 按现有栏目字段保存的当前起点理解
  review_questions:
    - key: work_autonomy
      understanding: 她在工作安排上重视自主性
      question: 她是不喜欢被安排，还是只反感临时且不解释理由的安排？
      result: narrowed
      revision: 目前更接近后者；避免把它写成普遍不愿合作
      source_refs: 已读取材料引用，可有前段和后段
  unresolved: 仍影响产物的歧义
  next_action: 回查节点前两次任务调整的对话
```

这是可恢复工作，不是新增“Claim Verifier”结构。不会为每条心理判断要求一组 verdict、最低证据条数或跨场景计数。完整工具回执沿用 artifacts 缓存与引用；摘要保留当前判断、为什么修订、尚待解决的问题。

上下文压缩时必须保留 NodeCompilationScope、当前字段草稿、未解决复核问题、关键修订与下一步。不能只保留最近两次工具调用，否则进入后段后会忘记自己原先要检查什么。压缩后的原文可通过引用重新读取，不靠 Phoenix 回放恢复正常工作。

### 9.7 与七栏目协作如何相容

仍按 Coordinator 原有依赖阶段共享冻结快照，不让同批次 Agent 读取彼此写到一半的内容。

例如 life_context 通过后续回忆确定节点时尚在旧岗位，提交带节点归属的工作模块；practices 在下一次既有依赖读取中据此调整作息，agency 据此理解工作体验，identity 再综合这些情境。其他 Agent 不需要为同一个岗位事实各重做一遍相同调查，但可因不同问题主动回查。

共享的是“当前节点的结论、适用范围与可回查出处”，不是独立证据票数。某栏目引用另一栏的推断后，不能把它计算成又一次后续支持。

若复核导致模块发生实质变化，沿现有依赖记录标记受影响栏目待重新考虑，合并为一次必要的修订批次；不立刻重启正在运行的 Agent，不递归触发七栏无限重编译。新增一轮后若仍有分歧，应明确保留冲突或交给用户，不为追求所有栏目一致而无限互相说服。批次恢复和累计预算仍归已有 Coordinator/Controller/Job 管理。

### 9.8 提交与停止：不恢复僵硬调查门槛

Agent 在已能填写本栏、关键时间歧义已处理或明确保留、继续查询的价值较低时提交。后段检查应体现在任务目的和工作结果中，但不规定“至少 N 次工具”“每个字段必须验证”“必须找到反例”。

`submit_section` 检查已有字段结构、引用是否来自本次允许材料、时间用途标记是否完整等可修复参数问题。模型负责判断内容是否适用于节点；后端不得用词匹配替代它。审核 UI 展示该栏是“参考过后续材料”“无可用后续材料”还是“复核尚有问题”，不能从若干工具调用自动推断审核通过。

模型因网络或预算失败而未提交时，继续保留草稿和复核工作，栏目状态是未完成，不用缺省空对象冒充完成。恢复后从当前理解和下一步继续，不重新跑前段编译。

### 9.9 一个完整的单栏目回环例子

以 practices 为例，节点为 5 月 1 日：

1. 初始输入给出节点、节点前对话入口和已就绪的工作模块。
2. Agent 读取 4 月工作日场景，暂定“该阶段通常傍晚结束工作”，保存草稿；没有凭一条消息立即固定全年作息。
3. Agent 向后段检索“岗位或上下班安排是否发生变化，以及是否回顾此前作息”。
4. 读到 6 月聊天说“换岗以后终于不用等到七点了”。这既提示变化，也促使它回查换岗时间及 4 月提到的“结束”是下班还是离开某项活动。
5. Agent 回到前段重读相关上下文，修订为当时适用的具体安排；若时间仍不清楚就写范围或暂定，不编造精确时刻。
6. 保存修订和简短理由，调用原有 `submit_section`。Runtime 只得到起点安排；6 月换岗和原话留在审核材料里。

整个过程只有一个 practices Agent 的原生工具循环，可能来回查多次，但没有“先结束 Agent，再启动审核 Agent”。其他六栏按各自目的使用同样的运行机制。

## 10. 发布、纠正与图谱治理

一份共享图谱可关联多个节点画像，因此“项目唯一最新画像”不能继续承担所有分支的选择逻辑。

- 图谱版本仍是共享资产版本。
- 画像与审核版本增加节点作用域；批准一个节点不替换另一个节点的画像，也不改变已有分支。
- 分支固定引用用户批准的具体节点画像版本，不在聊天时读取项目最新 Profile。
- 用户纠正“这个节点的性格理解”通常只修改节点画像，不应自动改写共享图谱为全时期事实。
- 用户纠正真实消息主体、实体或关系时，才可能形成图谱 ChangeSet；沿用逐步理解、Profile Patch、Graph Patch 和最终明确批准。
- 图谱更新后标记相关画像可能过期，允许显式重新编译；不静默重绑已有分支。

需要沿现有 PersonWorldProfile、Publication、Revision 的存储方式扩展作用域和查询条件，而不是直接多塞一个字段后仍按项目查询“最新”。

## 11. 前后端状态和用户体验

图谱索引可用与画像发布必须拆开表达。优先在已有资产和任务上拆分就绪条件，不为展示再建一套万能 workflow 数据库。

对用户的流程变为：

| 页面 | 主体内容与下一步 |
| --- | --- |
| 人物资料 | 身份绑定、别名和索引进度；下一步调查起点 |
| 选择起点 | 原文、候选、问题和边界预览；确认后整理该起点背景 |
| 起点背景审核 | 明确起点日期；阅读七栏目，可展开后续辅助材料并纠正 |
| 分支准备 | 背景版本、计划、Director 初始化的真实状态 |
| 聊天 | 使用该分支背景，保留原历史边界 |

页面不反复要求用户重新选择同一个起点。切换节点时明确提示正在查看另一个版本；历史项目的全量背景保留可读，不把它伪装为某个节点的审核结果。

`journey.py` 不再把全量画像审核当作调查前置；`BranchCreatePage` 在节点画像批准且后端能力就绪后才开放创建。未完成编译、失败或取消时，有明确状态、错误和恢复入口，不能只返回永久 preparing。

## 12. 改动范围与工作量判断

这是**中等偏大的跨模块改造**：复用主要模型能力，但修改核心资产的作用域和主流程。不是只改几个 Prompt，也不需要重写统一 Agent Runtime。

| 模块 | 改动程度 | 主要工作 |
| --- | --- | --- |
| LightRAG 存储/建图 | 小 | 不按节点复制图谱；固定查询版本 |
| 世界构建任务 | 中 | 索引就绪后可调查，取消强制全量画像编译 |
| 节点调查 | 小 | 独立索引就绪接线，批准结果交给节点编译 |
| 检索与原文定位 | 中到大 | 精确边界标记、混合片段、未知定位、Runtime 输出隔离 |
| PersonWorld 七栏目 | 中到大 | 节点作用域、输入、Prompt、共享栏目、恢复与投影 |
| 画像发布与纠正 | 大 | 多节点版本并存，基线和发布查询不得串节点 |
| 分支快照与初始化 | 中 | 固定批准版本、时间、记忆及表达资料边界 |
| AgentLoopController | 原则上不改 | 使用已有契约指纹、检查点、取消、工具错误反馈 |
| 前端 journey 与审核 | 中 | 审核顺序、节点归属、编译状态及创建交接 |
| 数据迁移与冒烟 | 中 | 保留旧资产；验证新边界与旧分支不受影响 |

具体工时需要在确认存储迁移方案后估算，不能依据“复用 Agent”就承诺很小改动。

## 13. 成本、质量与行为影响

### 正面影响

- 无需每个节点重建昂贵图谱。
- 新用户只为实际选中的节点编译，不必先支付全量画像成本。
- 可利用后续记录解释隐晦的早期信息，更适合聊天资料而非规范事实数据库。
- 节点背景、表达方式和当前关系有明确归属，不再所有分支共用同一套最新人物理解。

### 成本与局限

- 每个新节点仍有画像编译成本；回顾前后变化可能增加检索次数，不能保证每次比旧编译更快。
- 全量图谱会使检索偏向显著的后续事件，需要在 Prompt 中要求理解时期变化，并用原文定位工具支持。
- 人格重建仍可能存在事后偏见，工具能保证材料位置，不能确定性证明心理判断正确。
- 后续新导入材料可能改变对旧节点的理解；旧分支保持冻结，新审核版本由用户选择是否使用。
- 存量纠正可能写成无时间限制的陈述，需要复核作用域，不能自动套到所有节点。

## 14. 分阶段实施与安全迁移

### 第一阶段：作用域与状态拆分

定义编译身份、扩展节点画像/审核作用域，拆开索引就绪与画像发布；保留旧数据读取。节点选择不依赖全量 Profile。此时历史创建仍关闭。

### 第二阶段：节点编译与检索

完善时间标注和定位，接入 Coordinator 与七栏目 Prompt，形成审核视图与 Runtime 投影。用一个明确节点完成真实编译审阅，检查是否混入未来事件。

### 第三阶段：审核到 Runtime

批准节点画像后生成快照绑定，接通表达资料、原文、记忆、DayPlan 和 Director 初始化。只有这一步闭环后，才打开新创建入口。

### 第四阶段：流程切换与存量兼容

前端调整顺序，旧全量画像保留只读或可选入口。旧 latest_profile 分支标识不变，不自动裁剪聊天、改时钟或重跑初始化。新导入任务使用新流程，已排队旧任务需要明确恢复/取消策略，不能静默按新语义继续。

迁移前备份数据库；图谱 workspace 和原始资料不删除。回滚时停止新编译和创建，恢复兼容版本读取，不把新式节点分支强行转换成旧模型引用。

## 15. 最小验收

测试以少量契约和流程冒烟为主，不用大量心理结论快照测试。

1. 无全量 Profile、但索引可查询时，可以启动并完成起点调查。
2. 同时间消息的 before/after、空档时刻、跨节点片段和无法定位片段分类正确。
3. 后续回忆可支持早期状态；后续新工作、新关系、未来结果不会直接进入角色的起点记忆。
4. 编译器可读取后续材料，但 Runtime 工具、风格示例、表情包候选和初始化历史不能越界。
5. 两个节点使用同一图谱，产生独立画像、审核状态和检查点，不互相覆盖。
6. 取消和恢复保留相同节点进展，改变边界或图版本不复用旧成功结果。
7. 用户批准后准备计划和初始化，失败可见；未批准或未准备好不能聊天。
8. 旧分支的聊天、时钟、训练资产和背景不被迁移改写。

真实模型冒烟应在明确的测试节点执行，通过 Phoenix 检查实际工具输入输出和错误；质量由用户阅读节点画像确认，不能只把模型调用成功当成重建正确。

## 16. 完成定义

用户不需要先审阅全量人物背景，可以从共享图谱调查起点，编译和审核该时刻的画像，并进入一个时间、背景、记忆和表达资料一致的新分支。编译能够利用后续记录辅助理解，但角色不会因此提前获知未来事件。

达到以上闭环，才算补齐快照缺口；新增一个 snapshot_mode 或让页面按钮可点击，都不算完成。
