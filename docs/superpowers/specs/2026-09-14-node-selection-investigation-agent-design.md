# 节点选择调查 Agent 设计

日期：2026-09-14  
状态：节点调查前后端已实现并通过离线冒烟与构建；体验环境迁移、重启及真实模型质量验收另行执行。  
范围：重新设计节点调查、候选定位和用户确认；不沿用现有粗糙事件节点发现与评分逻辑。

## 1. 目标与边界

节点选择 Agent 帮助用户梳理目标人物与自己的经历，找出值得重新开始的具体时刻。它使用连续原文、普通 RAG 和 LightRAG 调查，也允许用户补充聊天之外的经历。

它需要完成：

- 从记录开头按时间推进，避免只找到检索最容易命中的几个片段。
- 追踪跨窗口经历，通过远处的相关材料完善理解。
- 逐步展示、修订候选，而不是全部运行完才一次性交付。
- 对会改变节点判断的疑问主动询问，用户回答后继续原调查。
- 将用户选中的候选定位为可确定的分支边界。

本阶段不做：

- 不复用旧事件提取流水线、重要性打分、固定关键词命中规则作为候选发现器。
- 不从聊天空档直接断言旅行、争吵、互删或关系中断。
- 不自动创建分支，不自动修改已发布人物画像或 LightRAG 图谱。
- 不编译历史节点的 PersonWorldProfile；下一阶段另行实现。
- 不把最新画像和完整图谱包装成“截至历史起点”的人物背景。

旧 EventNode 的字段、页面和处理接口不是新方案必须遵循的约束。历史数据是否只读保留、旧入口如何退役，实施时单独核对依赖；本文不授权直接删除历史数据。

## 2. 核心区分：重要经历与分支起点

经历描述“发生了什么”，起点回答“从哪一刻开始另一种走向”。二者不能合并成一个时间点。

例如，一次共同旅行可以关联几个起点：提出旅行之前、商量行程时、出发前最后一段交流、回来后关系变化时。一次恢复联系也可能关联删除前最后一次交流、聊天空档中的用户确认时刻、重新联系后的第一段交流。

因此：

- 一个候选经历可以提出多个起点选项。
- Agent 解释各选项对应的当时处境和可能继续发展的方向，不预测必然结果。
- 用户最后选择的是具体起点，不是仅勾选一个经历标题。
- 事件的发生时间与记录中提到它的时间分别保存，不能互相替代。

五月回忆四月旅行的消息，可以作为调查线索；五月这条消息本身不等于旅行发生的时刻。

## 3. 在项目 workflow 中的位置

前置条件是导入记录可读、参与者绑定可用，以及配置启用的检索资产有明确准备状态。不能在索引尚未准备好时把查询失败当成“没有相关经历”。

流程为：

1. 用户启动节点调查，或提供想寻找的经历。
2. 节点 Agent 建立记录概览，顺序阅读并展开调查。
3. 候选和调查进度逐步呈现在页面中。
4. 必要时提交问题，暂停等待用户；收到回答后继续。
5. 用户选择候选起点，后端解析并展示确定边界。
6. 用户确认边界，产出节点选择结果。
7. 后续 workflow 才启动历史背景编译、DayPlan 准备和 Director 初始化。

Agent 是 workflow 中的正式节点，使用统一 AgentLoopController、LangChain 工具和 LangGraph 检查点。不得为它再写一套模型调用循环、网络重试或自建执行 Trace。

节点调查可以使用整份历史中的后续回忆来发现早期经历，但这属于回顾性调查。这样的材料不能自动进入后续历史分支画像；后续编译仍须执行自己的时间可见性规则。

## 4. 调查流程

### 4.1 先建立材料概览

后端提供：记录版本、时间范围、消息数量与分布、参与者绑定、已知导入缺口、可读窗口、检索准备状态。

概览用于导航，不产出人物事实。长时间无消息只表示当前材料存在空档，原因可能是线下相处、其他渠道联系、记录缺失、导入不完整，也可能是关系变化。

### 4.2 顺序阅读是覆盖主线

默认从最早记录开始，分批读取连续窗口，不逐条调用模型。用户明确要求从某一段调查时，只报告该范围的覆盖情况。

- 后端负责消息排序、分页游标和有界返回。
- 窗口保留发送者、时间、消息类型和原文引用；缺失媒体语义如实表示未知。
- 模型可以展开窗口前后文；分页边界不是事件边界。
- 一段经历跨越多个窗口时继续跟踪，不因翻页重新创建候选。
- 顺序覆盖游标与检索阅读范围分别记录。检索到了末尾一条消息，不代表已经读完中间记录。

推进不要求每个窗口必须发现事件。没有值得分支的经历时可以继续阅读，不为展示进度凑节点。

### 4.3 围绕线索深入调查

三类资料的职责：

| 资料 | 主要作用 | 注意事项 |
| --- | --- | --- |
| 连续原文 | 理解参与者、指代、互动过程和前后变化 | 相邻消息不一定是问答；不能仅凭发送者判断事实主体 |
| 普通 RAG | 找相似说法、同一经历的其他片段、较远处的上下文 | 命中结果要能定位回原文；语义相似不证明属于同一事件 |
| LightRAG | 调查人物、地点、活动及关系，发现跨片段联系 | 生成总结是线索，不等于已经确认的经历或时间边界 |

Agent 根据当前疑问选工具，不强制每个候选调用所有检索，也不要求固定轮数。反复查询没有进展时，使用统一循环的无进展保护，不另加“没有新增证据就不能继续”的业务硬规则。

### 4.4 持续维护调查工作状态

可恢复状态至少包含：

- 已绑定的材料版本和调查范围。
- 顺序阅读游标、已读区间及主动跳过的区间。
- 当前正在跟踪的经历及其时间线。
- 候选引用与当前修订版本。
- 尚待查清的问题、已经尝试的调查方向和下一步工作。
- 用户已回答的问题、纠正与补充，以及待回答问题。

上述内容是业务工作状态，不是模型隐藏思维。进程重启时恢复已有材料和草稿；上下文压缩时保留工作摘要及可回查引用，不重新调查全部原文。

## 5. 聊天之外的重要经历

### 5.1 有间接线索

出发前讨论行李，几天后回忆民宿，足以让 Agent 调查“共同出行”的可能性，不必等到明确出现“我们一起旅行了”。

Agent 可以综合片段提出暂定经历，但应区分哪些是原文信息、哪些是自己的理解。对时间、参与者或事件归属拿不准时继续查找或询问用户，不把每个细节都补成确定事实。

### 5.2 有转变，但原因不明

长时间空档后出现重新联系、解释过去或道歉，可以形成待调查线索。不能直接命名为“互删后复合”。

提问应先陈述可见现象，再开放询问原因，例如：

> 这段记录中间缺了一段，恢复聊天时提到了重新联系。中间发生过什么？也可能只是记录不完整。

“旅行”“互删”“争吵”等是本文说明情形，不是固定事件题库，也不是必须主动套用给用户的选项。

### 5.3 完全没有可见线索

Agent 无法保证发现完全没有记录的线下经历。前端应允许用户随时补充经历、时间范围或直接圈选消息。

用户补充进入本次调查材料，保留来源和原话，不伪装成原始聊天。用户纠正可以改变候选解释，但不会通过本流程直接更新 LightRAG 图谱。

## 6. 询问用户与恢复

### 6.1 什么时候暂停

仅当疑问会实质改变下面一项时主动询问：

- 经历是否发生，或是否值得保留为分支候选。
- 涉及的人物和关系。
- 大致发生时间与应定位的原文范围。
- 不同解释会导向明显不同的分支起点。

其他小疑问记入工作状态，继续调查。每次只提出一个会影响判断的核心问题，不把全部待查问题一次抛给用户。

### 6.2 暂停是正常交互，不是失败

Agent 用提交工具交付结构化问题和必要的工作状态，统一循环返回 waiting_for_user，workflow 保存检查点并结束本次后台执行，不保持 Worker 占用。

用户可以回答、纠正前提、表示记不清或先跳过。后端绑定问题 ID、问题版本和回答请求幂等键；不让模型生成这些后台标识。旧问题的回答不能覆盖已修订的新问题。

收到回答后，workflow 从现有调查状态继续，向 Agent 提供回答及其对应问题，不从头重新扫描。Agent 可以根据回答进一步追问，但不能机械要求用户反复确认已明确的内容。

跳过问题后，候选保留未确定内容；没有确认的解释不得自动升级为已确认事实。

### 6.3 用户在调查期间补充信息

补充先保存，单个调查任务只保留一个活动执行者。在下一次模型调用前补入未读补充，不为每条回答启动并行调查，也不因补充到达取消已经发出的模型请求。

候选修订及最终选择通过版本检查避免覆盖新修改。用户明确纠正了某项内容后，旧执行产物不能静默覆盖；冲突返回可理解的工具错误，继续原调查或提示用户。

## 7. 候选与边界的语义结构

下列是设计上的字段责任，不是最终数据库表定义。尽量复用现有任务和检查点设施，避免为执行过程新增多套实体。

### 7.1 候选经历

候选包含：简短标题、经历概述、大致发生时间或范围、与分支选择的关系、相关原文、用户补充、暂定理解、剩余疑问、起点选项。

候选编号、修订版本、创建时间由后端生成。模型更新时选择已有候选引用，不重复生成同一经历。Agent 可以合并或排除重复候选，但保留变化说明；不能悄悄删掉用户选中的内容。

建议状态：调查中、待用户回答、可供选择、已排除。用户选择与边界确认是另外的明确动作，不等同于 Agent 把状态设为“可供选择”。

### 7.2 消息边界起点

模型选择真实消息引用，并说明分支从消息之前还是之后开始。后端据此绑定时间、稳定消息顺序及包含/排除语义。

同一秒多条消息不能只靠 timestamp 区分。确定结果要绑定记录版本和稳定顺序；不得由模型填写一个看似精确的时间替代消息定位。

### 7.3 用户确认的时间起点

经历发生在线下或聊天空档时，允许使用用户确认的时间起点。

如果只有“那周旅行回来之后”，先保留时间范围，并展示附近可选消息；不能自动补成某天零点。用户选择可确定的时刻或消息边界后，后端才生成正式边界。当地时间按项目明确的时区解释，歧义需要确认。

### 7.4 最终选择结果

至少交付：选中的候选及版本、起点类型、原始定位依据、已解析的确定边界、记录版本、用户确认信息。

确认时后端检查候选是否被修改、消息是否存在及材料版本是否仍一致。未解析的模糊时间不能进入正式分支创建。

## 8. 工具职责与参数边界

工具名称以下为建议名，实施时按统一注册约定落地，不另造工具协议。

| 工具 | 模型负责 | 后端负责 |
| --- | --- | --- |
| get_record_overview | 无必填参数 | 当前材料版本、范围、分布、缺口与准备状态 |
| read_next_messages | 已有游标；可选读取量 | 连续顺序、真实消息、分页与返回边界 |
| read_message_context | 已有消息引用；可选展开范围 | 原文定位、身份、时间与可读范围 |
| search_source_messages | 要查清的问题；可选召回量 | 当前原文索引、引用还原、检索状态 |
| search_world | 当前调查问题 | 绑定图谱、检索策略、来源引用 |
| save_investigation_work | 当前理解、未解决问题、下一步调查方向 | 保存工作状态；已读游标从实际读取行为取得，不接受自报全部读完 |
| upsert_node_candidate | 候选内容、已有候选引用、起点建议、修改理由 | 新编号、版本、消息定位检查、草稿变化通知 |
| submit_investigation_turn | 提问或本轮调查完成；对应问题/概览 | 接受回执、waiting_for_user 或完成状态、工作流暂停与恢复 |

候选逐个保存不结束 Agent 调查。只有明确的提交工具接受回执才能结束本次 Agent 回合。

用户回答、候选选择与最终确认由前端/API 提交，不给 Agent 一个能够代替用户批准的工具。Agent 只能建议边界，不能通过填写 confirmed=true 获得批准。

工具 Schema 由 LangChain 单独注册。Prompt 不重复整份 Schema，不要求模型填写项目 ID、图版本、时间戳编号、状态 hash、授权或执行次数。

错误统一走已有 tool_error 回执：

- 错误消息引用、游标、参数：给出字段位置和修正方向。
- 候选版本冲突：提示读取最新候选，不覆盖用户修改。
- 正常无匹配：返回 empty；不能与检索不可用混淆。
- 服务故障：由 Controller 按现有请求策略处理。
- 等待用户：正常提交状态，不报错、不自动重试问题。
- 取消或整任务额度耗尽：明确终态，保留草稿，不自动重新创建任务绕过预算。

## 9. Agent Prompt 的设计方向

行为 Prompt 独立维护，工具说明放在工具定义中。它需要指导 Agent：

- 找可以重新开始的时刻，不收集所有聊天摘要。
- 按时间覆盖材料，同时允许围绕线索跨时间回查。
- 综合间接表达推断经历，不把明确自述设为唯一入口。
- 分清谁说、对谁说、事情涉及谁，以及发生时间和提及时间。
- 把空档和变化当作疑问，不直接填入戏剧化情节。
- 将候选写成用户能理解的具体经历和起点选项，解释为什么值得选择。
- 有关键疑问时停下来问；没有材料可判断时允许未知。
- 接受用户补充，修订已有候选，不不断产生重复卡片。

不预设固定“重要事件类型表”，不要求每个时间段必须产出节点，也不靠给模型一套抽象分数来代替节点选择理由。

## 10. 前端交互

### 10.1 页面布局

左侧为候选列表，逐个出现并持续更新；右侧为当前候选详情、原文定位和调查对话。

候选卡片展示标题、时间或范围、建议起点摘要、状态。展开后展示经历理解、为什么值得分支、起点选项、相关原文、用户补充及待确认问题。

页面始终可添加用户补充；遇到 Agent 提问时，在对应候选下显示问题并聚焦回答区域，允许回答、跳过或纠正前提。

### 10.2 工作流程可见，但不展示隐藏推理

展示真实业务动作与简短调查说明，例如：已读到某月、正在查询出行讨论、找到相关片段、更新候选、等待回答。

不把模型隐藏思维原样输出，也不只显示无意义的 loading。原文展开与候选修改记录使用户能够核查调查过程。

这些是 UI 所需的业务状态和有界活动记录，不另建 AgentRun/Step/ToolInvocation 执行账本。真实模型调用、工具耗时与故障分析继续使用 Phoenix。

### 10.3 增量更新与稳定页面

- 使用稳定候选 ID 和修订版本更新卡片，更新不追加重复节点。
- 订阅有序的候选/状态变化；断线后先校准最新快照，再接续增量，重复事件可去重。
- 不因轮询或订阅更新重建整个页面，不重置当前候选和原文滚动位置。
- 新候选默认提示出现，不抢走用户正在查看的候选。
- 问题等待状态刷新后仍在；重复点击回答不会触发两次调查。
- 显示实际覆盖范围、跳过区间及剩余疑问，不把局部检索冒充完整调查。

实时传输可以沿用项目已有机制；若需要新增 SSE，应仅承载上述业务增量，不能把 Phoenix 当成前端状态数据库。

## 11. 完成与用户选择

调查完成不要求每个疑问都解决，也不要求一定找到候选。完成概览应明确已覆盖范围、主要候选、未解决疑问和用户主动跳过的部分。

用户可以在完整调查结束前选择已经准备好的候选；是否继续后台调查应作为明确的界面选择，不能选完节点后仍无提示地持续消耗模型。

用户确认边界后，输出不可歧义的选择结果。当前阶段可以交付这个结果，但在历史画像编译尚未完成前，不得声称历史分支已准备好聊天。

## 12. 验收场景

以少量冒烟测试和人工体验验证核心行为，不追求逐字匹配 Prompt 产物。

1. 普通连续记录：顺序推进、逐个保存候选，跨窗口不重复创建同一经历。
2. 旅行间接线索：能关联出发前后材料；没有证据的细节保留为暂定或询问。
3. 聊天空档：不自动解释为互删；用户说明记录缺失后，修正候选而非坚持原猜测。
4. 用户补充线下事件：保存为用户来源，能定位附近消息或要求确认时间。
5. 后来回忆早期经历：发生时间与消息时间不混淆。
6. 询问、刷新、回答、重启：恢复原问题和调查进度，不重复发问、从头扫描或占住 Worker。
7. 同秒消息与前后边界：最终确认能明确包含哪条消息。
8. 检索不可用：页面与 Agent 收到真实错误，不生成“没有经历”的结论。
9. 候选持续修订：当前选择、滚动位置稳定，旧版本回答和修改不能覆盖新内容。
10. 任务失败或取消：草稿保留、状态明确，不自动新建任务绕过整任务预算。

## 13. 后续实施顺序

先确定候选和起点边界契约，再落实统一运行时的工具、工作状态与问题提交；随后接前端增量候选、原文查看和用户回答，最后打通节点确认结果。

实现节点选择后，再单独设计“确定边界 → 历史可见资料 → 七栏目画像编译”的流程。节点调查中看到的未来回忆和最新图谱理解，不能直接进入历史分支背景。
