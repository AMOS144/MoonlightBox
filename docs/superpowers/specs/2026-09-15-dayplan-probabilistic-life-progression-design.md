# DayPlan 随时间推进的概率生活机会设计

日期：2026-09-15。

状态：已落实为正式 Runtime 路径。生活概率推进是必需能力，不设置启停开关；下文参数为第一版实际默认配置，效果仍需真实体验检验。

本文替代[旧模拟生活事件设计](2026-09-12-dayplan-simulated-life-events-design.md)中的概率机制、影响预算、冷却、有效期、离线处理和强制协商规则。共享通信沿用[2026-09-15 消息交付实现](../implementations/2026-09-15-runtime-peer-message-delivery.md)，Agent 内部仍使用统一 AgentLoopController。

## 1. 核心目标：骨架逐渐成为一天，而不是提前写好一天

DayPlan 提前制定工作、学习、用餐、休息、出行等骨架安排。它表示人物原本打算怎样生活，不是未来必然发生的事实。

随着虚拟时间推进，后端随机给 DayPlan 一个**当下的生活变化机会**。模型收到的机会只有方向和强度；具体发生什么、是否值得发生、怎样影响人物及日程，由 DayPlan 自己判断，必要时与 Director 商量。

三条不能混淆的时间语义：

1. **计划**：将来打算做什么，可以调整。
2. **机会或候选**：此刻可以考虑怎样的变化，尚不是事实。
3. **已发生经历**：已经在分支中提交发生的内容，后续对话可以回顾。

上午六点可以知道下午计划工作，不能知道下午一定会吵架。下午实际到来、机会命中后，才考虑当时是否发生一次互动；争执、化解或没有后续，不能在早晨预写。

概率机制的目的不是制造麻烦、强迫聊天或完成事件数量指标，而是让骨架在时间中逐渐丰满。

## 2. 职责与权限

| 组件 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Scheduler | 根据虚拟时间发现到期检查，持久化抽样，安排现有 Job | 不编剧情，不调用模型判断情绪 |
| OpportunityPolicy | 计算当前时段命中概率，命中后抽方向和强度 | 不规定事件耗时、日程影响、人物最终反应 |
| DayPlan | 结合当前处境选择具体变化、放弃机会、调整安排、推进后续 | 不假装用户已经参与，不直接向用户发聊天 |
| Director | 理解人物当下关切、感受和选择，按需参与讨论，决定行动与表达 | 不是所有机会的审批人，不替 DayPlan 编制完整日程 |
| Executor | 检查结构及真实状态冲突，原子提交经历、计划与通知 | 不靠正则判断故事好坏，不以每日事件额度替模型决策 |

不增加新 Agent、远程 A2A 服务、消息中间件或独立 Agent 循环。当前表达沿用 Director 的 speaking skill，本设计不接回 PersonaActor 或 LoRA。

## 3. 概率的三个独立维度

### 3.1 触发概率：这个时刻是否给一个机会

第一版每 **20 分钟虚拟时间**检查一次。没有命中就不启动模型。

20 分钟是检查间隔，不是事件发生间隔；相邻两次可以都命中，也可以连续多次不命中。取消固定 90 分钟冷却，不在命中后再套冷却门槛。

命中概率由分支本地时间决定。以下为第一版可调产品初值，不是心理学测得的发生率，也不是已经确定的最佳数值：

| 本地时间锚点 | 每次检查命中概率 |
| --- | ---: |
| 00:00 | 0.08 |
| 03:00 | 0.03 |
| 06:00 | 0.10 |
| 09:00 | 0.25 |
| 12:00 | 0.35 |
| 15:00 | 0.30 |
| 18:00 | 0.40 |
| 21:00 | 0.25 |

这些是**每次 20 分钟检查的概率**，不是每小时强度；新实现不再沿用旧 `hazard` 积分，不能把旧 `busy_rate=0.10` 直接解释成相同意义。

举例：如果某一小时内三次检查的概率都约为 0.30，期望命中 0.9 次，至少命中一次的概率约为 `1 - 0.7³ = 65.7%`。这不是每天必须发生多少事件；命中后 DayPlan 仍可以不生成事件。

### 3.2 用平滑曲线连接时段

第一版使用周期性、分段 smoothstep 插值。相邻锚点为 `(t0, p0)`、`(t1, p1)`，当前时刻在二者之间：

```text
u = (t - t0) / (t1 - t0)
s = 3u² - 2u³
p(t) = (1 - s) × p0 + s × p1
```

这样锚点处连续且一阶导数连续，不会到下午或午夜突然跳变；相邻锚点之间不会插值出负概率或超过两端的概率。这里不要求更复杂的曲线库。

21:00 到次日 00:00 也按相邻锚点插值，午夜首尾闭合。概率沿本地 24 小时时刻循环，不通过“上午”“傍晚”等自然语言或活动标题的正则来决定。

第一版不叠加睡眠、忙碌等状态硬开关。夜间概率自然较低；真的正在睡觉，DayPlan 可以认为不应产生变化。以后如需根据工作制度或生活块调整概率，应显式扩展配置，不偷偷恢复 `asleep=0` 等固定规则。

### 3.3 方向权重：命中后更可能出现什么体验方向

第一版固定方向权重：

| direction | 含义 | 初始权重 |
| --- | --- | ---: |
| autonomy | 与选择空间、自主安排有关的体验机会 | 0.25 |
| competence | 与做事、掌握、完成、遇到挑战有关的体验机会 | 0.35 |
| relatedness | 与连接、互动、距离或被理解有关的体验机会 | 0.40 |

这不是事件题库。`relatedness` 不等于吵架或恋爱，`competence` 不等于加班，`autonomy` 不等于拒绝别人；它们也不代表某种需求欠缺，不能成为必须“补足”的任务。

分类方向使用加权抽样，不对分类名称做连续插值。第一版使用固定权重，不添加尚未实现的时间权重字段。以后确需扩展时，再对各方向权重分别平滑插值并归一化；不要为第一版写满所有时段、职业和活动组合。

### 3.4 强度：连续分布，中低强度居多

命中后抽取：

```text
intensity ~ Beta(alpha=2, beta=5)
```

输出在 `0～1` 内，连续变化。该初值的均值约为 0.286，概率密度峰值在 0.2 附近，中低强度更常见，高强度较少但并未被禁止。

强度是本次变化机会的生成参考，不是：

- 人物的情绪值；
- 必须耗费多少分钟；
- 必须改变几块日程；
- 严重程度或重大事故的等级；
- 模型必须执行的影响额度。

同样的 0.6，在不同人物处境下可以有不同意义。强度高也可以是较突出的顺利进展，不应默认制造冲突或灾难。

第一版方向与强度独立抽样，不额外引入按方向、职业分开的强度曲线。参数集中配置，为后续体验调整留出空间。

## 4. 数据契约：模型只收到方向与强度

### 4.1 模型可见的机会

```json
{
  "direction": "relatedness",
  "intensity": 0.34
}
```

新 `EventOpportunity` 只保留这两个字段：`direction` 为枚举，`intensity` 为有限的 `0～1` 浮点数。不要额外填充正负情绪、故事类别、耗时预算、主题题库或未来结果。

当前虚拟时间、骨架计划、当前活动、人物资料、近期经历、已知心理状态和本次协商记录由现有上下文装配器提供。它们不是概率种子的字段，不需要在机会里重复。

### 4.2 后端保留的执行信息

执行记录仍需包含以下信息，但不让模型生成：

- 所属分支与稳定检查序号；
- 原定检查时间、实际抽样/处理时间；
- 随机种子或可重放抽样状态；
- 策略版本、实际配置内容或内容哈希、抽样算法版本；
- 本次计算出的概率、是否命中、命中后的方向与强度；
- 消费状态、对应 Job、失败与恢复信息。

这些只用于正确执行、重放和观测。即使后端有随机种子，也不能预计算并交给模型一份“今天将发生的机会列表”。

## 5. 统一配置

配置位于 `runtime_v1/life_events/policies/default.yaml`，统一由 `load_policy()` 读取。`MOONLIGHTBOX_RUNTIME_LIFE_POLICY_PATH` 只用于覆盖策略文件路径，省略时使用内置配置，**不是启停开关**。已移除旧 `MOONLIGHTBOX_RUNTIME_LIFE_EVENTS_ENABLED` 及代码门控；普通 Runtime 调度始终检查生活推进。分支虚拟钟暂停仍正常暂停时间，这是时间语义而非功能开关。

示意配置：

```yaml
version: life-opportunity-v2
check_interval_minutes: 20

trigger_probability:
  interpolation: periodic_smoothstep
  anchors:
    "00:00": 0.08
    "03:00": 0.03
    "06:00": 0.10
    "09:00": 0.25
    "12:00": 0.35
    "15:00": 0.30
    "18:00": 0.40
    "21:00": 0.25

direction_weights:
  autonomy: 0.25
  competence: 0.35
  relatedness: 0.40

intensity_distribution:
  family: beta
  alpha: 2.0
  beta: 5.0
```

加载时校验时间格式、锚点唯一性、概率范围、方向集合、非负权重及总权重大于零、Beta 参数大于零。错误应明确报告，不能默默使用另一组默认值。

第一版允许修改文件后重启加载，不要求热更新和配置管理页面。“不必改代码”不等于第一版必须在线热更新。

已有机会沿用其冻结配置，尚未抽样的下一检查使用新配置。**幂等身份不能包含策略版本来允许同一检查在换配置后重新抽奖。** 改检查间隔是明确的节拍重设：从最后已完成检查之后安排下一点，不回头补抽；配置中概率就是该间隔的单次概率，不能更改间隔却仍声称每小时发生率不变。

## 6. 调度、时钟和重放

### 6.1 与现有 3 秒扫描的关系

现有 Scheduler 每约 3 秒真实时间检查队列；这不等于每 3 秒抽一次生活机会。它只判断是否到达了下一个 20 分钟虚拟时间检查点。

虚拟钟暂停则不推进；加速则按虚拟经过时间到期。检查节拍以固定 UTC 时间点及序号保存，本地时区只用于计算概率曲线位置。不要用会回拨、重复出现的本地时分作为唯一键。

分支启用时设稳定检查锚点，首次检查在一个完整间隔之后，不因进程重启立刻多抽一次。同一分支、同一检查序号只处理一次。

### 6.2 一次检查的顺序

1. 在短事务中确认检查到期且未处理。
2. 冻结本次配置与随机信息，按该检查时刻的本地时间计算 `p(t)`。
3. 抽 `u ∈ [0,1)`；`u < p(t)` 为命中。
4. 未命中：只推进并持久化检查进度，不创建 Agent Job。
5. 命中：抽方向与强度，持久化机会，并交给现有调度队列。
6. 提交检查进度和机会后，才让 Worker 执行模型。

双 Scheduler、重启和 Job 重试不能重复抽同一检查；唯一约束和事务是保护，不依赖“通常只有一个进程”。机会及其随机结果一旦落盘，恢复使用原结果，不换种子求另一个结果。

## 7. Agent 忙碌、机会堆积与离线恢复

### 7.1 忙碌时不取消推理，也不并发制造多个 DayPlan

概率检查继续按时间推进，但命中只入队。同一分支现有 DayPlan 执行继续运行，收到新机会不使旧工作失效。

下一次接收机会时，一次读取全部尚未处理的机会，附各自到达时间及当前实际时间。模型判断哪些还能融入当前生活、哪些已经没有意义、哪些可以合并。**多个机会不等于必须生成同样数量的事件。**

这里的批次是输入交付方式，不是把一天的随机未来提前交给模型。只允许包含接收时刻之前真实命中的机会。

不追加一个隐蔽的“每日待处理机会数”上限。若输入很长，由统一 Harness 容量管理处理，并保留原记录和处理进度；不可静默丢弃后声称已经完成。

### 7.2 删除自动过期，改成依据最新处境判断

不再在 30 分钟后或生活块结束时自动宣判机会无效。

处理延迟的机会时，DayPlan 同时看到机会时间和当前时间，决定继续、改写、合并或放弃；不能装作自己仍在原来的时刻。后台仍在提交时读取最新计划版本和时间，防止覆盖已提交状态，但不能以“跨块”直接否决内容。

### 7.3 离线恢复不是逐个补跑抽奖

服务停止期间没有真实执行的检查，不在重启后逐个补抽，再据此宣称离线时必然发生了很多事件。

但这不等于禁止补充离线生活。恢复时给 DayPlan 一份**恢复上下文**：最后处理时刻、当前虚拟时刻、期间骨架安排、离线前未结束工作及用户实际输入。它不是新的概率方向字段，也不是一批伪造机会。

DayPlan 整体判断这段时间生活如何推进、哪些内容值得补充、哪些应保持未知；必要时与 Director 讨论。恢复请求复用现有 Job，并用稳定恢复区间去重，不增加一个补演 Agent。

补充的离线经历必须标明“恢复时生成的模拟内容”和实际记录时间，不伪装成当时已经提交的记录。不能编造用户发言、用户同意或过去发给用户的消息，也不能覆盖已有真实分支互动。

已经持久化但尚未处理的机会和草稿继续恢复，不因离线丢弃。处理完恢复区间后，从当前时间之后继续正常节拍，不把遗漏检查堆成瞬时事件风暴。

## 8. DayPlan 与 Director 怎样协作

DayPlan 收到机会后，先结合当前活动、人物生活处境、近期经历、已知心理状态和已有公开沟通理解它。

- 已有信息足以决定普通生活细节，可以自行提出事件及安排。
- 涉及不清楚的当下关切、情绪取舍或关系反应，向 Director 发消息讨论。
- 机会不合适，可以结束为不发生事件；不用为每次命中找一个故事。
- 后续影响尚未明朗，可以记录预计安排和待推进事项，不提前宣告结果。

取消旧“每个模拟事件必须先拿到 Director 许可”的硬规则。协作是否需要、要讨论什么，由 Agent 判断；不是固定往返仪式。

公共通信使用 `send_agent_message`。Director 正在聊天时，消息进入其正常输入队列，不启动另一个 Director，也不取消正在进行的推理；Director 自己判断这件事与用户互动的优先级。

需要等待时沿用检查点保存工作并让出执行，不同步阻塞等待另一个 Agent。现有 `life_responses` / `candidate_accepted` 的恢复接线需要随本次改造一起检查：不得出现模型已经通过公共工具回答了、后端却仍永远等待另一套批准字段的情况。内部关联由宿主保存，不把机会 ID、Job ID、版本号堆进公共工具参数。

事件及计划变化提交成功后，可靠通知 Director。**知道发生变化不等于必须向用户讲述，更不等于用户已经知道。**

## 9. 取消旧的内容限制，保留执行正确性

| 旧设计/字段 | 新设计 |
| --- | --- |
| `max_events_per_day=3` | 删除，不以每日数量拒绝事件 |
| `max_changed_minutes_per_day=30` | 删除，影响范围由 Agent 判断和协商 |
| `cooldown_minutes=90` | 删除，频率由时段概率和检查节拍控制 |
| `ttl_minutes=30` / `expires_at` 硬过期 | 不再用于新机会自动取消；模型根据当前处境判断 |
| `busy_rate` / `available_rate` / `resting_rate` 与 hazard | 替换为固定间隔的时段命中概率曲线 |
| 睡眠、未知强制零概率 | 删除状态硬门槛，夜间通过曲线降低概率 |
| `max_schedule_disruption=none/minor` | 不再作为机会输入或提交上限 |
| 每次最多增加 15 分钟/影响只能在当前块 | 删除，允许跨生活块，必要时影响后续日程 |
| `salience_budget=low` 等强度硬上限 | 替换为连续 intensity，不指定实际心理反应 |
| 不能产生长期影响、必须低影响、必须自行解决 | 不再用固定类型替模型规定结果；结合人物与上下文判断 |
| 每次必须获 Director 批准 | 改为按需协商 |
| 停机后完全不补充生活 | 改为恢复时整体理解和推进，不逐次补抽 |
| 机会自己的 `max_attempts` 重试额度 | 删除遗留双重预算，统一由 Controller / Job 管理 |

同步收窄校验器：保留字段类型、范围与有限数值检查、来源归属、任务取消、幂等、版本冲突、事务一致性。日程仍不能时间倒序或重叠，也不能静默改写已经提交的经历。

取消概率机会的内容上限，不代表取消所有领域正确性：不能凭一句提案认定用户已经同意新约定，不能把预计结果写成完成事实，不能偷偷覆盖既有承诺而不经过相应更新流程。

对事件影响的输出可以保留耗时估计、安排变化、未解决事项等**描述字段**，但不能再用 `le=30`、`Literal["minor"]`、`current_block` 等类型把旧规则藏回来。跨块/跨日变更应交付明确的日期与计划修改，复用 Executor 的版本与事务保护；不允许用一个任意 JSON patch 绕过日程契约。

## 10. 事件的后续也要随时间推进

计划逐渐丰满，不只是不断增加新的起因。已经发生的事情也可能需要继续：任务尚未结束、原估计有变化、某个安排到了复查时点。

DayPlan 可以提出下一次需要关注或推进的虚拟时刻，交给已有 Wakeup。它是**这件事的后续提醒**，与每 20 分钟的随机检查独立，不得拿它覆盖随机节拍或恢复固定冷却。

唤醒时重新看当前情况，决定是否完成、继续、调整或不再跟进。后端不会到预计结束时自动写入“已完成”。不要强制为每次小变化创建复杂生命周期；只有确实需要后续的事件才保留待推进事项。

## 11. 代码改造范围与迁移

### 11.1 概率与配置

- `life_events/policy.py`：替换旧 hazard、状态 rate 和影响预算抽样，增加配置模型、周期曲线、加权方向和 Beta 强度抽样。
- `life_events/policies/default.yaml`：统一初值；应用 Settings 只提供策略路径，不提供开关。
- `life_events/scheduling.py`：固定虚拟节拍、检查去重、命中入队、忙碌批次和恢复区间处理。扫描线程不跑模型。

### 11.2 持久化

优先扩展现有 `LifeOpportunityRow` 和现有分支运行状态，不建立另一套消息、任务或 Agent 调用账本。

落地时必须有独立的“最后完成检查 / 下一检查”持久化位置，因为未命中也需要推进进度；不能靠最后一个命中机会推断。若现有表不能清晰承载，可增加一条每分支唯一的轻量调度游标记录，这是调度状态，不是新业务 Agent 或消息实体。

检查身份与命中记录使用唯一约束。策略、方向和强度冻结在机会记录中；过期、hazard、attempts 等字段先停止参与新路径，再随迁移清理，不在旧记录上强行伪造新强度。

旧数据迁移规则：

- 已提交经历和计划版本完整保留、可读，不重新生成。
- 尚未激活的旧 hazard 机会明确标记被新版策略替代，不把旧预算换算成 intensity。
- 正在调查或等待回答的旧任务先保留工作、显式完成或暂停；不能部署时静默丢掉。若不能安全续接，显示需要恢复，而非伪装成功。
- 停止创建旧版任务后再删除旧生成路径；旧字段读取兼容不能继续控制新版概率行为。

### 11.3 Agent、提交和通信

- `life_events/contracts.py`：最小化机会输入，移除影响上限类型，表达候选、预计影响及已发生事实的区别。
- `life_events/service.py`、`agent_mode.py`：接入新机会与恢复上下文，仍使用统一 Controller。
- `life_events/delivery.py`：收敛公共消息与等待恢复，移除依赖固定批准字段的必经关卡。
- `life_events/commit.py`：删除次数、分钟、过期与跨块硬拒绝；保留新时刻/版本检查、原子经历和日程提交及可靠通知。
- DayPlan 生活模式 Prompt：解释 direction/intensity 的使用方式、按需协作和逐步发生，不重复 Schema，不加入故事题库。
- Director Prompt：理解收到的是当下协作或已提交变化，不把候选当已发生，不必每次告诉用户。

本次不重建 LightRAG，不重编人物画像，不修改节点范围，不改变聊天时间片策略或表达 skill。概率设置第一版不必新增前端管理页；诊断信息复用现有状态展示和 Phoenix。

## 12. 观测与验收

执行状态保存在数据库；真实模型调用、工具调用和失败分析仍以 Phoenix 为准，不新建 AgentRun/Step/ToolInvocation。

调度诊断记录：检查时间、实际概率、策略版本、命中与否、机会方向/强度、是否处于积累或恢复状态。不要把每个未命中检查创建成一个 Agent trace。Agent trace 关联本批机会，记录放弃、生成、协商、计划提交等结果。

离线冒烟至少覆盖：

1. 锚点概率准确，区间平滑，午夜连续且概率不越界。
2. 相同检查不重复抽样；重启和策略更新不改变已落盘结果。
3. 未命中不调用模型；命中后才抽方向和强度，模型上下文没有未来机会。
4. 固定随机源验证权重选择和 Beta 调用；不以不稳定的小样本频率作为测试成败标准。
5. 虚拟暂停不推进；加速按虚拟时间处理；概率使用分支本地时区。
6. DayPlan 忙时不并发或取消，多个已经到达的机会可一起处理，不要求逐个生成事件。
7. 模型可放弃机会；超过旧事件数、分钟数或跨生活块，不再被旧规则拒绝。
8. 延迟机会交给模型判断，不再自动过期；离线恢复不补跑事件风暴，也不伪造用户参与。
9. 公共通信答复能够恢复原工作；计划/经历提交和通知保持可靠、幂等。
10. 未来结果不被提前记成事实；已有经历及承诺不被无版本检查地覆盖。

正式运行时默认且必需执行本机制，不需要再次同意“启用”。真实体验应先看一天逐渐形成的经历是否自然，再调概率和强度初值；不能为了提高“事件数量”强迫模型生成内容，也不能把离线测试通过称为真实生活效果已验收。

## 13. 最终原则

**提前安排生活骨架，按时间随机提供当下机会，由 Agent 决定具体变化，再随时间逐步形成经历。**

后端控制抽样与执行正确性，不预写故事、不分配情绪、不用固定影响预算替人物做选择。
