# LightRAG 构建失败与自动恢复

## 职责

沿用 Job 层恢复机制。Controller 仍负责 Agent 的单次模型/工具故障；Job 负责整个构建的恢复时机和累计次数；Sidecar 负责判断文档是否完成以及继续原生流水线。禁止在 HTTP 写请求上再叠加盲目重试。

## 写请求结果不确定时

后端每批索引前调用受认证的 `POST /v1/workspaces/{workspace}/documents:status`，只读查询本批固定文档 ID 的状态和 `pipeline_active`。

- 全部 processed 且流水线空闲：直接确认本批完成。
- 流水线仍活跃：不重复提交，Job 进入等待检查。
- 流水线空闲但存在 failed：Sidecar 使用已有失败文档恢复入口。
- 流水线空闲但存在 pending / processing 等中断状态：继续原生处理流水线。
- 只有缺失文档才重新入队；冻结文档内容不一致仍拒绝写入。

索引 POST 超时、断连、429 或服务端失败后，再只读核实一次状态。已经完成则接受结果，仍在运行则等待；其他故障交给 Job。Sidecar 的索引锁占用时直接返回 `lightrag_index_running`，状态查询不等索引写锁。

`processing` 文档不等于活跃任务：活跃性同时参考本进程锁和 LightRAG 的 pipeline busy 标记。不凭等待时长强制夺走流水线。若底层服务永久卡死，需要运维处理，不声称自动修复任意死锁。

## 恢复预算与重启

`jobs/runtime_recovery.py` 保留现有入口，按任务类型声明策略。Runtime 原策略不变；图谱构建新增 `job_recovery` 和 `job_retry_attempt` 检查点字段。

- 临时故障：自动恢复最多 5 次（不含首次执行），指数退避并加入抖动：第 n 次恢复等待区间为 `[15×2ⁿ, 30×2ⁿ]` 秒，n 为已恢复次数。
- Sidecar 仍执行：30 秒后再核实，不消耗故障恢复次数。
- 认证、参数、冻结来源不一致等错误：不自动重试。修正原因后可显式恢复，仍累计次数。
- 次数耗尽：明确终态，不因手动恢复清零额度；需处理原因后重新发起构建。
- 用户取消：退出自动恢复；在途同步请求不能立即强杀，等待其退出，不再开启下一批。Sidecar 可能继续完成已接收的文档；已完成文档保留。

安全状态读取使用统一请求策略，单次最多 10 秒、最多 2 次传输重试，总窗口 40 秒。写入不使用传输重放。Worker 每 5 秒独立扫描恢复，不被耗时构建阻塞；租约未过期不抢占其他 Worker。

同一 Job 恢复保留检查点、累计次数、已确认片段数和进度。重新遍历已确认批次时进度不倒退。故障码保留到 Job，不统一折叠成无法分类的构建失败。

## 页面与部署

Journey 返回构建状态、片段进度和恢复时间，退避期仍保持轮询。人物资料准备栏展示等待、继续检查、终态、取消状态，提供立即恢复和取消；操作期间互斥，失败显示错误并允许再次操作。

后端、Worker 与 Sidecar 需要一同更新并重启，新后端依赖新增状态接口。不存在该接口时明确失败，不降级成盲目重放。无需迁移数据库，不重建现有图谱，不删除原始数据。

## 验证范围

测试使用临时数据库、MockTransport 和伪流水线，不调用真实模型。覆盖丢失写回执、避免重复写入、安全读重试、认证不重试、长时间 busy 不耗预算、退避与耗尽、进度保留、取消、状态查询不被索引锁阻塞，以及 Journey 轮询和前端按钮状态。真实供应商稳定性、进程崩溃后的底层存储一致性不由这些冒烟测试保证。
