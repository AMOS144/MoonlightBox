# LightRAG 时间检索改造：依据、实验与实施路径

日期：2026-09-15  
状态：时间检索适配器已通过真实在线查询验证；节点编译、独立审核及纠正、按节点发布、冻结历史分支与准备任务的代码链路已接通。实际节点仍须用户审核批准，计划及 Director 初始化完成后才允许聊天。本轮验证为离线冒烟与构建，不代表已经完成一次真实七栏目生成和用户验收。实现与验收见第 12 节。

## 1. 要解决的具体问题

项目希望只构建一份昂贵的完整 LightRAG 图谱，同时支持不同节点的人物世界编译：七个 PersonWorld Agent 先理解节点之前的聊天，再利用节点之后的聊天支持、反驳或修订理解。

这要求工具能够可靠地“查节点之前”“查节点之后”，不能仅在问题里加日期，也不能全库取 top-k 后把时间不符合的结果删掉。假设全库最相关的 20 个片段都是后期材料，后过滤即使返回空，也不代表早期没有相关资料。

本次目标是：**让时间范围在候选选择和排名之前生效，复用完整图谱和已有向量，最终返回时间位置明确的原始材料。**

不承诺顺带实现历史图谱还原。一个实体的描述已经融合不同时期信息，限制它关联的原文范围，不会自动把该描述变回历史版本。

### 1.1 能力名称必须准确

正式对外描述为：**时间范围内的原文检索 + 来源约束的图谱辅助定位**。

| 能力 | 本设计是否覆盖 | 当前验证程度 |
| --- | --- | --- |
| 原文候选按消息边界限制 | 是 | 验证图的 380 个 chunk 已全部完成映射；其他存量图须单独回填验收 |
| 实体、关系候选在向量排名前受来源范围约束 | 是，不仅改 mix 的原文向量路径 | 已接入 Sidecar，真实 mix 回放与在线冒烟通过；尚未开放历史分支 |
| 实体/关系描述、向量恢复到历史时期 | 否 | 未实现，也不能由前两项推出 |

后文的“时间检索视图”均指前两项，不是历史事实子图。此前只说“修改了 RAG 部分”不够准确，因为图候选和扩展也已参与实验；反过来称其为“完整图谱按时间还原”也不准确。

## 2. 与人物世界方案的关系

本设计细化并修订 `2026-09-14-node-conditioned-person-world-compilation-design.md` 第 7 节：全库召回后的时间分类只保留为结果校验，不能承担主要时间检索能力。

- PersonWorld 编译仍复用七个栏目 Agent 和统一 AgentLoopController。
- 编译 Agent 可以显式切换 before/after/all，在一次工具循环中进行前段理解与后段复核。
- Director、DayPlan、表达工具的历史资料权限由分支边界限制，不能通过 period 参数放开未来材料。
- 不按节点复制图谱，不新增时间审核 Agent，不为解决检索问题重写 Agent Runtime。

## 3. 查了什么代码，确认了什么事实

### 3.1 项目接入层

改造前：`sidecars/lightrag_sidecar/pyproject.toml` 固定依赖 `lightrag-hku==1.5.6`，`core.py::query` 构造 QueryParam，再调用 `aquery_llm`，没有时间范围接线。现在有 `temporal` 时进入第 12 节的适配器；普通全量查询保留原路径。

`core.py` 创建 LightRAG 时未覆盖向量存储类型；所检查本地实现默认使用 NanoVectorDBStorage。本地实验环境版本为 LightRAG 1.5.6、nano-vectordb 0.0.4.3。

### 3.2 上游公开接口

LightRAG 1.5.6 的 QueryParam 提供 mode、top_k、chunk_top_k、关键词、上下文额度等选项，没有消息时间过滤字段。BaseVectorStorage.query 也未定义时间范围或候选 ID 过滤参数。

来源：[LightRAG v1.5.6 base.py](https://github.com/HKUDS/LightRAG/blob/v1.5.6/lightrag/base.py)。不能依据其他文档中出现过 ids 字段，就假定当前接入版本支持过滤。

### 3.3 底层向量库

NanoVectorDB.query 支持 filter_lambda。其余弦查询先根据过滤条件选择矩阵行，再计算分数、排序并取 top-k。因此可以把时间范围转换成允许的 chunk ID 集合，用这个集合约束候选，而不是结果后过滤。

来源：[NanoVectorDB dbs.py](https://github.com/gusye1234/nano-vectordb/blob/main/nano_vectordb/dbs.py)。正式实现应固定依赖版本，不能将 main 永远视为同一接口。

LightRAG 的 NanoVectorDBStorage.query 当前没有把这个过滤入口暴露出来，所以仍需适配，不是配置一个现成参数即可。

### 3.4 图谱检索不是只有向量路径

LightRAG mix 会结合实体检索、关系检索和原文向量检索，再沿实体/关系的 source_id 选出关联 chunk，之后做截断、合并和上下文组装。

本地检查并调用过 `_build_query_context`、`_find_related_text_unit_from_entities`、`_find_related_text_unit_from_relations`。关联片段有 WEIGHT 和 VECTOR 两种选择方法。

来源：[LightRAG v1.5.6 operate.py](https://github.com/HKUDS/LightRAG/blob/v1.5.6/lightrag/operate.py)。公开 tag 与本地安装文件不能只凭版本字符串假定逐字相同；实验记录源码 hash，后续固定实际适配代码的版本。

**因此只改 chunks_vdb.query 不够。实体/关系 top-k、邻接扩展、关联片段选择和最终上下文都必须检查。**

## 4. 两轮实验与结论

### 4.1 第一轮：隔离合成原型

脚本：`scripts/probe_lightrag_temporal.py`。报告：`2026-09-15-lightrag-temporal-prototype-results.md`。

使用人工二维向量和明确的消息顺序，不访问真实图谱，不调用模型。实际调用 NanoVectorDB 的过滤查询和 LightRAG 的实体/关系 WEIGHT 片段选择函数。

18 项断言通过，主要观察：

| 检查 | 结果 |
| --- | --- |
| 全库 top-1 后过滤 | 早期材料被漏掉，复现旧设计的问题 |
| 向量排名前限制早期候选 | 找回早期材料 |
| 实体/关系选择片段之前过滤 source_id | 未来片段不再挤占早期片段的位置 |
| 同 timestamp 的消息边界 | 用顺序区分前后，不靠时间戳猜测 |
| 空范围、未知来源、交错请求 | 能安全处理，未修改共享图来源 |

它证明具体代码切入点可用，不证明真实映射准确、语义质量达标或完整查询链无泄漏。

### 4.2 第二轮：真实资产映射与 mix 回放

脚本：`scripts/probe_lightrag_real_temporal.py`。

报告与原始计数：

- `2026-09-15-lightrag-real-temporal-audit.md`
- `2026-09-15-lightrag-real-temporal-results.json`

数据库以 SQLite mode=ro 打开，使用项目当前 active Publication 对应的图谱 `1400178b-8e4a-468d-afd1-8e7c12d7aeec`。图、chunk 与三种向量只载入内存。五个源文件运行前后 SHA256 一致。

#### 来源映射

| 项目 | 数量 |
| --- | ---: |
| 全部 chunk | 380 |
| 严格验证后可完整映射 | 200，约 52.6% |
| 重建 Bundle 文本仍不一致 | 154 |
| Bundle 可重建，但 chunk 无法唯一定位 | 26 |

验证方法不是“找到了某句就算成功”，而是：重放真实建图清洗，校验完整 Bundle 文本一致，再验证 chunk 的唯一字符位置，通过字符区间重叠映射到消息。

发现两个具体缺陷：

1. 当前 `_matching_indexes` 用原始 message.content 渲染；建图使用 `build_clean_world_messages` 清理技术载荷和引用署名，两者输入不同。
2. 200 个可完整定位的 chunk 中，192 个截断了头尾消息。181 个使用字符区间映射得到的消息数多于现有完整行匹配。

376 个 chunk 所属 Bundle 的未清洗整段重建不一致，**不等于 376 个 chunk 完全无法找到任何消息**。旧完整行方式实际只有 4 个 chunk 完全没有命中，但这种“有命中”不能证明整个 chunk 的来源范围。

154 和 26 两类残余缺口尚未逐个归因，不能直接宣称全部是空白、别名或某一个清洗版本的问题。

#### 混合检索

使用三个不同的真实已存 chunk 向量作为回放输入，组合 all/before/after 和 WEIGHT/VECTOR，共完成 18 次真实 `_build_query_context(mode="mix")` 执行。

覆盖实体向量召回、邻接关系扩展、关系向量召回、端点实体读取、chunk 向量召回、关联片段选择、上下文截断、合并去重和最终组装。不是仅分别调用三个孤立函数。

实验边界取可映射消息集合的中间时间，前段有 100 个允许 chunk、后段 99 个；一个跨界 chunk 和未映射片段不进入限定范围。12 次限定范围回放的最终 chunk 均无越界，另外 6 次为全量基线。

以上是旧原型实际运行记录，不改写实验结果。后续用户明确要求跨界 chunk 归入 before，按第 6.3 节执行；该新规则尚未重跑验证。原型的跨界排除不是正式实现要求。

#### 实体、关系的排名前过滤：已实际验证

不是仅给 chunk 向量加过滤。真实实验中，实体和关系向量使用同一个 `Vectors.query` 适配方法，执行顺序是：

```python
ix = [i for i, row in enumerate(self.rows) if self.allowed(row)]
mat = self.matrix[ix]
scores = cosine_similarity(mat, query_vector)
chosen = argsort(scores, descending=True)[:top_k]
```

上面为等价伪代码；实际实现见 `scripts/probe_lightrag_real_temporal.py::Vectors.query`。只有 allowed 候选进入相似度计算，不能先取全库 top-k 再判断 allowed。

同一实验资产的候选量如下（这些是排名之前的数量，不是最终回答中出现的数量）：

| 范围 | 实体向量候选 | 关系向量候选 | 原文向量候选 |
| --- | ---: | ---: | ---: |
| all | 704 | 780 | 380 |
| before | 290 | 285 | 100 |
| after | 264 | 246 | 99 |

实体资格取决于来源与允许 chunk 是否相交；关系还要求两端实体和关系本身在请求局部图视图中可见。随后真实 LightRAG 调用这些适配器执行 mix 检索和图扩展。

本实验不是在线 Nano 适配器已经实现过滤：它读取真实已存向量，用自有只读适配器实现前置过滤和余弦排名。第一轮单独验证过 Nano 的 filter_lambda。因此“底层可以做”与“真实混合链路可以接入”各有实验依据，但正式版本仍要把二者接好。

before/after 表中的集合建立在严格映射成功的部分 chunk 上，不代表完整历史语料召回。实验向量来自三个真实 chunk，不是通过在线模型生成的用户问题向量，不能据此声称自然语言相关性效果已经验收。

#### 暴露的新风险

全局实体/关系描述仍进入最终上下文。前段候选图中 160 个节点、后段 148 个节点的原始来源包含范围外 chunk。这是跨期描述风险数量，不是已逐条证明的未来事实数量。

此外，允许参与排名的实体/关系**仍使用全时期内容生成的既有向量**。即使输出时隐藏全局描述，排名也可能受后期材料影响。这不违反“在允许候选中排序”的契约，但说明它不是纯历史语义排名。七栏目回顾式编译可接受这种跨期线索定位；不能把它当作无未来信息参与的历史预测实验。

**返回 chunk 无越界，不等于整份模型上下文无越界。**

### 4.3 实验没证明什么

- 没有在线调用自然语言 embedding、关键词抽取或回答模型；已存向量回放只验证检索接线。
- 真实回放使用请求局部自有存储视图和余弦排名，并非已经修改线上 Nano 适配器。
- 没有覆盖 sidecar HTTP、aquery 缓存与正式超时取消。
- 没有修好全部来源映射、实现跨界片段重嵌入或测量生产性能。
- 使用较大 token 额度观察检索路径，不能据此推断生产额度下的召回质量。

## 5. 为什么判断能做

判断依据不是“模型应该能理解日期”，而是以下已观察事实：

1. **候选前置过滤能改变检索结果。** 底层已有实现，合成实验复现了后过滤失败和前过滤成功的差异。
2. **图谱有关联来源。** 可以通过来源集合约束实体/关系相关 chunk，不必重新抽取整张图。
3. **真实 mix 内部链路接受请求局部存储视图。** 原型已驱动实际上下文构建完成，不需要修改 Agent 的循环。
4. **部分真实来源可严格回填。** 已对 200 个 chunk 证明了字符位置与消息映射，说明可以工程化补齐来源索引，但剩余部分仍是阻塞项。

准确结论是：**检索适配的技术可行性得到验证，生产可用性尚未验证。** 剩余风险集中在数据来源准确性、跨期合并描述、缓存隔离及维护成本，而不是时间过滤在技术上无从下手。

## 6. 正式改造从哪里入手

### 6.1 第一优先：消息到 chunk 的来源索引

在现有 Bundle/消息映射基础上扩展，不再靠每次查询重新猜原文：

```text
图版本 / 文档版本 / chunk_id
→ chunk 在冻结清洗文本中的字符区间
→ 相交的 message_id、消息顺序、完整或部分覆盖
→ 消息时间及映射状态
```

建图时就记录清洗后每条消息的字符范围，以及 chunk 对应位置。若现有切分接口不给偏移，需要在切分结果产生时记录并验证，而不是后面用模糊搜索猜位置。

必须处理同内容重复消息、chunk 重叠、截断消息、跨 Bundle carry-in，以及清洗后为空的内容。不要只用 min/max 时间作为唯一边界依据；同一时间的多条消息以批准的消息序列分界。

存量回填策略：

1. 精确文本和唯一位置可证明的，直接回填，不重算向量、不重抽图。
2. 不一致的保存诊断类别，核对冻结清洗输入和版本；有明确依据才能补映射。
3. 仍无法证明的标 unresolved，不进入受限结果。必要时重新切分/嵌入相关原文，保留旧 chunk 与图来源的关联，不能更换 ID 后让图上的 source_id 失联。

这一步可能需要局部重建索引，但不是默认全图重新抽取。来源集合本身也要检查是否被上游数量限制截断；被截断时不能宣称来源覆盖完整。

#### 6.1.1 已有哪一半，缺少哪一半

`ConversationBundleMessage` 已保存 Bundle 与原始 message_id 的对应及 ordinal。现在缺的是：消息在**送入建图的冻结清洗文本**中占据哪些字符，以及 LightRAG 最终实际使用的 chunk 占据哪些字符。

不要用原始数据库 content 的字符位置替代清洗后位置，也不要用查询时的最新清洗规则覆盖旧文档。清洗版本、冻结文本 hash 和切分版本属于映射身份。

#### 6.1.2 新数据：拼接时记录消息范围

改造 `world/bundles.py` 的渲染、拼接结果，在已有 BundleMessage 映射上增加范围信息。实际代码以当前清洗入口 `build_clean_world_messages` 的输出为准：

1. 保留消息原始 ID 和冻结的消息顺序。
2. 渲染一条清洗后消息，得到将要入库的真实文本。
3. 在追加到 Bundle 前记下当前位置 start，追加后记下 end。
4. 追加分隔换行；换行不归入任何消息正文。
5. 完成后冻结 Bundle 文本、hash、清洗/渲染版本及所有消息范围。

范围统一使用 Python Unicode 字符索引和左闭右开区间 `[start, end)`；不是 UTF-8 字节数，也不是前端 JavaScript UTF-16 索引。涉及其他语言或 tokenizer 时必须显式转换并验证。

示例：

| message_id | 清洗渲染行在 Bundle 的范围 |
| --- | --- |
| m1 | [0, 40) |
| m2 | [41, 100) |
| m3 | [101, 150) |

消息范围包含实际渲染的时间、发送者前缀和正文，不意味着能从该范围直接切回未经清洗的原始 content；回查原文仍通过 message_id。两条消息内容相同也不影响，因为位置来自拼接过程，而不是搜索得到的。

#### 6.1.3 新数据：切分时记录 chunk 范围

在 sidecar 的切分适配入口保留每个最终 chunk 的文档 ID、chunk ID 和原文区间。优先适配当前切分器，使它在输出内容时同时输出位置，不另造一套与真实入库 chunk 不同的切片。

若选择由项目生成预切分 chunk，必须先核对固定版本 LightRAG 的接收入口，确认它不会再次切分、改变内容或重新分配不受控 ID。不能假定存在可直接使用的 API；这仍属于正式实现前要补的接口契约测试。

逐个检查：

```python
frozen_bundle_text[chunk.start:chunk.end] == chunk.content
```

如果 tokenizer 的切片无法无损对应 Unicode 边界，不能凭 token 数量累加出字符位置；切分适配需要保留原文本偏移并以实际文本验证。若存在附加标题等非原文内容，应单独标记，不把这些文字虚假映射到消息。

该第一版范围模型适用于连续原文片段。将来若采用合并非连续段落的切分，应明确记录多个 source spans，不能用一个大区间把中间未包含的消息也算进来。

#### 6.1.4 用区间求交建立对应关系

假设 chunk A 为 `[0, 80)`，chunk B 为 `[60, 150)`：

| chunk | 对应消息及覆盖情况 |
| --- | --- |
| A | m1 完整；m2 部分 |
| B | m2 部分；m3 完整 |

判断依据是区间有交集：

```python
overlap_start = max(message.start, chunk.start)
overlap_end = min(message.end, chunk.end)
has_overlap = overlap_start < overlap_end
```

记录 overlap 范围及是否完整覆盖。后端由 message_id 取得冻结顺序和时间，再判断 chunk 位于节点前、节点后或跨界。**这是来源位置计算，不是正则事实判断，也不需要 Agent 推断。**

只碰到消息前缀也属于部分覆盖，不能告诉模型“这里包含完整消息”。扩展上下文时再按 message_id 读取相邻消息，并重新应用查询范围限制。

#### 6.1.5 存储方式与 ID 一致性

优先扩展现有 BundleMessage 映射，另增加 chunk 来源记录；不为每个节点重复保存同一套来源。

| 记录 | 最小内容 |
| --- | --- |
| BundleMessage 范围 | bundle_id、message_id、ordinal、rendered_start/end、渲染版本 |
| Chunk 来源 | graph_version_id、文档版本/hash、实际 chunk_id、start/end、content_hash、切分版本、映射状态 |

chunk 与 message 的交集可以由这两类记录计算；只有性能测量证明需要时，才物化倒排对应关系，并使其可从基础记录重建。消息时间摘要可加索引，但不能替代精确消息边界。

同一实际 chunk_id 必须在 text_chunks、向量库和图谱 source_id 中一致。若上游允许同一 chunk ID 对应多个文档来源，要保留全部来源位置，不以单一外键覆盖；无法区分的跨期重复片段应标记歧义，不能只选择有利于当前查询的一个时间。

构建完成前做一致性核验：每个可检索 chunk 的内容 hash、来源记录和存储 ID 对得上；图谱引用不存在的 chunk 要报数据问题。映射和图谱跨存储无法靠一个数据库事务原子写入时，先记录构建中状态，全部校验通过才把相应时间索引版本标为 ready。中断重试按版本和 chunk ID 幂等补齐。

#### 6.1.6 存量数据的回填步骤

1. 固定图版本，读取已持久化 Bundle 文本、BundleMessage 顺序及实际 chunk；不改图谱。
2. 尝试用能确认的清洗/渲染规则恢复每条消息的冻结渲染行。整段拼接必须等于已有 Bundle 文本。
3. 在该冻结文本中定位 chunk。唯一位置可直接建立映射；重复位置只有在原切分顺序、偏移等额外信息能证明时才消歧，不能简单取第一个。
4. 按区间求交回填来源，并核对内容 hash；保存此次回填版本和诊断状态。
5. 无法证明的保持 unresolved，区分文档缺失、重建不一致、片段非连续/变换、位置歧义等原因。尚未归因的不能直接写成某个确定原因。

现有实验的 200/380 是第二、三步通过严格校验的结果，不是新建图的目标覆盖率。剩余 180 个必须继续处理或明确阻止完整时间检索，不能静默丢掉后宣称检索完整。

局部重切会产生新 chunk 时，必须先设计旧来源到新来源的关系：可以增加只读的检索派生映射，不立即改原图 source_id；若要更新正式图谱来源，则按已有资产版本与批准策略执行。不能把新片段冒名存到旧 ID 下，也不能删除旧 chunk 让原图悬空。

#### 6.1.7 边界情况与验收

- carry-in 消息在多个 Bundle 有多个范围，但保留相同 message_id；查询合并时去重，映射不能丢来源位置。
- 清洗后无正文但渲染行仍有时间/发送者时，记录实际范围；完全未写入文档的消息标 omitted，不伪造 chunk 引用。
- 同秒消息、重复正文、emoji、中文、换行与 chunk 重叠均检查字符位置。
- 无法定位的内容不能被 Bundle 开头的几条消息替代。
- 重启和重复导入不生成冲突映射；更改清洗或切分版本不复用旧范围。

最小验收包括：拼接文本完全一致；每个 chunk 切片等于其内容；区间交集正确区分完整/部分消息；同时间 before/after 无误；图、向量、原文 ID 一致；残余未知明确可见。先完成这些，才能让允许 chunk 集合成为可信的时间检索输入。

### 6.2 第二优先：请求局部时间检索视图

在 sidecar 内增加独立模块，建议命名 `temporal_retrieval`，职责只包括范围解析、存储视图和上下文输出。

```text
批准边界 → 允许消息 → 可检索 chunk
→ 三路候选检索与图扩展 → 片段合并 → 输出契约校验
```

查询范围由请求显式携带并绑定图版本，不写入全局 rag 实例、不修改共享 graph，不 monkey patch 安装依赖。每个并发请求持有自己的不可变范围对象。

向量适配使用 Nano 的前置过滤能力；实体与关系向量也应根据其来源是否与允许 chunk 相交来过滤，避免上游 top-k 全被另一时期占满。邻接扩展必须继续使用同一范围视图。

#### 6.2.1 从 chunk 范围传到图候选的明确算法

首先区分目前真实存在的关联和待补能力：

```text
实体/关系 --source_id--> chunk             已存在
chunk --full_doc_id--> Bundle             已存在
Bundle --BundleMessage--> 原始消息列表      已存在
chunk --精确位置交集--> 原始消息范围         尚未完整建立
```

对本次真实已发布图谱另做只读核验：704 个实体、780 条关系全部带 source_id；实体来源引用共 1,935 次、关系来源引用共 1,589 次，均能找到对应 chunk，未发现悬空引用。引用可解析不等于来源完整，也不等于描述中的每句话都有独立来源。

设 C 是按第 6.1 节确定的允许 chunk 集合，S(x) 是图记录 x 的来源 chunk 集合：

1. 实体候选 E：满足 `S(entity) ∩ C 非空` 的实体。
2. 关系候选 R：满足 `S(relation) ∩ C 非空` 且两端实体在 E 中的关系。这个保守端点条件可能损失来源缺失的关系，必须记诊断，不能宣称该关系不存在。
3. 实体向量检索先限制到 E，再排名；关系向量检索先限制到 R，再排名。
4. 获取端点、度数、邻接边时使用同一个请求视图，不在图扩展阶段重新读无限制邻居。
5. 选择关联原文时使用 `S(x) ∩ C`，然后才运行 WEIGHT/VECTOR 和数量截断。
6. 直接 chunk 向量检索先限制到 C，再排名；合并后检查所有返回片段的来源权限。

E、R 是“与所选时期原文有来源关联的候选”，不是断言实体/关系在那个时期有效。特别是后来的回忆可能描述早期事实；这属于 Agent 对内容所指时间的判断，不能由消息时间过滤自动完成。

例如某条任职关系同时引用早期 A 与晚期 C，before 可以让它作为线索参与检索，并只返回 A；但其合并描述可能包含离职结果，其向量也可能包含后期语义。必须按第 6.4 节处理输出，不能将来源过滤当作描述还原。

#### 6.2.2 实现和验收中不允许混淆的地方

- 必须分别记录实体、关系、chunk 排名前候选量，不能只统计最终原文条数。
- 保留“高相似度范围外候选挤占 top-k”的反例测试，实体和关系也要覆盖，不只测原文。
- 验证图扩展、两种关联选择算法和最终上下文，不把单个存储函数通过当作整链完成。
- 候选过滤可通过原图上的请求局部索引/视图实现；原型复制内存图只是隔离实验手段，不要求生产每次复制整图。
- 不因候选过滤成功而重算所有实体/关系向量。若以后要求真正历史向量与事实版本，应单独设计并评估成本，不隐含在本次改造承诺内。

关联 chunk 的 WEIGHT/VECTOR 选择均只看允许来源，并在数量预算生效之前裁剪候选。之后的最终结果检查是防漏，不是主要检索机制。

### 6.3 第三优先：跨边界片段完整归入 before

用户确认的规则：**跨界 chunk 不丢弃，完整归入 before，复用原内容、chunk ID 和向量。** 不把跨界裁剪、派生片段、重新 embedding 或派生缓存作为本方案的前置任务。

| chunk 中消息的位置 | 查询归属 | 返回方式 |
| --- | --- | --- |
| 全部在节点前 | before | 原片段 |
| 同时包含节点前、后消息 | before | 完整原片段，标记 mixed |
| 全部在节点后 | after | 原片段 |
| 来源无法确定 | unknown | 显式报告映射缺口，不冒充已知跨界片段 |

边界按批准的消息顺序计算，包括同时间消息的前/后选择。对于精确可映射的 chunk，只要存在一条节点前消息就进入 before；仅当全部消息在节点后时进入 after。all 包含全部可用片段，按 chunk ID 去重。不要把同一个跨界 chunk 同时算作两份独立的前后支持材料。

这同时改变第 6.2 节用于过滤实体、关系和原文候选的集合 C：before 集合包含 mixed chunk，而非先把它排除再在最后补回。三路检索必须使用相同的集合定义。

返回区分 `assigned_period=before` 与 `boundary_relation=mixed`，并保留逐消息前后位置。before 是查询分组，不再保证返回片段的每个字都说在节点前。PersonWorld Agent 可以完整阅读该场景，但应辨认哪一部分属于节点后，不能把它当成纯前段原话；审计展示跨界数量与消息位置。

该规则适用于节点画像编译的材料检索，不自动把片段中的节点后事件写入当时的角色记忆。第 6.4 节的 Runtime 输出权限仍需单独执行；不能把编译时允许完整阅读理解成角色可以提前知道未来。此处不改变节点时间或把节点移动到 chunk 末尾。

缓存身份加入分组策略版本，例如 `mixed_to_before_v1`，避免命中旧跨界排除结果。验收应检查完整片段保留、原 ID/向量复用、三路候选同步分组及 mixed 标记；不能继续用“before 绝无节点后消息”作为新策略断言。

### 6.4 第四优先：处理全局描述

把两种用途分开：

**PersonWorld 编译检索**允许全量理解，可返回单独的 `global_graph_clues`，明确它来自跨期合并、不是指定时期事实；`temporal_fragments` 才是经过范围约束的原文。Agent 根据原文判断结论适用时期。裁剪过的来源不能给未裁剪描述提供虚假历史背书。

**Runtime 历史检索**不返回跨期合并描述，依赖节点画像、分支记忆和时间内原文。图谱内部可以帮助定位候选，但输出中不能附带其未来描述、未来关系标签或仅在未来出现的实体详情。

这应当是两种明确的工具输出权限，由调用方后端绑定，不能让模型传一个参数就切换为无限制模式。

### 6.5 第五优先：缓存、错误与生命周期

- 查询缓存身份包含图版本、来源索引版本、边界/范围 hash、权限模式、检索参数和 embedding 版本。
- 编译 before、after、all 不可复用错误范围的结果；旧无时间缓存不得直接命中新接口。
- 节点画像检查点继续由现有 AgentLoopController 维护；不要在 sidecar 另建任务重试系统。
- 索引未完成、图版本不符、来源覆盖不完整、供应商失败要区分；不能都返回空数组。
- 前置过滤结果为空时安全返回，不进入不支持空矩阵的底层路径。
- Phoenix 记录候选量、各路贡献、映射排除量、跨界量、缓存命中和错误，不再只记录“没找到”。

## 7. 是否要 fork LightRAG

不建议现在直接维护一个大 fork，也不应承诺完全不碰上游内部接口。

优先做项目自有、版本锁定的 sidecar 适配层，复用现有检索算法与存储，通过请求局部视图传入限制。原型证明这种接法有可能成立，但正式化还需要补齐协议方法、错误、异步生命周期与缓存。

若固定版本的内部接口无法稳定支持必要能力，再维护小型补丁，范围限定为候选约束传递和上下文输出边界。补丁放入可审查版本管理，不直接编辑 `.venv/site-packages`。升级 LightRAG 必须跑对应回归，而不是只改版本号。

不建议复制整个 operate.py 到业务代码。对少数私有函数的依赖要集中封装，记录兼容版本和源码 hash；上游改签名时明确失败，不能悄悄退回无时间限制查询。

## 8. Agent 看到的接口

```json
{
  "question": "她在这个阶段如何回应临时的工作安排？",
  "period": "before"
}
```

模型只表达调查问题与需要的时期。图版本、目标人物、节点、时区、允许消息和权限模式由后端提供。需要继续调查时可使用分页引用，不让模型传巨大 ID 集合。

返回至少区分：指定时期原文、映射覆盖限制、是否还有结果、跨期图谱线索（仅编译权限可见）。返回时间表示“消息说在什么时候”，不自动解释“内容所指的事情发生在什么时候”。后一层仍由栏目 Agent 判断。

## 9. 改动面和成本

| 区域 | 改动 | 是否重做核心能力 |
| --- | --- | --- |
| Bundle/切分与来源持久化 | 增加精确映射、存量回填及版本 | 不重做七栏目；部分原文索引可能需补建 |
| sidecar 查询/存储适配 | 三路前置过滤、图扩展约束、结果权限 | 中等偏大，是主要代码工作 |
| LightRAG 图谱资产 | 复用；检查来源完整性 | 不默认重抽整个图 |
| 工具服务 | 传入编译边界与权限，完善错误 | 不让 Agent 填内部 ID |
| PersonWorld Prompt | 正确使用 before/after 和跨期线索 | 不增加审核 Agent |
| Runtime 工具 | 固定历史权限，阻止未来描述输出 | 不重写 Director/DayPlan 调度 |
| 缓存与诊断 | 时间身份、覆盖率、三路计数 | 复用统一恢复和 Phoenix |

成本主要是来源映射工程、适配维护，以及确实需要修复的存量索引，不是每个节点重新付费抽取全图。跨界 chunk 直接归入 before，不为此重算 embedding。实际延迟取决于允许集合规模与过滤实现，当前实验不足以给出生产耗时承诺。

## 10. 实施顺序和上线条件

1. **只读资产诊断补齐**：把 154/26 类缺口进一步归因，确定回填和局部补建策略。
2. **来源索引写入与回填**：新建图可准确追溯，旧资产显式标识覆盖状态。
3. **独立 sidecar 时间查询端点或明确的新契约**：三路过滤、输出权限、缓存一并接线；不替换所有旧查询后才发现兼容问题。
4. **少量在线真实问题验证**：前后分别查工作、关系、作息；检查实际 embedding、关键词和上下文输出，以及 HTTP、取消、失败重试。
5. **接入节点画像编译**：七个 Agent 同循环完成前段理解与后段复核，审核资料能定位原文。
6. **接入受限 Runtime**：验证节点后材料不会随查询或时间推进进入历史角色记忆。

上线必须同时满足：来源映射可靠或缺口明确阻断、三路无范围绕过、受限上下文不含跨期描述、缓存不串范围、并发不串请求、错误可恢复。不能因为本次 18 次回放通过就打开历史分支创建。

## 11. 最终判断

**可以做，理由是已有可操作的存储过滤入口、图谱来源关联和真实 mix 回放结果，而不是对 Prompt 的期待。**

原型阶段只有 52.6% 的 chunk 完成严格映射。第 12 节记录的实现已解决这批真实资产的映射缺口，并将全局描述与受限原文分开返回；这不代表生成了历史实体描述或历史向量。

时间检索已经过真实在线冒烟；完整节点人物画像的质量、发布和历史聊天仍需独立验收，不能把检索成功等同于历史分支完成。

## 12. 2026-09-15 实现与验收记录

### 12.1 已落地代码

- `world/bundles.py` 在冻结文本生成处记录每条消息的字符范围、原始 ID、时间与来源序号；`world/jobs.py` 将这些位置随文档交给 Sidecar。
- `imports/message_order.py` 统一起点调查与来源索引的同秒顺序：时间、导入 ID、原始消息编号、消息 ID。旧 Bundle 的文本顺序保持不变，字符位置与时间顺序独立保存，不能拿旧 UUID 排序替代批准边界。
- Sidecar `source_index.py` 保存独立 `moonlight_source_index.sqlite3`，绑定来源版本、顺序契约和 embedding 模型/维度。索引重试幂等，来源或位置冲突拒绝覆盖。
- `source_aware_chunking` 调用真实上游切块器，保留其位置到 chunk KV；不改变切块内容、ID 或已有向量。编码清理同步使用 LightRAG 的清理函数，不拿清理前坐标映射清理后文本。
- `temporal_query.py` 为每次请求构造独立图视图。chunk、实体、关系均在 Nano 相似度排序之前限制候选；邻居、度数、source_id 与 VECTOR 二次取向量使用同一范围。
- Sidecar `/query` 增加后端使用的 `temporal` 契约。当前仅支持完整 `mix`；时间查询不复用全图结果缓存。来源、边界、模型或适配器不匹配返回明确错误，映射失败不伪装为检索为空。
- `context/references` 返回带时间位置的原文；`global_graph_clues` 仅给编译权限，明确是全时期描述。历史 Runtime 查询只允许 `before`，不返回全图描述；mixed 原文暂不下发给 Runtime，并记录排除数量。

编译器的 mixed 规则没有删：完整跨界 chunk 归 before，纯后段归 after，不裁剪、不重嵌入。Runtime 的知识权限与编译器不同，不能因为归入 before 就把其中未来原话交给角色。

### 12.2 七栏目内部接线

`person_world/node_scope.py::NodeCompilationScope.from_approved` 读取已批准起点，核对图谱来源与调查的完整消息顺序一致，再绑定查询范围。模型只能填写问题和 `period`，不能填写 source_version、included_count 或 access。

Coordinator 可接收此作用域：历史编译不默认加载项目最新画像，七栏从前段入口起步，恢复身份包含节点范围；跨节点恢复直接拒绝。同一栏目在原有 Controller 内查 before/after，不新增七个核验 Agent。

七份独立 Markdown 分别增加本栏的时间调查目的，公共 `_temporal.md` 只维护边界解释。`save_section_work` 保存当前草稿、复核问题、修订发现与下一步，随 artifacts 检查点保存，压缩时保留，审核工作记录不混入栏目正文。精确检索引用直接恢复对应原消息，不再依靠整行文本包含匹配。

### 12.3 存量映射实测

验证图版本：`1400178b-8e4a-468d-afd1-8e7c12d7aeec`。

### 12.5 本轮补齐的任务入口与 Runtime 防线

新增 `person_world/node_jobs.py`，后台任务类型为 `person_world_node_compile_v1`，由普通 background/all Worker 领取。创建请求只引用图版本、已批准调查、批准 hash 与幂等键；后端验证消息顺序、前后相邻消息、来源版本，再冻结任务范围。执行前重新校验，期间修改起点不会让旧任务悄悄编译新边界。

API 前缀为 `/api/projects/{project_id}/world-agent`：

- `POST /node-compilations`：接收 `graph_version_id`、`investigation_id`、`preview_hash`、`idempotency_key`，返回 Job 身份。
- `GET /node-compilations/{job_id}`：返回该项目任务状态、错误、冻结范围和完成后的 `profile_v3` 草稿、调查报告、工作记录。跨项目请求返回 404。

任务使用同一图谱，不克隆 workspace、不改写全量 Profile 或活动 Publication。七栏目仍由 `PersonWorldCoordinatorV3` 调用，节点范围随运行保存；普通任务恢复使用相同 Job 检查点。取消信号接入 Controller。输出保存在已有 `PersonWorldProfileDraft`，任务成功仅代表草稿交付，`failed_sections` 单独保留，不表示七栏目全部成功或已经获批。

Runtime 的 `snapshot_sources.temporal_retrieval_scope` 从冻结快照读取范围，并核对完整消息前缀与图来源。非 `latest_profile` 快照缺少此契约时明确报错，不能退回全图检索。查询强制 `access=runtime, period=before`，不随虚拟日期扩展。`routine_evidence.query_frozen_history` 是 Director 记忆、Planner 资料与表达资料共用的语义检索入口：历史查询只还原精确映射的纯前段消息，不透传 Sidecar 的全图 context；mixed 被排除或来源覆盖不全时返回 partial，而不是完整召回。

历史聊天分页也改为使用同一冻结消息清单，跨导入批次和同秒边界不再退回 EventNode 或字符串 source_id 比较。以上为受限快照的消费契约；对应生产与审核入口现见 12.6，不能跳过审核直接使用。

本轮后端相关冒烟 51 项、另行运行 Runtime 基础冒烟 18 项、Sidecar 23 项通过；新增测试覆盖固定查询权限、前缀顺序、错误引用拒绝、全图 context 不透传、草稿任务不复制图、幂等键冲突和执行前范围重验。Runtime 冒烟中一条仍使用旧 EventNode/LoRA 创建接口的用例已改为验证落库批准边界决定时钟，不恢复旧接口。没有重新执行完整七栏目在线编译，也没有变更生产 Publication 或分支数据。

### 12.6 节点审核发布到历史分支聊天

起点确认后，在原工作台启动 `person_world_node_compile_v1`。它复用七栏目 Coordinator 和共享图谱，输出绑定 `node_scope` 的独立草稿。离开页面或刷新不会另起任务；失败可通过现有 Job 恢复入口继续。

1. **审核版本**：`POST /world-agent/node-drafts/{draft_id}/review` 将草稿固化为节点 PersonWorldProfile。内容 hash 相同则复用；栏目重试改变内容后生成新的审核版本，不修改旧会话基线。
2. **审核页面**：`/projects/:projectId/node-profiles/:profileId` 使用现有七栏目展示和选择组件、Revision 对话侧栏。用户可逐步讨论、确认 Profile Patch、Graph Patch 和最终批准；不新增另一套纠正 Agent。
3. **独立发布**：`POST /world-agent/node-profiles/{profile_id}/approve` 必须提交页面所读内容的 `approval_hash`。失败栏目、尚在运行的重试、变化的草稿或发布基线都会阻止批准。纠正发布也核对同一个节点边界，不允许退回全量作用域。
4. **节点指针**：`PersonWorldProfile.node_boundary_hash` 和 `WorldPublication.node_boundary_hash` 区分全量及各个节点。全量读入口显式限定 NULL；每个节点只有一个 active Publication。节点发布不替换全量发布、不退役别的节点所用共享图，也不触发全量起点重新调查。
5. **创建分支**：提交 `investigation_id + preview_hash + publication_id + title`；不要求 EventNode 或 LoRA。后端核对发布范围与来源，原子保存 Branch、历史 Snapshot、暂停的 VirtualClock 和唯一 bootstrap Job。
6. **历史 Snapshot**：固定图/画像/Publication ID、精确原文前缀、来源版本、cutoff 与时区。运行材料剥离调查引用和审计层；Runtime 原文工具继续执行冻结前缀检查，不能把 after 原文暴露给角色。
7. **准备后聊天**：进入既有 `/branches/:id/preparing`，由既有准备任务生成 DayPlan 并完成隔离的 Director 初始化。准备期间不能发消息，失败显示可恢复状态；准备成功后开放聊天。后续节点纠正不改变已创建分支的 Snapshot。

旧 `/branches/new` 入口统一回到起点工作台，不保留“历史链路未接通”的死路，也不允许绕过审核。真实用户的批准不能由开发测试替代。

### 12.7 入口范围继承补齐

统一恢复入口为 `node_scope.inherited_node_scope` / `NodeCompilationScope.restore`：从运行、画像和纠正会话的持久化范围恢复，核对图版本、来源版本、顺序前缀、相邻消息、时区与计数。多个宿主对象范围不同，或一个有节点范围而另一个丢失范围，均报错；不能默认为全量。恢复既有工作不重新读取“用户现在选择的起点”。

| 入口 | 范围与写入规则 |
| --- | --- |
| 七栏目首次编译及工作恢复 | 保留原有范围；栏目工具只读本节点冻结的栏目快照，不再回退项目活动画像 |
| 独立栏目重试 | 从 run 与 draft 同时恢复范围；节点任务允许使用 ready/superseded 共享图，只修改自身草稿，使用版本及待审核状态的 CAS 保护 |
| Revision 调查 | 会话从基线画像继承范围；图查询带时间作用域，原文加 before/after 标记，模型上下文解释同一节点边界 |
| 纠正后栏目重编译 | 同样传入时间检索、原文分类、本节点栏目快照与公共时间协议；不能通过纠正回到全量模式 |
| Graph Patch 检索与批准产物 | 检索继承范围；v3 批准产物只可将同一时间边界显式绑定到直接派生图，来源不变；缺少已批准节点产物时不能走全量编译兜底 |
| 当前栏目与有效纠正工具 | 栏目只读本节点快照；纠正先按批准节点筛选再限量，并校验来源、时间边界。同节点的图修订可延续纠正，其他节点或全量纠正不混入 |
| Runtime 初始化、对话与表情用法 | 使用 `ordered_frozen_message_ids`，历史前缀先验证再读取；不能各自用时间/UUID 排序代替同秒导入顺序 |

节点调查本身仍看全量资料，这是发现候选起点所需的权限，不应机械地加 before 限制。现有 latest_profile 末端分支保留读取兼容，不修改它们的时钟、聊天或背景数据。

本轮 73 项后端冒烟通过，包括节点草稿重试不写全量 Profile、缺失/跨节点范围拒绝、恢复不依赖后来选择、旧读取链路回归；相关代码通过 Ruff 与编译检查。没有执行付费在线七栏目重编译。

执行入口的范围继承与 12.6 的产品流程现在共用同一契约。Revision 仍以 PersonWorldProfile 为基线；独立节点 Draft 先固化为审核 Profile，再进入既有纠正流程。全量批准入口继续拒绝节点产物，节点专用入口负责发布。
